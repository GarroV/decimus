# Dodo Audit Service

Здесь собрано всё, что нужно, чтобы начать строить сервис выездных проверок пиццерий: методика, рабочий движок, правила, выведенные на двух боевых проверках, и границы первого шага.

Материал не гипотетический. В августе 2026 через этот движок прошли две реальные проверки в Белграде — 82 фотографии, два отчёта, оба ушли партнёрам. Всё, что здесь написано про правила и грабли, вылезло на этих прогонах.

## Что уже работает

Это не пакет для старта — сервис построен и проверяется прогоном. Ниже то, что
есть сегодня; порядок чтения документов — следующим разделом.

| Поверхность | Чем поднимается | Что делает |
|---|---|---|
| Телеграм-бот | `docker compose up -d` | Проверка целиком: старт, фиксация с кадра или словами, правка в чате, завершение с PDF и письмом. Завершённая проверка и её кадры уходят в историю сами |
| Движок оценки | `engine/audit.py`, `engine/report.py` | Считает процент, букву и разбивку по зонам; собирает PDF и письмо. Оценку не считает больше никто |
| База проверок | `make db-up`, `make migrate` | Завершённые проверки, находки, кадры, справочник точек. Изоляция партнёров ключами схемы; завершённое от правки закрыто политиками |
| MCP-сервер | `docker compose up -d` (сервис `mcp`) | Чтение истории через Claude, правка методики версиями и загрузка исторических проверок из старых отчётов (`docs/14-history-import.md`), доступ личным токеном. Слушает только петлю и наружу не публикуется; снаружи доступен туннелем — сервис `tunnel`, профиль `tunnel` |
| Веб-админка | `make web-up` | Реестр проведённых проверок сети, карточка проверки со снятием и письмо партнёру по ней: пересобирается движком, правится на месте, выгружается файлом. Одна команда поднимает базу, накатывает схему, сеет демо-историю и печатает адрес. Вход по логину и паролю; учётки заводит `make web-user`, запрет после перебора снимает `make web-unlock`. Слушает только петлю: наружу выходят туннелем — `docs/12-web-admin.md` |
| API чтения для Swarm | вместе с веб-сервисом, сервисный токен из `api.tokens` (`tools/api_token.py`, D388) | Рейтинги РС/РКО, собираемость, топ нарушений и принятые проверки сети для главной Swarm — только чтение, по сервисному токену. Swarm этих данных у себя не хранит (D387). Контракт — `docs/12-web-admin.md`, раздел «API чтения для Swarm» |
| Мини-апп обхода (прототип) | вместе с веб-сервисом, кнопка в боте по `BOT_WALK_URL` | Рабочий экран аудитора в Telegram: какие зоны ещё не осмотрены, что было на этой точке в прошлый раз, и запись прямо здесь — фото, пункт, класс, рекомендация, сведения о визите. Чат остаётся рабочим путём, обе дороги пишут в одну проверку — `docs/13-walk-mini-app.md` |
| Демо | `docker compose --profile demo up -d` | Синтетический англоязычный набор, боевых данных не касается |

**Главный сквозной сценарий:** аудитор идёт по точке → присылает кадр с комментарием
или пишет словами → бот предлагает пункт, класс и зону → аудитор подтверждает
нажатием → в конце «Завершить» → PDF и текст письма партнёру, а следом сама
проверка и её кадры ложатся в историю. Оценка в отчёте совпадает с тем, что
выдаёт движок на тех же данных, — это проверяется прогоном, а не глазами; база
без настроек — законная конфигурация, и тогда бот работает без истории.

**Где живёт (с 26.09.2026).** Прод — VPS Contabo, каталог `/srv/decimus`:
бот, админка, MCP, база, MinIO — один проект compose `decimus` за общим Caddy
площадки. **Адреса для людей — Cloudflare Worker'ы, это постоянный вход
(D304):** админка `https://decimus.vasiliy-garro.workers.dev`, MCP
`https://decimus-mcp.vasiliy-garro.workers.dev`. До сервера Worker идёт
туннелем, а не через интернет (`docs/08-deploy.md` §8.9); адреса
`*.<ORIGIN_DOMAIN>` остаются служебными и запасным путём. Ночной бэкап VPS уходит restic'ом на
MUSPELHEIM: база, MinIO, `state`, `.env`. Стенд разработки остаётся на
MUSPELHEIM (mac-stands). Как устроено, как обновлять и как переносили —
[`docs/08-deploy.md` §8](docs/08-deploy.md#8-прод-на-linux-vps--переезд-с-muspelheim).

**План.** Постоянный домен на Cloudflare — позже; с ним меняются
`GOOGLE_REDIRECT_URI`, `GOOGLE_MAIL_REDIRECT_URI` и `BOT_MCP_URL`. Старые
боевые контейнеры на MUSPELHEIM гасятся после проверки владельцем (#352,
скрипт из #395). Адреса возврата в Google Console и смена учётки из #395 — за
владельцем.

**Чего пока нет:** режим проверки по чек-листу отложен до первой версии,
справочника точек в интерфейсе нет — название вводится текстом.

## Что лежит рядом

- `docs/00-map.md` — карта кода; начинайте с неё, если пришли в код.
- `engine/` — рабочие скрипты. Это не черновик, это то, чем собраны оба отчёта.
- `docs/_legacy-skill.md` — `SKILL.md` исходного плагина. Устарел и противоречит `docs/`, оставлен как след происхождения.
- `data/` — данные предметной области: чек-лист на 136 пунктов, критерии, зоны, ставки вычетов. **Вне git** — см. «Чего нет в git».
- `examples/` — две настоящие проверки: `inspection.json`, фотографии и собранный PDF. Эталон **формата**, но не формулировок — см. `examples/README.md`. **Вне git.**
- `src/db/` — где живут завершённые проверки: Postgres по `DATABASE_URL` и кадры в S3-совместимом хранилище по `S3_*`. Схема правится только миграциями (`src/db/migrations/`). Поднять базу рядом с ботом и накатить схему одной командой — `make db-up` (снести — `make db-down`); локальное хранилище для смоука — `make storage-up` / `make storage-down`. Имена переменных и что они значат — `.env.example`.
- `tests/methodology/` — синтетическая методика, **по которой идёт набор тестов**. Боевая лежит вне git (D002) и её правит управляющая компания: пока тесты читали её, добавленное в данные слово красило нашу сборку, а формулировки и названия зон утекали в публичный репозиторий через исходники тестов (T141, T146). Совпадают с боевой только идентификаторы — коды пунктов и зон, классы, ставки; формулировки, названия зон, критерии и подсказки выдуманы. Подробности — `tests/methodology/README.md`. Тесту, которому нужна именно боевая методика (боевой якорь на `examples/`, полнота каталога управляющей компании), её дают фикстуры `live_data_env` / `live_data_copy` под меткой `requires_data`.
- `demo/` — синтетический **англоязычный** набор для показов: вымышленная точка, свой чек-лист на 10 пунктов, свои ставки вычетов и своя карта кадров (`demo/data/photo-cues.md`). Боевых данных не касается. Наполняется `make demo`; демо-стенд в контейнере — `docker compose --profile demo up -d`. Английский там не только в данных: профиль ставит демо-боту `BOT_UI_LANG=en`, поэтому по-английски он и здоровается, и ведёт мастер начала проверки. Карта кадров нужна показу не для полноты: без неё в демо не работает быстрый путь (D063), и на первом же комментарии показ упирается в модель — то есть в чужой ключ.

## Чего нет в git

Репозиторий публичный, поэтому в нём нет данных управляющей компании и партнёров
(D002, `docs/furca/decisions.md`):

- `data/` — боевая методика: чек-лист на 136 пунктов, критерии D1/D2/D3, зоны, ставки
  вычетов, карта слов. Правит её управляющая компания; в клон она не приезжает.
- `examples/` — две настоящие проверки в Белграде с фотографиями и PDF партнёрам.
- `.env` и секреты — по образцу `.env.example`; настоящие значения лежат у владельца.

Где взять `data/` и `examples/` — **у владельца**: в документах репозитория другого
источника не названо. Рабочую копию для блока `tools/worktree_new.sh` собирает из
основной, копируя их оттуда; в чистом клоне копировать нечего.

**Что делать без них.** Почти всё работает и так:

- тесты идут на синтетической методике `tests/methodology/` (`tests/methodology/README.md`),
  боевой не читают; тестам, которым она нужна, прогон ставит пропуск и печатает
  «ПРОГОН НЕПОЛНЫЙ» — пропуск не зелёный;
- `make demo` собирает демо-проверку на синтетическом наборе `demo/` и печатает оценку,
  отчёт и письмо — движок, PDF и письмо проходят целиком;
- не работают только боевые якоря: `make regress` падает с «папки проверки нет», а замеры на
  боевых данных (`make fastpath` и ещё несколько) пишут «замерять нечего» — они читают
  `data/` и `examples/`, которых в клоне нет.

## С чего начать

1. Прочитать `docs/02-domain.md` и `docs/03-recording-rules.md` — без этого код будет правильным, а отчёты неверными. Код — с `docs/00-map.md`.
2. Поднять окружение и убедиться, что проверки зелёные (в свежем клоне):

```bash
make bootstrap            # .venv и зависимости, нужен Python 3.12
make fmt lint types       # формат, линт, типы
.venv/bin/pytest -q       # тесты без базы; пропущенное прогон называет вслух
make demo                 # движок, PDF и письмо на синтетических данных
```

3. Есть `data/` и `examples/` (у владельца) — сверить движок с эталоном:

```bash
cd examples/belgrade-1
python3 ../../engine/audit.py score      # ожидается 97.5%, оценка A
python3 ../../engine/report.py pdf       # соберётся в examples/belgrade-1/reports/
```

Имя PDF детерминировано (пиццерия + аудитор + дата), но сборка кладёт отчёт в `reports/`
рядом с проверкой и приложенный эталон не трогает. Сверять — с ним; `--out` пишет ровно
по указанному пути, поэтому эталон им не перекрывать. Без `examples/` — `make regress`
скажет, чего не хватает; ответ «зелёный» он без них не даёт.

4. Только после этого браться за `docs/06-mvp-bot.md`.

## Команды проекта

Единственный список — `Makefile`; у каждой цели в строке объявления стоит
описание после `##`, а собранная таблица всех целей — в
[`docs/inventory.md`](docs/inventory.md#makefile) (обновляется `make map`). Здесь
только то, чего оттуда не видно.

- До коммита обязателен `make check` (формат, линт, типы, тесты, мёртвый код, границы
  модулей). Он **требует поднятой базы** (`make db-up`): без неё прогон краснеет 360
  ошибками, и это правильно — раньше те же тесты молча пропускались, а гейт считался
  зелёным (#207). Без базы тесты идут мягкой целью `make test`: пропущенное она называет.
- Правили код, файл, маршрут, инструмент MCP, переменную окружения, миграцию или цель
  Makefile — `make map` и результат в тот же коммит: `tests/test_docs_map.py` краснеет, если
  карта и инвентарь отстали.
- `make regress` — движок на эталонных данных; ожидается дословно: `belgrade-1` → 97.5%, A,
  5×D1; `belgrade-2` → 97.0%, A, 6×D1. Разошлось — регрессия.
- `make test-honest ARGS=tests/<файл>.py` — тот же прогон без кеша байткода, для проверки
  тестов порчей. Отдельной целью: в обычном прогоне это замедляет набор в разы.
- `make demo-down` сносит **только** демо-стенд: напрашивающаяся `docker compose --profile
  demo down -v` унесла бы вместе с демо боевой бот и том состояния идущих проверок.
- `make loadcheck-live` — **платный** прогон с настоящими вызовами модели; без `--yes` показывает
  только план и цену. Замерено 03.09: разбор кадра 5.3 с медиана, под очередью из восьми
  одновременных 7.8 с, отказов нет.
- Замеры без расхода (`make fastpath`, `make processhint`, `make zonewords`) детерминированы;
  числа на дату — в `docs/furca/blocks/recognize.md`. Вывод `make zonewords` несёт боевые
  названия зон — в репозиторий его не кладут.
- Подключение к MCP: поднять — `make mcp` (в стенде он идёт сервисом `mcp`), к Claude — мостом
  `tools/mcp_bridge.sh`; доступ с чужой машины — `make mcp-outside` (петлю он проверкой не
  считает и отказывается на ней зеленеть). Сколько инструментов и какие — `docs/inventory.md`.

Тесты с живой базой требуют `DATABASE_URL`; без неё они уходят в пропуск, и
покрытие выходит ниже — это не регрессия, а неполный прогон.

## Два правила, которые не обсуждаются

**Оценку не считать заново.** Проценты, буква, разбивка по зонам, сроки — только через `audit.py score`. Один отчёт уже ушёл партнёру с буквой, которую модель поставила «на глаз», а не посчитала.

**Модель предлагает, фиксирует человек.** Никакая запись не попадает в отчёт без подтверждения аудитора. Причины — в `docs/05-calibration.md`.
