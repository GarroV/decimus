# Runbook: сломалось — куда смотреть и что делать

Для человека, который подключается к проду без нейросетей: зашёл на сервер, понял, что живо, нашёл, что сломано, починил или понял,
что звать владельца. Каждая команда здесь сверена с кодом и compose-файлами репозитория; чего проверить на живом проде нельзя, помечено
«не проверено на проде». Значений ключей и паролей в документе нет и быть не должно: только имя переменной и место, где она лежит.

Как устроены сами выгрузки — в их документах ([`24-dodois.md`](24-dodois.md), [`09-pointer-api.md`](09-pointer-api.md),
[`17-aggregators.md`](17-aggregators.md), [`15-ratings.md`](15-ratings.md), [`20-training.md`](20-training.md)); как обновлять прод и
откатывать — [`08-deploy.md`](08-deploy.md); бэкап и восстановление — [`33-backup-restore.md`](33-backup-restore.md).

**Правило для того, кто добавляет выгрузку или фоновую задачу:** без раздела здесь она не готова. Это держит тест
`tests/test_runbook_covers_jobs.py`: файл задачи, не названный в этом документе, роняет сборку.

## Первые 10 минут

### 1. Зайти на прод

```bash
ssh contabo                      # имя хоста — в ~/.ssh/config у владельца; адреса в репозитории нет
cd /srv/decimus                  # клон репозитория, ветка main, рядом .env (права 600) и compose.edge.yaml
```

Все команды ниже — из `/srv/decimus`. Чтобы не печатать длинное, один раз в сессии:

```bash
dc() { docker compose -f docker-compose.yml -f docker-compose.prod.yml -f compose.edge.yaml "$@"; }
sql() { dc exec -T db sh -c 'PGOPTIONS="-c default_transaction_read_only=on" psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB"'; }
```

`dc` — compose прода: основной файл, прод-надстройка и надстройка площадки (без неё `web` теряет сеть прокси и снаружи 502,
[`08-deploy.md`](08-deploy.md) §8.1). `sql` читает SQL из stdin, база открывается **только на чтение** (`default_transaction_read_only`):
`echo "select count(*) from maps.loads" | sql`. Все запросы ниже — `select`, их можно гонять без опаски.

### 2. Что живо

```bash
dc ps                            # состояние и health каждого сервиса
docker ps --format '{{.Names}}\t{{.Status}}'
```

Сервисы прода (проект compose `decimus`, имена контейнеров `decimus-<сервис>-1`):

| Сервис | Контейнер | Что делает | Как проверяется здоровье |
|---|---|---|---|
| `bot` | `decimus-bot-1` | телеграм-бот **и все фоновые задачи** (таблица ниже) | `pgrep -f "python -m src.bot"` внутри образа (`Dockerfile`, HEALTHCHECK) |
| `web` | `decimus-web-1` | админка и API | запрос `/inspections` внутри контейнера должен дать 200 (`docker-compose.yml`) |
| `walk` | `decimus-walk-1` | мини-апп обхода | `tools/walk_healthcheck.py` |
| `mcp` | `decimus-mcp-1` | MCP-сервер для Claude | `tools/mcp_healthcheck.py` |
| `db` | `decimus-db-1` | Postgres 16 | `pg_isready` |
| `storage-live` | `decimus-storage-live-1` | хранилище кадров (MinIO) | `mc ready local` |

`web-link`, `link` и `tunnel` в проде не поднимаются (профиль `legacy-link`). Внешний смоук после любых работ — `scripts/prod-update.sh`
делает его сам (админка `/login` — 200, MCP без токена — 401); отдельно, по петле сервера, те же две проверки смотрят адреса,
которые печатает `dc port web 8267` и `dc port mcp 8265`.

### 3. Логи каждого сервиса

Docker держит по 5 файлов по 10 МБ на контейнер (`x-logging` в `docker-compose.yml`): старше — уже стёрто.

```bash
docker logs --since 2h decimus-bot-1 2>&1 | tail -n 200        # бот и фоновые задачи
docker logs --since 2h decimus-web-1 2>&1 | tail -n 200        # админка
docker logs --since 2h decimus-walk-1 2>&1 | tail -n 200       # обход
docker logs --since 2h decimus-mcp-1 2>&1 | tail -n 200        # MCP
docker logs --since 2h decimus-db-1 2>&1 | tail -n 100         # база
docker logs --since 2h decimus-storage-live-1 2>&1 | tail -n 100   # хранилище кадров
docker logs -f decimus-bot-1                                   # следить вживую, Ctrl+C — выйти
```

Фоновые задачи пишут в лог бота строками с префиксом своего предмета («Оценки карт», «Dodo IS», «Обучение», «рейтинги», «дозагрузка»):
`docker logs --since 6h decimus-bot-1 2>&1 | grep -E "Dodo IS|Оценки карт|Обучение|рейтинги|агрегатор|дозагрузка"`.
Строка `ERROR`/`Traceback` — упавший заход; строка `WARNING` — ожидаемый сбой (внешний сервис), задача живёт и повторит.

### 4. Экран здоровья в вебе

«Администрирование → **Подключения**» (`/administration?tab=connections`, только главный админ): цвет на каждое подключение — OpenAI, бот,
хранилище кадров, Google, Pointer, ночные сборы (карты, агрегаторы, таблица контроля, обучение), iSpring, Dodo IS по странам. Зелёный — работает,
жёлтый — не в срок или не удалось проверить, красный — сбой, серый — нечего сказать (не настроено или ещё не шло). У пробуемых плиток есть «Проверить».
Ниже таблица «Данные рейтингов по стране и источнику» (пустые и неполные источники). Подробно — [`27-web-administration.md`](27-web-administration.md).
Плитка «Ночной бэкап» серая всегда: бэкап делает сервер, и его исход сюда не приходит.

**Если плитки жёлтые «Проверка давно не шла — проверьте, жив ли бот»** — встал бот (проверяет он): `dc ps`, `docker logs decimus-bot-1`.

### 5. Куда приходят тревоги

Только владельцу: сообщение в канал FURCA (доходит до него в Telegram). Шлёт бот (`src/notify/furca.py`) через `FURCA_NOTIFY_URL` и
`FURCA_SECRET` из `/srv/decimus/.env`; людям продукт сам не пишет ничего. Тревоги:

- смена цвета подключения (красный/жёлтый и «снова работает», `src/health/alerts.py`); входы Dodo IS по странам склеены в одно сообщение;
- суточный сбор агрегаторов с ошибками (`src/ratings/aggregators/alert.py`);
- первый сбой загрузки обучения после удачной (`src/bot/learning_loader.py`);
- пустой или неполный источник «страна × источник» (`src/health/coverage_check.py`, раз в сутки после 10 часов);
- отдельным проектом `vps-infra` — сбой ночного бэкапа сервера (раздел «Бэкап»).

**Тревог нет — это не значит «всё хорошо».** Канал мог быть не задан: в логе бота на старте строка «Оповещения владельцу о сбоях подключений:
включены / выключены», и та же строка есть на экране «Подключения» (плитка канала, код `alerts_channel` в `health.checks`). В демо
(`WEB_DEMO=1`) тревоги не уходят никогда. Проверка — глазами по экрану и таблицам из разделов ниже раз в день, пока канал не подтверждён.

### 6. Блокировки и «заход пропущен»

Каждая фоновая задача берёт замок базы на время захода (таблица ниже). В логе «заход ведёт другой процесс — пропущен» — обычное дело при
выкатке (два бота на минуту) и не ошибка. Если строка идёт часами, замок держит зависший процесс:

```bash
echo "select objid as ключ_замка, pid, granted from pg_locks where locktype = 'advisory'" | sql
```

`ключ_замка` — число из таблицы ниже (`125_0001` читается как `1250001`). Живой замок сам отпускается базой, когда умирает соединение:
`dc restart bot` снимает все замки бота.

### 7. Чего не делать

- `docker compose down -v` и любое удаление томов (`decimus_pgdata`, `decimus_state`, `decimus_storage-data`, `decimus_methodology`) — это данные.
- Дамп поверх рабочей базы не восстанавливать ([`33-backup-restore.md`](33-backup-restore.md)).
- Не перезапускать `bot` при `write_failed` у входа Dodo IS (раздел «Dodo IS: входы»): пара ключей живёт только в памяти бота.
- Не читать и не печатать значения из `.env`, `vault.secrets`, `service_keys`; проверять «задано / не задано» формой `[ -n "$VAR" ]` и экраном.
- Не катить прод вне окна и без «да» владельца ([`08-deploy.md`](08-deploy.md)).

## Фоновые задачи бота

Все запускаются при старте бота (`src/bot/app.py`, `asyncio.create_task`) и живут в контейнере `decimus-bot-1`; упавший бот — это сразу
остановка всего ниже. Замки — `src/db/job_lock.py` (ключ в `pg_locks.objid`); агрегаторы берут свой замок в `agg_store.collector_lock` тем же приёмом.

## Dodo IS: входы по странам

**Симптом.** На «Администрирование → Dodo IS» строка страны красная («Вход истёк», «Сбой связи») или жёлтая («Открыто не всё»); в «Качестве» у
страны пустые ячейки; владельцу пришла тревога «Dodo IS». Что это за вход и как он выпускается — [`24-dodois.md`](24-dodois.md).

**Где смотреть.**

```bash
echo "select country, state, reason, units_open, units_total, refreshed_at, access_expires_at, checked_at from dodois.logins order by country" | sql
docker logs --since 6h decimus-bot-1 2>&1 | grep "Dodo IS"
```

`state`: `ok`, `partial`, `expired`, `failed`; `reason` — код из таблицы «Причина» в [`24-dodois.md`](24-dodois.md) (там же «что делать» по каждому коду).
Ключей в базе этих таблиц нет: они в `vault.secrets`, значения не читать.

**Частые причины.**

1. Вход страны истёк или отозван (`refresh_rejected`, `expired`) — учётку закрыли или ключ продления прожил дольше срока. Чинится **новой ссылкой**, не кодом.
2. Не заданы ключи приложения Dodo IS (`no_keys`): `DODOIS_CLIENT_ID` / `DODOIS_CLIENT_SECRET` — на экране «Ключи и API», запасной путь — `.env`.
3. Не открывается шифрование ключей (`no_tokens`): нет или сменился `SECRETS_KEY` в `.env`.
4. Dodo IS не ответил (`network`, `rate_limited`) — повторится в следующий час.
5. `write_failed` — пара ключей получена, но не записалась в базу; живёт в памяти бота до его перезапуска.

**Что сделать.**

- «Проверить сейчас» в панели страны — внеочередная проверка входа (продлевает, если пора). Команды в консоли для входа нет.
- Нужна новая ссылка: «Выпустить ссылку» на вкладке «Dodo IS» (главный админ), отправить её коллеге страны вручную — код его не пишет.
- Перенести готовый вход вместо ссылки: `docker exec -i decimus-bot-1 python tools/dodois_import.py --country <XX> --by <логин> < token.json` (JSON на stdin, разово; значения ключей не печатает; не проверено на проде).
- `write_failed`: **бот не перезапускать**; посмотреть базу (доступна ли, `dc ps`), после починки следующий час запишет пару сам.

**Когда звать владельца.** Вход истёк у страны (новая ссылка — действие коллеги страны и главного админа); у нескольких стран разом (`refresh_rejected`
у всех — вероятно, сменились ключи приложения у Dodo IS); `no_tokens` (трогать `SECRETS_KEY` нельзя без владельца: потеряется всё в `vault.secrets`).

## Dodo IS: данные для «Качества»

**Симптом.** На «Качестве» у страны пусто или старые месяцы: продажи, оценки клиентов (КР), РКО/РС по неделям, заказы агрегаторов. Тревоги **нет**.

**Где смотреть.**

```bash
echo "select country, kind, started_at, ok, rows, left(error, 120) as error from dodois.metric_loads order by started_at desc limit 40" | sql
echo "select country, kind, max(started_at) filter (where ok) as last_ok from dodois.metric_loads group by 1, 2 order by 3 nulls first limit 30" | sql
docker logs --since 12h decimus-bot-1 2>&1 | grep "Данные Dodo IS"
```

Виды (`kind`): `sales`, `aggregators`, `kr`, `ratings`. Страна с истёкшим входом **пропускается молча**: сначала смотреть раздел «Dodo IS: входы».

**Частые причины.** Вход страны не `ok` (метрики ключей не продлевают); у вида `error` с кодом ответа Dodo IS; у страны нет работающих пиццерий (`no_units`); бот
не жил сутки (заход идёт раз в час, вид по стране — если последняя удача старше 20 часов).

**Что сделать.** Починить вход страны (раздел выше) — метрики подтянутся сами на ближайшем заходе. Принудительно собрать страну можно только кодом
(готовой команды нет, это пробел, он записан в #1572). Пример для страны `RS` — читает базу и ходит в Dodo IS только `GET`-ами, печатает исход каждого вида
и пишет в `dodois.metric_loads`:

```bash
docker exec decimus-bot-1 python -c "
from datetime import UTC, datetime
from src.db import dodois_logins as logins
from src.db.space import SYSTEM_SPACE, acting_space
from src.dodois import metrics
with acting_space(SYSTEM_SPACE):
    login = logins.get_login('RS')
    print(metrics.collect_country(login, list(metrics.parse.KINDS), today=datetime.now(UTC).date()))
"
```

Не проверено на проде: команда сверена по сигнатурам (`get_login`, `collect_country`, `parse.KINDS` существуют), но не запускалась. Она **не берёт замок** — не запускать в минуту захода.

**Когда звать владельца.** Данные за прошлые месяцы не восстановились после починки входа; нужна тревога на этой задаче (решения нет, #1572).

## Карты (Pointer)

**Симптом.** Блок «Оценки на картах» на «Рейтингах» и карта в «Качестве» не обновляются; плитка «Pointer — ночной сбор оценок с карт» жёлтая или красная;
старый «снимок на дату». Устройство — [`09-pointer-api.md`](09-pointer-api.md), типовые ответы API — там же, «Типовые сбои Pointer».

**Где смотреть.**

```bash
echo "select at, outcome, companies, ratings, left(error, 160) as error from maps.loads order by at desc limit 10" | sql
echo "select count(*) filter (where backfilled_from is not null) as история, count(*) as пар, max(topped_up_on) as последний_дозабор from maps.reviews_sync" | sql
docker logs --since 6h decimus-bot-1 2>&1 | grep -E "Оценки карт|История карт|Оценки карт поштучно|Ключ Pointer"
```

Экран: «Подключения» → «Pointer» (проба ключа, **только по кнопке «Проверить»**) и «Pointer — ночной сбор оценок с карт» (цвет по `maps.loads`: упало — красный, старше 26 ч — жёлтый, 52 ч — красный).

**Частые причины.**

1. Нет ключа: в логе при старте «Оценки карт: POINTER_API_KEY не задан — загрузка выключена». Задача карт стартует, **только если `POINTER_API_KEY` есть в окружении бота**;
   ключ, поставленный лишь на экране «Ключи и API», её не включает (расхождение записано как #1583; по коду, на проде не проверялось).
2. Ключ не принят (`Pointer ответил 401/403`) — отозван или заменён.
3. Лимит 1 запрос в секунду (`Pointer ответил 400`, «слишком много запросов») — рядом шёл ручной запуск.
4. Pointer не отвечает (`Pointer недоступен`) — повторится в следующий час.
5. Расхождение сверки поштучных оценок со счётчиком карточки — в логе строка «Оценки карт поштучно…» (предупреждение), людям не уходит.

**Что сделать.**

- Ключ: «Администрирование → Ключи и API → Наши ключи к внешним сервисам → Pointer» (в базе, шифруется) **и** `POINTER_API_KEY` в `/srv/decimus/.env`; после правки `.env` — `dc up -d bot`
  (пересоздать контейнер с новой средой; значения не печатать). Затем «Проверить» на экране.
- Руками (внутри бота, замок **не берётся** — не запускать, пока бот сам грузит; паузу в 1,1 с между запросами код держит сам):

```bash
docker exec decimus-bot-1 python -m src.ratings.maps                  # снимок на сегодня
docker exec decimus-bot-1 python -m src.ratings.maps history 12       # история на 12 месяцев разом
docker exec decimus-bot-1 python -m src.ratings.maps reconcile        # сверка оценок поштучно со счётчиком
docker exec decimus-bot-1 python -m src.ratings.maps link             # связать филиалы с пиццериями
```

Эти четыре формы — все ветки `src/ratings/maps.py:main`. Не проверено на проде: запуск живым ключом не делался.

- Филиал не пиццерия (тестовая карточка, учебный центр): `maps.companies.excluded_reason` — пишет разработчик, не оператор.

**Когда звать владельца.** Ключ отозван или просрочен (новый выдаёт поддержка Pointer по заявке владельца); сверка расходится неделю подряд; нужно расширить набор стран.

**Когда звать владельца.** Площадка изменила разметку (нужна правка кода); закрылась страна; сбой держится больше суток при живом домашнем сервере.

### Ретранслятор на домашнем сервере (Migros и Яндекс Еда)

Эти две площадки закрыты с адреса прод-сервера, поэтому запрос идёт через маленький контейнер на домашнем сервере MUSPELHEIM (`deploy/migros-relay/`, адрес в `MIGROS_RELAY_URL`
в `.env` прода; http допустим только на адреса tailnet).

- **Симптом:** в журнале сбора у `migros_yemek` / `yandex_eda` «домашний сервер не отвечает», «Migros ответил HTTP 403 (через домашний сервер)»; в тревоге добавлена подсказка «проверь, не спит ли он».
- **Проверка с прода:** `curl -s -m 10 -o /dev/null -w '%{http_code}\n' "$MIGROS_RELAY_URL/health"` из оболочки, где переменная задана (значение не печатать; ответ 200 — ретранслятор жив). Не проверено на проде.
- **Проверка на домашнем сервере** (доступ `ssh muspelheim`, у владельца): контейнер называется по compose `decimus-migros-relay-relay-1` (имя выведено из `name:` и сервиса `relay` в `deploy/migros-relay/compose.yaml`, на сервере не сверялось): `docker ps` и `docker logs decimus-migros-relay-relay-1`.
- **Что сделать:** разбудить сервер (домашний сервер засыпает и сам не просыпается); перезапускать контейнер или сервер самостоятельно не нужно — перезагрузка этой машины делается только особым способом, это дело владельца.
- **Обновление ретранслятора** — порядок и команда в [`17-aggregators.md`](17-aggregators.md) («Обновить ретранслятор»): сначала ретранслятор, потом прод.
- **Когда звать владельца:** всегда, если дело в самом домашнем сервере.

## Календарь срока отчёта

**Симптом.** У проверяющего нет события «Отправить отчёт по проверке …» после завершения проверки; событие осталось на старой дате после переноса; у человека в «Настройках» (плитка Google) сказано «календарь отключён или не ответил — переподключите». Задача — `src/bot/calendar_loader.py`, суть — [`39-calendar-deadline.md`](39-calendar-deadline.md). Завершение проверки к Google не обращается, поэтому сбой календаря проверку не ломает.

**Где смотреть.**

```bash
echo "select user_id, google_email, connected_at, problem, problem_at from calendar_grants" | sql
echo "select inspection_id, due_date, title, synced_at from calendar_events order by synced_at desc limit 20" | sql
echo "select occurred_at, user_id, outcome, target from action_journal where action = 'calendar_sync' order by occurred_at desc limit 20" | sql
docker logs --since 2h decimus-bot-1 2>&1 | grep -E "календарь"
```

`problem` — код причины Google, не текст: `invalid_grant` (человек отозвал доступ у Google или он истёк), `secret_unreadable` (ключ не открылся: сменили `SECRETS_KEY`), `SERVICE_DISABLED`/`accessNotConfigured` (в проекте Google Cloud выключен Calendar API), `insufficientPermissions` (в окне согласия не отмечено право на события), `http_5xx` и имена сетевых ошибок (временное, повторится само).

**Частые причины.** Проверку вёл человек без календаря или без привязки бота (`bot_bindings`) — события нет по замыслу; проверка не из УК или заведена задним числом (`origin` не `field`) — события нет по замыслу; нет `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` или `SECRETS_KEY` в окружении бота — проход пропускается (в логе «нет GOOGLE_CLIENT_ID/SECRET»); срок давно прошёл (больше суток) — новое событие уже не ставится.

**Что сделать.** `invalid_grant` и `secret_unreadable` — человек подключает календарь заново в «Настройках»; `SERVICE_DISABLED` — включить Calendar API в проекте Google Cloud (шаги — «Что сделать владельцу» в `39-calendar-deadline.md`). Бот: `dc ps`, `dc up -d bot`, лог. Принудительно прогнать проход нельзя и не нужно: он идёт каждые 5 минут и сводит всё, что разошлось.

**Когда звать владельца.** Calendar API выключен или скоуп не добавлен в экран согласия Google; Google потребовал проверку приложения; `SECRETS_KEY` менялся.

- Уведомления экшн-планов внутри приложения — записи в базе, показываются на экране.

**Симптом.** «Подготовить письмо» не создаёт черновик; ошибка при привязке Google; шаблон письма не сохраняется.

**Где смотреть.** Лог `decimus-web-1` в момент нажатия; плитка «Google» на «Подключениях» (в ней видно, включён ли вход Google и привязана ли почта); [`27-web-administration.md`](27-web-administration.md), раздел «Письма и уведомления».

**Частые причины.** У человека не привязан Google с правом на почту (привязывает он сам, кнопка «Привязать Google»); адрес возврата `GOOGLE_MAIL_REDIRECT_URI` не заведён в Google Console; ошибка шаблона (переменная не из списка) — отказ до создания черновика.

**Что сделать.** Перепривязать Google в профиле; поправить шаблон («Сбросить» создаёт новую версию со встроенным текстом); `.eml` как запасной путь доступен без Google.

**Когда звать владельца.** Адрес возврата или клиент OAuth в Google Console — настройка владельца.

число строк по таблицам; в 09:00 приходит сводка. Подробности и восстановление по шагам — [`33-backup-restore.md`](33-backup-restore.md).

**Симптом.** Владельцу пришла тревога проекта `vps-infra` («Бэкап VPS (дата): …», «Проверка восстановления бэкапа VPS: …»); или сводка в 09:00 не пришла.
Плитка «Ночной бэкап» в приложении серая **всегда** — это не сбой.

**Где смотреть** (на сервере, от root; пути заданы `vps-infra/backup/lib.sh`):

```bash
ls -la /var/backups/vps/                     # локальные копии по датам; файл .pushed — ночь ушла на MUSPELHEIM
cat /var/lib/vps-backup/last_error           # причина последнего сбоя (файла нет — сбоя нет)
cat /var/lib/vps-backup/last_restore         # итог последней пробы восстановления
systemctl list-timers 'vps-*'                # таймеры vps-backup, vps-restore-test, vps-backup-report
journalctl -u vps-backup.service --since "2 days ago" | tail -n 50
```

Не проверено на проде: команды взяты из `vps-infra/backup/README.md` и скриптов, на живом сервере в рамках этого документа не запускались.

**Частые причины** (из контролей `vps-backup.sh`): MUSPELHEIM спит или недоступен («внешняя копия не ушла», локальная копия есть и догрузится следующей ночью); контейнер базы не запущен; дамп сжался
(меньше 50% вчерашнего) или в нём меньше таблиц с данными, чем в живой базе; том не найден; в снимке на MUSPELHEIM не все файлы; `restic check` не прошёл (иногда это брошенный лок убитого ручного запуска).

**Что сделать.** Брошенный лок: `sudo bash -c 'source /opt/vps-backup/lib.sh; restic unlock'`. Ручной запуск ночного бэкапа: `sudo systemctl start vps-backup.service` (после починки причины). Ручной restic запускать под `tmux`
или `systemd-run`, чтобы обрыв SSH его не убил. Восстановление — [`33-backup-restore.md`](33-backup-restore.md).

**Когда звать владельца.** Всегда при тревоге бэкапа, которая не ушла за сутки; при `restic check` с настоящей порчей; если не открывается пароль restic (его копия — у владельца, без неё бэкап не расшифровать).

## Потолок расхода модели у партнёра

Партнёр пишет, что «модель отключилась» и бот или обход просят выбирать пункты вручную, с текстом
«Месячный лимит расхода пространства исчерпан» (D759, #1670, `docs/27-web-administration.md`,
«Лимиты пространства партнёра»). Это не поломка: расход пространства за календарный месяц UTC достиг
потолка, ручной ввод работает.

**Где смотреть.** «Администрирование» → «Пространства» → карточка пространства → «Лимиты»: «N $ из M $ в
этом месяце». В базе:

```bash
echo "select * from space_limits" | sql                      # нет строки — умолчание: 5 проверок, 50 $
echo "select model, sum(input_tokens), sum(output_tokens), sum(audio_seconds) from model_usage where tenant_code = 'GE' and occurred_at >= date_trunc('month', now() at time zone 'UTC') group by model" | sql
docker logs --since 2h decimus-bot-1 2>&1 | grep "потолок расхода модели"   # так же decimus-walk-1, -web-1, -mcp-1
```

Строка журнала «потолок расхода модели достигнут» — вызов закрыт потолком; «не сверен (...)» — база не
ответила, вызов пошёл без проверки (потолок открыт, а не закрыт).

**Частые причины.** Реальный расход (≈1 $ на проверку; p90 1,38 $, максимум 3,25 $); в сумму не входят
модели без цены в `src/recognize/model_prices.json` — новую модель нужно завести с ценой, иначе потолок её не
видит; кэш потолка живёт 10 секунд — после правки лимита экран меняется сразу, живой бот подхватит за
секунды.

**Что сделать.** Поднять потолок в карточке пространства (главный админ или админ УК) либо пустое поле —
«без потолка»; 0 выключает модель. Писем и сообщений бота о потолке нет намеренно: предупреждение от 80 %
видно только на экране.

**Когда звать владельца.** Партнёр просит поднять потолок выше умолчания; расход пространства заметно выше
замера (возможна утечка запросов — смотреть «Расход модели», срез по людям).

## Когда звать владельца — общее правило

Звать, когда починка требует: нового значения ключа или пароля; решения про данные (удалить, восстановить, потерять); правки кода; действия на чужой стороне (поддержка Pointer, iSpring, Dodo IS); перезагрузки или настройки
домашнего сервера; выкатки прода (только по явному «да» и в окне). Не звать из-за одиночного жёлтого, который сам проходит в следующий час: выгрузки повторяются сами, а заход, пропущенный из-за замка, — норма.
