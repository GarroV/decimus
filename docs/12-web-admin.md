# Веб-админка управляющей компании

Третья поверхность продукта рядом с ботом и MCP. Документ описывает, что она
показывает сегодня, чего у неё нет и почему, и как её поднять.

Ведётся вручную. Инвентари ниже (разделы, переменные окружения) сверяются с
исходником — `src/web/sections.py` и `src/web/config.py`, — а не по памяти.

## Зачем она

Управляющая компания смотрит проведённые проверки: кто, где, когда, с какой
оценкой, что именно записано и по каким зонам разошлись потери. До неё это
было доступно только через бота (тому, кто проводил проверку) и через MCP
(агенту, по токену). Человеку с экраном — не было ничего.

## Что она умеет сегодня

| Действие | Где | Чем сделано |
|---|---|---|
| Увидеть реестр проведённых проверок сети | `/inspections` | `src/db/queries.py: list_inspections` |
| Сузить реестр по стране, городу, букве, виду; прийти в него кликом по городу с «Обзора» | `/inspections?country=GE&city=tbilisi&grade=D` | `src/web/app.py: registry`, география — `src/db/queries.py: unit_geography` |

| Отклонить проверку с обязательной причиной | там же, форма внизу карточки | `src/db/retract.py: retract_inspection` (D086, D089) |
| Открыть письмо партнёру по проверке, поправить текст, выгрузить файлом или положить в черновики своей почты | `/inspections/<id>/letter` | `src/report/letters.py: build` (T321), `src/web/letter_draft.py` (T352) |

| Опубликовать записанную версию отдельным шагом | кнопка на `/admin` | `publish_checklist_version` |
| Увидеть все чек-листы: код, названия, состояние, кто применён к проду | `/admin/checklists` | `src/web/methodology.py` → `src/mcp/checklists.py` (T347) |
| Завести чек-лист с нуля из бланка — он рождается черновиком | форма там же | `create` (T342, критерий приёмки D180) |

| Применить чек-лист к проду — после показа разницы | `/admin/checklists/<код>/apply` | `apply_to_production` (T343) |

**Оценка здесь не считается ни в каком виде.** Процент, буква, вычеты,
счётчики классов и разбивка по зонам приходят из базы такими, какими их положил
движок при завершении проверки. Это не обещание: контракт `engine-not-imported`
в `lint-imports` запрещает `src.web` импортировать движок, и нарушение роняет
прогон.

Своего SQL у админки нет — она ходит теми же дверями, что MCP. Схему данных
эта поверхность не меняет.

**Чек-лист в системе не один** (T341, D177). Перечень показывает все заведённые,
и по одному из них идут проверки — он помечен «в проде». Применение к проду
отдельного права не получает, и это решение, а не упущение: ролей в продукте нет
(D182), круг людей узкий, а от ошибки право не спасает — у ошибающегося оно как
раз есть. Вместо права три вещи: заслоны двери (пустой, снятый и не имеющий
опубликованного издания к проду не идут), след в журнале чек-листа с логином
вошедшего и **показ разницы** перед применением — сколько вопросов, какие зоны
с какими долями, по каким ставкам считается вычет. Третье и есть настоящая
защита, поэтому кнопка живёт на отдельной странице, а не в строке списка.

**Методику админка тоже не правит сама.** Состав чек-листа правится тем же
хранилищем версий, которым правит агент по MCP: снимок версии, правка копии,
сверка движком, новая версия, публикация отдельным шагом (D049, D050). Второй
копии этих правил в продукте нет — это единственный способ не разойтись с
дверью MCP молча. Подробности двери и её границ — `docs/10-checklist-configuration.md`.

проверок в объём не входят вовсе (D139) и показываются непостроенными
намеренно, а не временно.

## Вход: кто вообще видит эти страницы

**Без логина и пароля не открывается ничего** (T323, D155). Неопознанного
встречает форма входа — не 404, не пустая страница и не часть данных. Заслон
стоит одним `before_request` (`src/web/auth.py`), а не декоратором на каждом
маршруте: раздел, который появится завтра, закрыт с минуты появления. Открыты
ровно два endpoint'а, перечисленные в `auth.OPEN_ENDPOINTS`: сама форма входа
и статика дизайн-системы (без неё форма приезжала бы раздетой, а о данных
стенда эти файлы не рассказывают ничего).

**Учётки заводит команда проекта**, регистрации снаружи нет:

```bash
make web-user ARGS="add director --tenant demo"   # пароль спросят вводом без эха
make web-user ARGS="list --tenant demo"
make web-user ARGS="role director admin --tenant demo"   # первый админ стенда
make web-user ARGS="password director --tenant demo"   # сменить пароль (T340)
make web-user ARGS="email director director@dodobrands.io --tenant demo"   # почта для входа через Google
make web-user ARGS="email director --tenant demo"   # снять почту: вход через Google закрыт, пароль остался
make web-user ARGS="disable director --tenant demo"
```

**Смена пароля закрывает открытые сессии** этого человека, свою в том числе.
Иначе смена не выгоняет того, ради кого её делают: пароль меняют в ответ на
«его кто-то узнал», а вошедший по старому продолжал бы работать. Новый пароль
проверяется на длину так же, как при заведении — правило стоит в одном месте
(`_checked_password`), потому что действующее на одной двери из двух не
правило: завести с длинным и сменить на короткий было бы обходом в один шаг.

**Кто и что может делать с хешем пароля** (проверено запросом к
`information_schema.column_privileges`, а не по памяти): роль приложения
(`dodo_audit_app`) хеш ЧИТАЕТ — без этого не сверить пароль при входе, — но
записать не может; роль обслуживания (`dodo_audit_admin`) читает, вставляет
при заведении и обновляет при смене (`0022`). Поэтому получивший доступ к
продукту не заведёт себе вход и не подменит чужой пароль, хотя хеши видит.

**С экрана пароль пока не меняется** — задача #324.

### Вход через учётку Google (T332)

**Кнопка стоит РЯДОМ с паролем, а не вместо него.** У партнёра почта может
оказаться не гугловой, и отнимать у него единственную дверь ради стройности
схемы нельзя. Пароль остаётся запасным входом (D163).

**Кнопки нет вовсе, пока не заданы реквизиты** — `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` (у черновика письма свой адрес
возврата, `GOOGLE_MAIL_REDIRECT_URI`, — см. раздел о письме партнёру). Стенд без них работает паролем,
как работал; мёртвая кнопка читалась бы как поломка продукта. Значения лежат в
окружении площадки, в репозитории их нет: он публичный.

**Круг допущенных задаёт владелец, а не Google.** Google подтверждает ровно
одно — человек владеет этой почтой. Кого пускать, решает колонка `email` у
`web_users` (миграция `0021`): незнакомая почта получает отказ, а не заводит
учётку. Почта привязывается к УЖЕ заведённой учётке командой `email` (см. выше).
Снятие почты закрывает человеку вход через Google, не трогая пароль и саму
учётку — это и есть способ отозвать одну дверь из двух.

Тип приложения в Google — **Internal** (D168): входят только аккаунты
организации `dodopizza.com`. Партнёрам вход откроется после переключения на
External; переключение сохраняет Client ID, секрет и адрес возврата, то есть
код от этого не меняется.

Порядок шагов и то, чем каждый держится:

| шаг | что происходит | чем держится |
|---|---|---|
| `/login/google` | метка захода в подписанную куку, увод на согласие | метка своя на каждый заход и живёт 10 минут |
| возврат на `/auth/google/callback` | сверка метки ДО обращения к Google | иначе чужая страница откроет сессию в браузере человека |
| обмен кода | POST на token endpoint с секретом | канал TLS и наш `client_secret` |
| проверка `id_token` | `aud`, `iss`, срок, `email_verified` | без них годится токен чужого приложения |
| опознание | `find_by_email` — живая учётка своего арендатора | отключённый не войдёт и через Google |

**Подпись `id_token` не проверяется намеренно.** Токен приходит не от браузера,
а прямым ответом token endpoint по TLS с нашим секретом в запросе — Google в
этом случае проверку подписи разрешает пропустить. Всё остальное из таблицы
проверяется обязательно.

**Отказ один на все осечки возврата** — не та метка, не тот код, почты нет в
списке. Разные ответы рассказали бы подбирающему, на каком шаге он
остановился, и заодно кто здесь заведён. Там же решается, кому
отдать право писать хеш: сегодня оно есть только у роли обслуживания, и
пробитое приложение сменить пароль никому не может.

**С T338 то же делается с экрана** — раздел «Люди» (`/users`), но открыт он
только учётке с ролью `admin`. Накат `0020` роли не раздаёт НИКОМУ: кто
заведён на стенде, миграция не знает, а раздача «всем» или «по имени» выдала
бы права людям, на которых никто не смотрел. Поэтому первый администратор
назначается командой `role` выше — до неё раздел не откроется никому.

Заведение и отключение идут под ролью повышенных полномочий, и это не
удобство, а заслон: роль приложения на `web_users` имеет только `select`
(миграция `0014`). Завести учётку, подменить чужой пароль или отключить её
продукт не может физически — получивший базу продукта не заведёт себе вход.
Экран ходит под ролью администратора истории (`DATABASE_RETRACTION_URL`,
права выданы `0020` и `0022` поколоночно), командная строка — под
владельцем схемы. Пароль не меняет ни та, ни другая: смена чужого пароля это
вход под чужим именем. Забыл пароль — учётка отключается и заводится заново.

Пароль заведённого с экрана придумывает система и показывает ОДИН раз, на
странице ответа: в адрес он не попадает намеренно — адреса остаются в истории
браузера и в журнале обратного прокси.

**Что лежит в базе.** От пароля — scrypt с солью (`scrypt$n$r$p$соль$хеш`), от
сессионного токена — отпечаток SHA-256. Обе формы держит ограничение схемы, а
не договорённость в коде: записать значение вместо свёртки — отказ записи.

**Сессия живёт в базе, а не только в куке.** Кука подписана (`WEB_SECRET_KEY`;
не задан — ключ делается на запуск, и админка говорит об этом строкой на
старте), `HttpOnly`, `SameSite=Lax`, `Secure` — когда соединение HTTPS. Выход
помечает сессию закрытой, поэтому перестаёт работать любая копия куки, а не
только та вкладка, где нажали кнопку; снять пометку не может никто — сужающая
политика пропускает ровно переход «живая → закрытая». Срок сессии — 12 часов.
Отключение учётки действует немедленно: кто вошёл, сверяется на каждом запросе.

**Границы арендатора вход не ослабляет.** Учётка принадлежит арендатору, и
опознание ищет её по паре «арендатор + логин»; арендатор стенда по-прежнему
приходит из `WEB_TENANT`, а не из адреса и не из формы.

**Перебор пароля упирается в счётчик** (T325). Неудачные попытки считаются по
двум ключам сразу: по адресу, с которого пришли, и по логину, в который целятся.
Пять неудач подряд на логин (двадцать с одного адреса) — и форма перестаёт
принимать пароли: отвечает 429 и называет срок. Срок растёт с каждой следующей
неудачей — 1, 5, 15, 60 минут, — поэтому опечатка стоит минуту, а упорство час;
после часа тишины счётчик забывается сам, удачный вход обнуляет его сразу.

Важное свойство, которое и делает это ограничителем: **запертому не помогает
верный пароль**. Запертая попытка не доходит до сверки вовсе — не платится ни
обращение к учёткам, ни scrypt (16 МиБ и десятки миллисекунд на попытку, сам по
себе годный рычаг перегрузки). По той же причине выбран запрет, а не растущая
задержка перед ответом: waitress держит ограниченный пул потоков, и полсотни
спящих запросов заняли бы его для всех, включая тех, кто знает пароль.

Счётчик живёт **в базе** (`web_login_attempts`, миграция `0015`), а не в памяти
процесса: перезапуск здесь случается сам — выкладка, перезагрузка сервера, —
и ограничитель, которого нет ровно в эти минуты, выглядит работающим всё
остальное время. Хранятся только отпечатки ключей: в поле «логин» вводят, среди
прочего, пароль от соседней системы, и дословно он в базу не попадает. Срок
запрета не хранится, а считается по числу неудач и времени последней
(`src/db/web_throttle.py`) — второй записи того же факта в схеме нет.

**За туннелем обязательно задать `WEB_TRUSTED_PROXIES`** — сколько СВОИХ звеньев
стоит перед сервером (туннель — одно). Без неё заголовок `X-Forwarded-For` не
слушают вовсе, и это умолчание выбрано сознательно: поверить ему без своего
звена впереди — значит раздать перебирающему бесконечный запас «адресов» одной
строкой в запросе. Цена умолчания за туннелем обратная: все приходят с одного
адреса, счётчик по адресу становится общим на всех, и упереться в него может
тот, кто ни при чём. Счётчик по логину при этом работает как обычно.

Настройка называет звено **и серверу тоже**, а не только счётчику (#306).
`waitress` без объявленного доверенного звена вырезает все `X-Forwarded-*` на
входе, и до приложения они не доезжают вовсе. Пока этого не было сделано,
настройка выглядела работающей — читалась, проверялась на границы, печаталась в
отказах, — а за туннелем ломалось сразу два места. Заслон происхождения считал
запрос пришедшим по HTTP, сравнивал со схемой `https` в `Origin` и отвечал 403
на КАЖДУЮ отправку формы: войти, выйти и снять проверку было нельзя. Счётчик
неудач видел один адрес на всех пришедших снаружи. Оба следствия молчаливые:
стенд здоров, набор зелёный, а снаружи 403. Сторожит это
`tests/test_web_proxy_headers.py` — единственный набор, который поднимает
настоящий сервер и ходит к нему по сети: тестовый клиент Flask передаёт
заголовки сам и такую поломку не воспроизводит.

**Порог держит и при одновременных попытках** (T328). Решение «пускать ли» и
запись попытки идут одной транзакцией под замком на ключ, а сверка пароля
остаётся снаружи замка. Раньше это были два похода в базу по разные стороны от
сверки, и попытки, пришедшие до записи первой неудачи, читали одно и то же
число: замером порчей мимо порога проходило пятнадцать одновременных попыток
вместо пяти. Циклом такое не ловится — в нём попытки идут подряд, — поэтому
сторожит его проверка настоящими потоками.

**Адрес приводится к канону до отпечатка** (T328): `2001:db8::1` и
`2001:db8:0:0:0:0:0:1`, `::ffff:203.0.113.7` и `203.0.113.7` — один и тот же
отправитель, и счётчик у него один. Иначе порог по адресу обходился бы записью
того же адреса в другом виде.

### Запертого выпускает команда (T328, решение D158)

Раньше запрет проходил только по времени, и команды снятия не было намеренно —
это СНЯТО решением D158. Причина: логины здесь короткие и предсказуемые, круг
узкий, и посторонний, знающий логин администратора, держал его запертым сколь
угодно долго — по одной неудачной попытке раз в час, чтобы счётчик не успевал
забыться. **Пароль для этого не нужен вовсе.** Пока админка на петле, это
внутреннее дело; после публикации наружу цена такой атаки — «знать логин».

```bash
make web-unlock ARGS="list --tenant demo"                      # кто заперт и насколько
make web-unlock ARGS="unlock director --tenant demo"           # снять запрет с логина
make web-unlock ARGS="unlock-address 203.0.113.7 --tenant demo" # снять запрет с адреса
```

Команда работает **под ролью администратора истории** (`DATABASE_RETRACTION_URL`)
— той же, что снимает проверку: снятие запрета — действие человека из команды, а
не шаг продуктового сценария. Права выданы миграцией `0016`: читать счётчик и
удалять строки, ничего больше. Добавлять неудачи роль не может — иначе она умела
бы запирать вход человеку, то есть делать ровно ту беду, от которой команда и
заведена.

Что нужно знать, читая вывод:

- **Снять запрет = забыть неудачи.** Срок в базе не хранится, он считается по
  числу неудач и времени последней, поэтому отдельной пометки «разрешено» нет.
- **Адрес и логин запираются раздельно** — и снимаются раздельно: человек за
  запертым адресом не войдёт и с открытым логином.
- **Логины в списке узнаются, а не расшифровываются.** В счётчике лежат
  отпечатки; команда считает отпечаток каждой заведённой учётки и сопоставляет.
  Неузнанный ключ печатается началом отпечатка — это либо адрес, либо логин,
  которого у нас нет (перебирают и несуществующие).
- **«Снимать было нечего» — это код возврата 1**, а не успех: иначе человек,
  ошибшийся арендатором или логином, уходит ждать неснятого запрета.

Честная оговорка: «роль приложения запреты не снимает» — это утверждение о коде
(в админке нет такого пути), а не запрет базы. У роли приложения `delete` на
счётчике есть и нужен ей самой — обнулять счётчик при удачном входе и
выбрасывать старые строки. Заслон базы здесь другой: переставить накопленные
неудачи с чужого ключа на свой не может ни одна роль.

### Когда общий вход площадки занят соседом (`WEB_URL_PREFIX`)

Своего имени у админки может не быть: на общей площадке корень публичного

собирает с ним все ссылки страницы. Без него страница по своему пути

продукт, который там стоит.

же): разные `SCRIPT_NAME` при одном намерении разошлись бы молча. Пусто —
админка живёт под своим именем целиком, и это умолчание.

Сторожит `tests/test_web_proxy_headers.py`: префикс исполняет `waitress`, и
«настройка прочитана» ничего не говорит о том, доехала ли она до приложения —

порта (D100): площадка общая, и опубликованный порт отдал бы соседям по машине
ещё и форму входа для перебора. Сама публикация — отдельная задача.

## Письмо партнёру: заготовку пересобирают, отправленное хранят

Экран `/inspections/<id>/letter` показывает письмо, которое уедет партнёру по
этой проверке. Отправки из системы нет и не заводится (Q010): письмо уходит из
почты руками. Но **то, что ушло, хранится** — таблица `partner_letters`
(`0019`, T333, D035): без неё на вопрос «что именно мы отправили партнёру»
ответить нечем, а партнёр считает отправленное фактом и прав.

Поэтому на экране две разные вещи. **Заготовка** собирается заново — движком,
по методике той версии, которой помечена проверка, и только после того, как
посчитанное движком сошлось с записанным в базе. **Зафиксированное письмо** не
пересобирается ничем: показывается как записано, иначе ответ на «что мы
отправили» менялся бы от дня, когда его спросили.

Собирает его `src/report/letters.py` — тот же код, которым письмо по той же
проверке отдаёт инструмент модели. Своей сборки у админки нет ни строки: два
экземпляра одного правила разошлись бы молча, а увидел бы это партнёр.

### В черновики своей почты (T352, D174, D176, D185)

Кнопка «В черновики Google» кладёт письмо в ящик **того, кто вошёл**, откуда
человек отправляет его сам. Отправки из системы по-прежнему нет — черновик её
не заводит, а убирает лишний шаг с копированием текста.

Порядок на этой кнопке неочевиден и важен:

1. Письмо **фиксируется** — ровно тот текст, что человек видел (D171). Уход за
   согласием уводит со страницы, и правка из поля иначе умерла бы вместе с ней.
   Поэтому письмо остаётся сохранённым даже при отказе в окне Google.
2. Google спрашивает право `gmail.compose` — **отдельно от входа и только в
   первый раз**. На входе этот скоуп показывал бы экран доступа к почте
   каждому, кто открывает админку, включая тех, кто писем не пишет.
3. Черновик собирается из **зафиксированного** письма, а не из заготовки:
   заготовка пересобирается и к моменту возврата дала бы другой текст.

**Токен доступа к почте не сохраняется нигде** — ни в базе, ни в куке. Он живёт
внутри одного возврата: `refresh_token` не запрашивается вовсе, потому что
долговременный ключ к чужой почте нужен только фоновой отправке, которой нет.

Тема черновика собирается из шапки проверки («Проверка пиццерии · Белград ·
2026-09-12»), адресат — контакт партнёра из той же шапки; пустой контакт не
даёт заголовка `To` вовсе, иначе черновик был бы неотправляемым. Кнопки нет,
пока не задан `GOOGLE_MAIL_REDIRECT_URI` (см. `.env.example`) — адрес возврата
у почты свой, `https://<площадка>/audit/auth/google/mail`, и в консоли Google он
добавляется вторым в тот же список того же клиента `decimus-web`.

**«Собралось» и «можно отправлять» — разные ответы, и второй сказан вслух.**
Письмо бывает связным, подписанным и с верной оценкой, а отправлять его нельзя:

| Чего не хватает | Чем это опасно на вид |
|---|---|
| полей шапки (аудитор, город, партнёр, контакт) | движок подписывает прочерком — видно сразу |
| ответа аудитора про срок плана действий | срок **подставляется расчётом** и от настоящего ничем не отличается: партнёр получит не ту дату, что у него на руках |
| формулировок на языке письма | они печатаются на языке речи аудитора — письмо связное и наполовину на чужом языке |
| формулировок вообще | движок называет пункт пунктом; строка выглядит как соседние |

Перечень приезжает от сборщика кодами, а словами их называет интерфейс
(`src/web/view.py`, `letter_caveats`) — на языке того, кто смотрит. Код, для
которого подписи ещё нет, показывается сам: пропасть он не имеет права, каждый
из них — причина, по которой отправлять нельзя.

**Язык письма — третий язык продукта и выбирается отдельно.** По умолчанию
это язык отчёта проверки: партнёру пишут на его языке, а не на языке того,
кто открыл админку. Переключатель собран из языков МЕТОДИКИ
(`domain.models.TEXT_LANGS`), а не из языков интерфейса — свой список
предложил бы язык, которого в методике нет. Формулировки находок не
переводятся ни на каком языке письма: это слова аудитора.

**Правка сохраняется — кнопкой, а не уходом со страницы.** Поле с текстом
(`letter.edit.label`) показывает зафиксированное письмо, если оно есть, и
заготовку движка, если нет; ссылка «Вернуть заготовку» показывает свежую
сборку, ничего не записывая. Действий два, и у каждого своя кнопка:
«Сохранить изменения» пишет строку в `partner_letters` (кто и когда — видно на
экране), «Выгрузить файлом» отдаёт правленое простым текстом вложением
(`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`), дальше
человек прикладывает его к письму в почте. Зафиксированное письмо заморожено:
передумал — фиксируется новое, и обе записи видно.

**Куда это едет дальше (D169).** Выгрузка файлом снимается — копирование из
поля решает ту же задачу без файла; вместо неё у письма появляется простое
форматирование (жирный, курсив, зачёркнутый, гиперссылка) и кнопка «В черновики
Google». Письмо при этом остаётся несохранённым, пока человек сам не нажал
сохранение или отправку в черновики (D171): автосохранения заготовки нет,
иначе в истории лежало бы то, чего партнёру не отправляли.

Контейнеру админки для этого нужны методика и полка снимков изданий:
`AUDIT_DATA_DIR` → `/app/data:ro` и том `state` → `/app/state:ro`
(`docker-compose.yml`, сервис `web`). Без них экран письма честно скажет, что
собрать его не из чего.

## Чего у админки нет

- **Разбора «кто и откуда долбился» нет:** счётчик попыток отвечает на вопрос
  «пускать ли дальше», а не «кто это был». В нём лежат отпечатки, а не адреса, и
  строки стираются через час после последней неудачи.
- **Разбора «кто снял запрет» нет:** команда снятия удаляет строку счётчика и
  следа о себе не оставляет. Круг тех, у кого есть подключение администратора
  истории, узкий и заводится руками.
- **Ролей у учёток нет:** все вошедшие равны и видят одно и то же — включая
  снятие проверки и правку методики. Круг узкий и заводится руками, поэтому
  система прав здесь не появляется заодно с первой таблицей. Право MCP на
  методику (`MCP_CHECKLIST_TENANTS`) к экрану не применяется: оно про токены
  агента, а не про людей за экраном.
- **Зоны и их доли с экрана не правятся** — только читаются: доли задаются
  набором сразу, потому что обязаны сойтись к 100%, и эта правка осталась у
  двери MCP.
- **Отказ движка приходит на экран на языке движка**, а не на языке
  интерфейса: язык интерфейса — параметр, но текст отказа приезжает из
  подпроцесса как есть.
- **Смены пароля самим человеком нет:** команда умеет завести и отключить.
- **Снятия с чужой страницы нет:** `POST` с посторонним `Origin` отклоняется
  (`src/web/origin.py`, общий заслон для снятия, входа и выхода). Сессионную
  куку браузер приложил бы к запросу с чужой страницы сам, а снятие необратимо
  убирает кадры из хранилища.
- **Отправки письма из системы нет** и хранения писем тоже: письмо
  пересобирается по проверке, правится на экране и выгружается файлом, а
  отправляет его человек из почты (Q010, D035).
- **Разреза по процессам (D137) в этой волне нет** — он строится отдельно.
- **Кнопки «подтвердить все» и плашки «потенциально ещё N %» не будет**
  (D145): правило «модель предлагает, фиксирует человек» остаётся без
  исключений.

## Исправление даты и пиццерии (D195)

Администратор может исправить у сданной проверки дату и пиццерию, если при
заведении ошиблись, — блок «Исправить дату или пиццерию» в карточке. В коде и
базе это «перенос» (`move`, `inspection_moves`); на экране — «исправление». Записи, оценка, буква и разбивка при этом не
меняются: перенос правит «когда и где», а не документ. Каждый перенос остаётся
в истории — кто, когда, что было, что стало, причина, — и история видна на
карточке всем, кто её открывает.

История пишется **базой**, а не кодом: триггер `inspections_move_logged`
(миграция `0025`) на `update` даты или пиццерии сданной проверки пишет строку в
`inspection_moves` в той же транзакции и отказывает, если причина и автор не
переданы (`set local decimus.move_reason` / `decimus.move_actor`). Прямой записи
в историю нет ни у одной роли; переносит роль администратора истории, у которой
на шапку выданы ровно две колонки. Отклонённую проверку не переносят. Дверь —
`src/db/move.py`. Нет истории (схема без `0025`) — формы нет, администратор
видит пометку.

Отклонять и переносить может только учётка с ролью администратора: заслон
стоит на маршруте (`_admin_only`), а не только в разметке.

## Отклонённые проверки: «их нет» и «вам их не видно» — разные ответы

На экране и в ответах MCP это **отклонение** проверки (D194); в коде, базе и
именах инструментов — прежнее `retract` / `retracted_at`. Ниже «снятая» и
«отклонённая» — одно и то же.

Снятые проверки видит только администратор истории (роль `dodo_audit_admin`,
миграция `0010`), и приходит он отдельным подключением
`DATABASE_RETRACTION_URL`. Когда переменная не задана:

- реестр показывает список без снятых и плашкой об этом не говорит (D193):
  без этой роли снять проверку не может никто, значит снятых и нет;
- снятая проверка по прямому адресу отвечает «не найдена» — тем же ответом, что
  несуществующая;
- форма снятия не предлагается вовсе.

Молчаливо укороченный список выглядел бы полным, поэтому его здесь не бывает.

Подключение задано, но не работает (неверный адрес, пароль роли не
поставлен) — экран не падает: реестр и карточка читаются обычной ролью, без
снятых, а причина уходит в лог контейнера строкой «чтение под администратором
истории не удалось» (#307). Лежит сама база — обычное чтение падает следом, и
человек видит честное «База недоступна».

## Отбор: страна → город, код в адресе, слово на экране

Чипы отбора на «Обзоре» и в «Проверках» — одни и те же (`_pick.html`) и
ведут себя одинаково:

- **города зависят от страны.** Выбрана страна — в списке только её города;
  смена страны сбрасывает город. Иначе рядом с Анталией стоял Тбилиси и
  предлагал заведомо пустую выборку (24.09.2026);
- **список закрывается сам** — по клику вне него, по выбору и по Escape
  (`static/pick.js`; все списки — одна группа `<details name="pick">`, открытие
  одного закрывает другой);
- **в адресе код, на экране слово.** Справочник сети хранит город кодом
  источника (`tbilisi`, `novisad`), страну — ISO-кодом (`GE`). Слово на RU/EN
  берётся из `src/web/geo_names.py`; незнакомый код показывается как есть, с
  заглавной, и экран не падает. Новая страна или город сети — строка туда же.

Строка «Разбивки по городам» на «Обзоре» ведёт в «Проверки» с тем же срезом:
`country`, `city` и буква переезжают в адрес реестра, период — нет (у реестра
отбора по периоду нет). Географию реестр берёт у ТОЧКИ справочника, а не у
проверки; справочник недоступен — отбор по месту пуст, реестр работает, причина
в логе (`inspections.load_geography`).

## Статика: отпечаток в адресе и долгий кеш

`url_for('static', …)` дописывает к адресу `?v=<отпечаток содержимого>`
(`src/web/assets.py`), и такой адрес кешируется на год: поменялся файл —
поменялся адрес. Шрифты идут без отпечатка (CSS зовёт их голым путём) и
кешируются на неделю. Переход между разделами сглаживает `@view-transition`:
шапка и столбец навигации стоят на месте, меняется только содержимое. До этого
(замер 24.09.2026) каждый клик переспрашивал стили и шрифты по 0,3 с на запрос
через Funnel, и экран моргал белым.

## Стек и почему такой

Рамка задана решением D148: Python, тот же образ и `docker-compose.yml`, что у
бота и MCP, серверный рендеринг, синхронный код, без Node и сборщика. Внутри
рамки блок выбрал:

| Слой | Выбор | Почему |
|---|---|---|
| Приложение | Flask 3.1.3 | WSGI и синхронные обработчики зовут `src/db` напрямую, как весь остальной продукт. Асинхронные Starlette / FastAPI / Litestar увели бы синхронный вызов в пул потоков, то есть заплатили бы за то, чего блок не просил |
| Шаблоны | Jinja (в комплекте Flask) | Отдельной зависимости не нужно |
| Сервер | waitress 3.0.2 | Чистый Python, без компиляции и без второго процесса-менеджера. Встроенный сервер Flask сам пишет, что не для работы, и держит один запрос за раз |

**Отброшено:** Django — принёс бы собственный ORM и миграции поверх тех же
таблиц, то есть второго владельца правды, что контракт блока прямо запрещает.
Готовые админки (`flask-admin` и подобные) — по той же причине: они строятся из
моделей SQLAlchemy, а это описание схемы во второй раз.

## Стиль

Дизайн-система линейки `GarroV/forma`, коммит `a957dd2`, копией в
`src/web/static/` с отпечатками в `src/web/static/SOURCE.md`. Раскладка — из
прототипа владельца, стиль — из `forma` (D136); палитра `#5B57F2` и пара Space
Grotesk / Manrope из прототипа в продукт не переносятся. Третий файл,
`decimus-web.css`, — тонкий слой продукта: он только связывает токены ядра с
разметкой этих экранов и своих цветов не заводит.

Шрифты по сети не подгружаются: ядро объявляет их с системными запасными
вариантами, стенд закрытый.

## Как поднять

Одной командой — стенд целиком: база, схема, демо-история и сама админка,
адрес печатается на старте (#291).

```bash
make web-up                        # демо-стенд: открывать сразу
WEB_TENANT=<код тенанта> make web-up   # своя история вместо демонстрационной
```

Учётку стенда команда заводит сама, если её ещё нет, и печатает логин с
паролем на экран ОДИН раз — в базе пароля нет, только необратимая свёртка.
Постоянного пароля стенда в репозитории нет намеренно: он был бы известен
каждому, кто видел исходники. Потеряли — заводится новая:
`make web-user ARGS="add <логин> --tenant <код>"`.

Устроено это по образцу `npm run up` в meridius: в контейнере живёт только
база, а продукт запускается на хосте. Причина не стилистическая — строка
подключения из файла окружения указывает на порт **хоста**, и внутри
контейнера по ней базы нет.

Что делает команда по шагам: `make db-up` (поднимает Postgres профиля `db` и
ждёт готовности по пробе здоровья) → `make migrate` (схема) → `make web-demo`
(демо-история) → `python -m src.web`. Каждый шаг вызывается отдельной целью и
работает сам по себе.

**Демо-история — в базе, а не в состоянии бота.** `make demo` собирает
проверку для показа в телеграме, и веб её не видит вовсе: он читает базу
завершённых проверок. Поэтому у веба свой сид — `make web-demo`
(`tools/seed_web_demo.py`): три английские проверки вымышленной сети под
тенантом **`demo`**, собранные тем же кодом, что и бот, и слитые той же
дверью `src/db/push.py`. Повторный запуск возвращает демо к чистому виду:
прежние строки сносятся и собираются заново, поэтому идентификаторы проверок
после пересборки другие. В неместную базу сид писать отказывается —
`DATABASE_URL` не на петлю останавливает его с объяснением, снимается
`SEED_WEB_DEMO_FORCE=1`.

Дальше — руками, когда нужен не весь стенд:

```bash
WEB_TENANT=<код тенанта> make web     # только сервер, база уже поднята
```

Раздел «Методика» требует ещё двух переменных — `MCP_CHECKLIST_STORE` (каталог
хранилища версий) и `AUDIT_DATA_DIR` (каталог методики, из которого читает
движок). Это ТЕ ЖЕ переменные, что у сервера MCP: хранилище одно на продукт, и
своей переменной у веба нет намеренно — второй путь к одной методике разошёлся
бы с первым. Не заданы — раздел открывается и честно называет, чего не хватает,
вместо пустой таблицы. Чтобы публикация работала, `AUDIT_DATA_DIR` обязан
указывать на указатель `current` внутри хранилища; порядок настройки — в
образце окружения.

Переменные окружения — `WEB_TENANT` (обязательна), `WEB_HOST`, `WEB_PORT`,
`WEB_UI_LANG`, `WEB_SECRET_KEY`, `WEB_TRUSTED_PROXIES`, `WEB_URL_PREFIX`;
назначение каждой — в образце окружения. Читаются они из файла
окружения самой точкой входа (`load_dotenv`, как у бота и MCP): до issue #290
этого не было, и `make web` поднимался без `DATABASE_URL` — сервер отвечал
«База недоступна» при живой базе. К базе админка ходит по `DATABASE_URL`,
снятые проверки и снятие — по `DATABASE_RETRACTION_URL`.

У `make web-up` тенант по умолчанию — `demo`, и он выставляется целью, а не
берётся из файла окружения: переменная, выставленная make, сильнее
`load_dotenv` (тот не перетирает уже стоящее). Для своей истории тенант
передаётся в командной строке, как в примере выше; `make web` по-прежнему
требует его явно и ничего не додумывает.

В `docker-compose.yml` есть сервис `web` — тот же образ, другая точка входа. Он
живёт в **своём профиле** и вместе со стендом не поднимается:

```bash
docker compose --profile web up -d web
```

Профиль, а не сервис по умолчанию: боевой стенд не должен поднимать админку
просто потому, что поднимают бота. Обычный `up -d` даёт `bot` и `mcp`, и это
держится проверкой (`tests/test_db_stand.py`). Сервис проверяется пробой
здоровья (проба стучится в реестр, то есть меряет весь путь до базы) и порт
наружу не публикует: наружу выходят туннелем, см. «Вход» выше.
