## 8.2. Хранилище кадров на VPS и образ MinIO (D635, #396)

Службы `storage-live` (MinIO) и `storage-init` (заведение корзины и пользователя)
описаны в `docker-compose.prod.yml`. `scripts/prod-update.sh` перед подъёмом
приложений поднимает `storage-live` и запускает `storage-init`; тот идемпотентен:
`mc mb --ignore-existing`, политика `decimus-frames-rw` (чтение, запись и удаление
только в корзине `${S3_BUCKET}`), пользователь `decimus-app` с ключами
`S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` из `.env`.

Переменные `.env` на сервере (значения никуда не печатать):

| Переменная | Что это |
|---|---|
| `FRAMES_ROOT_USER`, `FRAMES_ROOT_PASSWORD` | root MinIO; пароль от 16 знаков, без них `storage-live` не стартует (F-014). Читает только compose |
| `S3_ENDPOINT_URL` | `http://storage-live:9000` |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | ключи приложения (`decimus-app`) |
| `S3_BUCKET`, `S3_REGION` | `inspection-frames`, `us-east-1` |

Закреплённые образы `quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z` и
`quay.io/minio/mc:RELEASE.2025-08-13T08-35-41Z` реестры больше не отдают (401 /
denied, проверено 26.09.2026). На VPS они уже загружены; на новом сервере их
переносят тем же тегом с машины, где они в кэше (на 23.10.2026 это MUSPELHEIM),
compose менять не нужно. **`docker image prune -a` на VPS их удалил бы** — чистка
кэша сборок (`vps-infra`, `builder prune`) образов не трогает.

```bash
ssh muspelheim docker save quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z quay.io/minio/mc:RELEASE.2025-08-13T08-35-41Z | ssh <vps> docker load
```

**Переезд 23.10.2026 (D635), для повторения:** `storage-live` и `storage-init`
подняты вручную до раскатки; все объекты залиты `mc mirror --preserve` со старого
MinIO (по ключам приложения) в новый; сверены множество ключей, размеры и etag
1:1 и ссылки базы (`photos.storage_path`, `photos.preview_path`,
`reports.storage_path`) против объектов нового хранилища; затем `S3_ENDPOINT_URL`
переключён и раскатка, и ещё один `mc mirror` для кадров, пришедших между
переливом и переключением. Откат: вернуть прежний `S3_ENDPOINT_URL` и раскатить.

## 4.9. Хранилище файлов проверок (D166, #318)

Кадры проверки уезжают в S3-совместимое хранилище при её завершении, потому
что `telegram_file_id` живёт ровно столько, сколько живёт бот с этим токеном:
в базе он становится мёртвой ссылкой на доказательство, ради которого проверка
и делалась.

Хранилище **своё, на площадке** и **временное по решению, а не по устройству**:
продукт говорит с ним S3-совместимым языком (`src/db/storage.py`), поэтому
переезд на внешнее стоит правки `S3_*` в окружении и ничего больше (D054,
D061).

> **История.** С 30.09.2026 по 23.10.2026 кадры жили в MinIO на MUSPELHEIM
> (D257, D259, D293); с 23.10.2026 они снова на VPS (D635, подробно — §8.2
> и [§8.5](33-backup-restore.md)): служба `storage-live` лежит в `docker-compose.prod.yml`, а не в
> общей сборке, `tools/storage_env.*` удалены (#396) и не возвращаются — корзину
> и пользователя заводит `storage-init`, ключи лежат в `.env` (§8.2). Порядок ниже — как было
> на MUSPELHEIM до D293, для чтения старых журналов.

**Не путать с соседней службой `storage`:** та мок, держит объекты в памяти и
умирает вместе с контейнером. Она для прогонов и смоука, и боевым хранилищем
быть не может.

Порядок:

```powershell
powershell -ExecutionPolicy Bypass -File tools\storage_env.ps1   # ключи, если их ещё нет
docker compose --profile storage-live up -d storage-live
docker compose --profile storage-live run --rm storage-init      # корзина
```

Секрет родится на самой машине и наружу не печатается; повторный запуск
процедуры существующий ключ не трогает. Корзину заводит стенд, а не продукт —
у кода нет и не должно быть прав создавать корзины.

**Бот подхватывает настройки только при перезапуске.** Пока он не перезапущен,
завершённые проверки продолжают складывать кадры мимо хранилища — и молчат об
этом ровно так же, как молчали до его появления.

**Том в бэкап площадки НЕ входит:** выгрузка умеет только дампы Postgres
([§4.8](33-backup-restore.md)), а файлы лежат отдельно. Это принятая цена отсрочки (D166), а не
недосмотр — при переезде на внешнее хранилище она отпадает.

### 4.9.1. Сжатые копии для кадров, выгруженных до D219 (#422)

Карточка проверки показывает кадр записи только по сжатой копии
(`photos.preview_path`). Выгрузка делает копию сама; кадры, выгруженные до
появления копий, её не имеют. Досоздаёт их `tools/backfill_previews.py` из
оригинала в хранилище.

Строка выгруженного кадра заморожена политикой `photos_uploaded_only_once`, и
миграции-исключения к ней нет и не будет: исключение осталось бы навсегда
ради разовой доливки. Поэтому доливщик идёт под учёткой наката схемы
(`DATABASE_ADMIN_URL`) и пишет только пустой `preview_path`
(`... where id = %s and preview_path is null`).

```bash
# внутри образа: tools/ в нём есть
python tools/backfill_previews.py            # сухой прогон: «кадров без копии: N»
python tools/backfill_previews.py --apply    # «сделано копий: X, не вышло: Y»
```

Повторяемо: второй прогон берёт только кадры без копии. Убранные кадры
(`purged_at`) и невыгруженные (`storage_path` пуст) не трогает: копию делать
не из чего. Нечитаемый кадр называется в выводе, остальные идут дальше, а код
возврата 1 говорит, что был хотя бы один отказ.

### 4.9.1.1. Разбивка по процессам для проверок до миграции 0073 (D507)

Карточка «Где сеть теряет проценты» на «Главной» читает `inspections.by_process`,
которую слив пишет с миграции `0073`. Проверки, принятые раньше, её не имеют и в
карточку не входят, пока их не долить: `tools/backfill_by_process.py` прогоняет
движок по записанной проверке её же методикой (`rescore`) и пишет только эту
колонку. Идёт под администратором истории (`DATABASE_RETRACTION_URL`); сторож
`inspections_by_process_guarded` пускает запись только из NULL. Процент и букву
доливщик не переписывает: расхождение с движком (или вклады процессов не
сходятся с вычетом) — проверка пропускается с сообщением, код возврата 1.
Историческим (`origin = 'legacy'`, D332) разбивка не кладётся.

```bash
# внутри образа: tools/ и методика в нём есть
python tools/backfill_by_process.py            # сухой прогон: «проверок без разбивки: N»
python tools/backfill_by_process.py --apply    # «записано: X, пропущено: Y»
```

Повторяемо: второй прогон берёт только проверки без разбивки.

На проде прогнан 28.09.2026: 88 из 88, 0 отказов (`progress.md`). Кадры,
которым копию сделать не из чего, карточка показывает пометкой «Фото
недоступно: N», а не выдаёт запись за запись без фото. Новый прогон нужен
только при подъёме из старого дампа или если в хранилище появятся кадры без
копии. Запуск на проде, как любой шаг на нём, делается по «да» владельца.

### 4.9.2. Хранилище лежит на сдаче — дозагрузка кадров (#459)

Хранилище кадров прода — MinIO рядом с ботом на VPS (D635; до 23.10.2026 — на
MUSPELHEIM, а тот засыпал, D259). Если оно всё же лежит (перезапуск, сбой тома),
происходит вот что со сдачей:

| Шаг | Что происходит |
|---|---|
| Отчёт (PDF) и письмо | доходят: собираются из кадров телеграма, хранилище не нужно |
| Проверка в истории | ложится: база на VPS, хранилище не нужно |
| Кадры | не ложатся; строки кадров остаются в базе с пустым `storage_path` |
| Что видит аудитор | «Проверка в историю записана. Хранилище фото сейчас недоступно… Бот догрузит фото сам, когда хранилище вернётся: делать ничего не нужно» (`finish.photos_deferred`, RU и EN) |
| Отчёт в хранилище | не выгружается (второй раз в лежащее хранилище не ходим); в админке у этой проверки документа нет — вопрос вынесен владельцу (PR по #459) |
| Сколько ждёт бот | одна попытка с коротким сроком соединения (`src/db/storage.py`: 5 с соединение, 30 с ответ, `total_max_attempts=1`). Так собирается клиент только на пути сдачи и дозагрузки (`fail_fast=True`: `upload_photos`, `upload_report`); админка, снятие, предписания, экшн-планы, MCP, доливщик копий и сверка (§4.9.3) остались с умолчаниями botocore и их повторами. Замер на стенде 05.10.2026: адрес не отвечает — отказ через 5,1 с, контейнер хранилища остановлен — 2,2 с. Раньше — умолчания botocore: тот же замер дал 309 с на один отказ, а их на сдаче два (кадры и отчёт) — около 10 минут, и бот обрабатывает сообщения по одному — стояли бы все аудиторы |

**Дозагрузка — внутри бота, без cron и без отдельного запуска.** Фоновая задача
(`src/bot/photo_backfill.py`) раз в 30 минут берёт кадры с пустым
`storage_path` старше 10 минут (`db.pending_photo_uploads`), качает их у
телеграма по `telegram_file_id` и зовёт ту же `upload_photos`. Внутри бота —
потому что байты после сдачи есть только у телеграма, а токен только у бота.
Свежие кадры не трогаются: их в эту минуту выгружает сама сдача.

- **Повторяемо.** Берутся только кадры без ссылки; ключ объекта собран из
  идентификаторов, повторно положенный кадр ложится на то же место; ссылку
  записывает тот, кто успел первым (`... and storage_path is null`), второй
  кадр своим не считает.
- **Хранилище ещё лежит** — проход сперва спрашивает хранилище (`head_bucket`)
  и, если оно молчит, у телеграма ничего не качает; кадры ждут следующего прохода.
  В журнале бота `дозагрузка: хранилище недоступно, кадров ждёт N`.
- **Отказ одной проверки** (не хранилища) проход не обрывает: в журнале её
  идентификатор, остальные проверки идут дальше.
- **Телеграм не отдал кадр** — кадр остаётся ждать и называется в журнале
  (`телеграм не отдал N кадр(ов) проверки …`). Кадр старше двух суток уходит из
  частого прохода в редкий — раз в сутки, не больше 200 кадров, со сводкой без
  стека: `кадров ждёт дольше 2 суток: N, дольше всех — M суток`. Так кадр,
  которого телеграм не отдаст никогда, не занимает выборку и журнал каждые
  полчаса, но и не пропадает: спящее хранилище дольше двух суток доливается
  этим же редким проходом. Людям бот отсюда ничего не пишет.
- **На сдаче часть кадров телеграм не отдал** (аудитор собрал отчёт без них) —
  за эти кадры бот «догрузим сам» не обещает: `finish.photos_deferred_partial`.
- **Снятые проверки и убранные кадры** не берутся: снятые роль приложения не
  видит, убранные помечены `purged_at`.
- **Нет базы или `S3_*`** — проход пропускается и перепроверяется на следующем,
  задача не останавливается. Очередь при этом непуста, а `S3_*` нет — строка
  ERROR `хранилище не настроено, кадров ждёт N`.
- Любой непредвиденный сбой прохода — в журнал со стеком, задача идёт дальше.

Проверено живым прогоном 05.10.2026 на одноразовых Postgres и MinIO на
MUSPELHEIM (настоящий код, без телеграма — байты кадров отдавала подставка):
две сдачи при лежащем хранилище (спящий адрес — отказ за 5,1 с, остановленный
контейнер — за 2,2 с) → четыре кадра в очереди; проход при всё ещё лежащем —
0 из 4, `storage_down` за 2,1 с, у телеграма ничего не качалось; хранилище
поднято — 4 из 4 за 0,5 с, байты прочитаны обратно и совпали; повторный проход — 0. Сам разговор с телеграмом
(`finish.photos_deferred` в чате) проверен тестом через диспетчер
(`tests/test_bot_archive.py`), а не живым ботом.

Сколько ждёт, посмотреть на площадке (под ролью приложения):

```sql
select inspection_id, count(*) from photos
where storage_path is null and purged_at is null group by 1;
```

### 4.9.3. Сверка хранилища с таблицами: экшн-планы и предписания (#496)

Версия экшн-плана (`action_plans.upload_version`) и файл ответа на
предписание (`prescriptions_write.reply`) кладутся в хранилище **до**
транзакции: заливка до 25 МБ не держит ни соединение, ни замок. Строка не
легла — объект тут же убирается. Но если процесс умер между заливкой и
коммитом или уборка не прошла (в журнале `объект … без строки в базе не
убран`), объект остаётся без строки; при обрыве связи на самом коммите
возможно обратное. Находит такое `tools/storage_reconcile.py`.

| Участок | Хранилище | Таблица |
|---|---|---|
| `action-plans` | `action-plans/<запрос>/<файл>` | `action_plan_files` |
| `prescriptions` | `prescriptions/<предписание>/<ответ>` | `prescription_replies`, только ответы с файлом |

Что называет:

- **объект без строки** — файл лежит, версии или ответа к нему в базе нет;
  партнёр его не видит. Объект моложе порога (`--grace-minutes`, по умолчанию
  10) не считается — это загрузка в эту минуту; он показан строкой «свежие
  объекты без строки, не считаются»;
- **строка без объекта** — версия видна в истории, а скачать её нельзя;
- **ссылка не разбирается или ведёт мимо префикса** — строка не в форме
  `s3://корзина/ключ` или указывает на чужой участок; проверить её нечем.

**Ничего не удаляет и не пишет.** База — роль приложения (`DATABASE_URL`) в
сессии только для чтения: у роли есть `select` на обе таблицы, политика строк
открыта. Хранилище — тем же `S3_*`, что у продукта, только список объектов.
Строки читаются до списка объектов: строка коммитится после того, как объект
лёг, поэтому загрузка, совпавшая со сверкой, ложной «строки без объекта» не
даёт.

```bash
# внутри образа, как и доливщик копий (§4.9.1)
python tools/storage_reconcile.py                    # оба участка
python tools/storage_reconcile.py --grace-minutes 30
```

Код возврата: **0** — сходится, **1** — есть расхождения, **2** — сверка не
состоялась (нет `S3_*` или `DATABASE_URL`, база или хранилище не ответили,
нет корзины). Отказ хранилища на любой странице списка — 2, а не «объектов
нет».

Что делать с найденным — решает человек, инструмент только называет:
объект без строки можно удалить (ключ из вывода); строка без объекта — файл
потерян, партнёру положить версию заново (для версии на приёмке — после
возврата УК). Фоновой периодичности нет: сверка запускается руками.

Проверено живым прогоном 05.10.2026 на одноразовых Postgres и MinIO на
MUSPELHEIM, засеянных настоящим кодом продукта (две версии плана после
возврата, три ответа на предписание, один без файла): с порогом по умолчанию
— 3 расхождения (2 строки без объекта, 1 битая ссылка) и 2 свежих объекта
отдельно, код 1; с `--grace-minutes 0` — 5, код 1, число объектов в корзине
до и после одно и то же; после починки руками — «сходится», код 0; без
корзины, без `S3_BUCKET`, с недоступной базой — код 2.

## 8.14. Мини-апп обхода — свой сервис `walk` (D312, D316)

Мини-апп обхода пишет в идущие проверки, а админка их только читает. Поэтому
запись живёт в отдельном сервисе compose — `walk`, тот же образ, точка входа
`python -m src.web.walk_main`, только адреса `/tg/walk*` (`src/web/walk_app.py`).
Том `state` на запись есть только у него; у `web` он смонтирован `:ro`.

| Что | Как |
|---|---|
| Вход снаружи | Не меняется: прокси площадки → `web:8267`. Админка передаёт `/tg/walk*` сервису `walk` по внутренней сети проекта (`WEB_WALK_UPSTREAM=http://walk:8269`, задан в `docker-compose.yml`). ## 8.25. Хранение голоса у OpenAI (F-112)

Кадры и записи уходят в OpenAI с `store=False` (Responses API,
`src/recognize/client.py`). У расшифровки голосовых (`audio.transcriptions`,
`src/recognize/transcribe.py`) такого параметра нет — проверено по типам SDK
`openai==2.9.0` (`TranscriptionCreateParams`: `store` отсутствует), а лишний
параметр дал бы отказ 400 и сломал бы транскрипцию. Поэтому «не хранить голос»
достигается только на уровне организации OpenAI: включить Zero Data
Retention (или эквивалентную политику хранения) для организации и проекта, чей
ключ лежит в `OPENAI_API_KEY`. Это решение владельца по аккаунту, не код;
до его настройки срок хранения голоса определяют настройки организации по
умолчанию. Перечень данных, уходящих наружу, — `docs/18-access-map.md`.

## 8.23. Цепочка поставки: lockfile, сверка, SBOM, сверка источника (GHSA-7gm6-hc9m-w3vc)

**Зависимости ставятся только из lockfile с хэшами.** В `pyproject.toml` прямые
версии закреплены через `==`, а транзитивные раньше плавали между сборками. Теперь
всё дерево зафиксировано с хэшами файлов:

| Файл | Что в нём | Кто ставит |
|---|---|---|
| `requirements.txt` | всё дерево продукта | `Dockerfile` |
| `requirements-dev.txt` | то же плюс экстра `dev` | `make bootstrap`, `.github/workflows/pr-checks.yml` |
| `requirements-build.txt` | зависимости сборки из `[build-system]` (setuptools) | `Dockerfile`, `make bootstrap`, CI — вместе с остальным lockfile |
| `requirements-audit.txt` | сканер зависимостей и генератор SBOM (экстра `audit`) | `make audit`, `make sbom` (свой venv `.venv-audit`), задание `audit` в CI |

Установка — `pip install --require-hashes -r <файл> -r requirements-build.txt`, затем
`pip install --no-deps --no-build-isolation -e .` (сам проект, без права дотянуть
что-то мимо хэшей). Без `[build-system]` и `--no-build-isolation` pip качал бы
setuptools и wheel в изолированное окружение сборки без хэшей — дыра в
`--require-hashes`; версия сборки закреплена в `pyproject.toml`. Пакет без хэша в файле или с
несовпавшим хэшем ставку обрывает. Обновление — осознанное: правка `pyproject.toml`,
`make lock` (нужен `uv`, он только собирает файлы; ставит обычный pip), коммит
`pyproject.toml` и всех четырёх файлов вместе. Если правишь только `pyproject.toml`,
образ соберётся со старым lockfile — расхождение ловит человек на ревью.

Сканер вынесен в отдельную экстру и отдельный venv не ради красоты: он тянет `lxml`,
а при установленном `lxml` openpyxl пишет книги другим писателем, и тест
`test_plan_file_core` (книга с управляющим знаком в XML) падает уже при сборке
книги. Среда тестов не должна меняться от того, что в неё поставили сканер.

**Сверка с базами advisory.** `make audit` (`pip-audit` по `requirements-dev.txt` и `requirements-audit.txt`)
и задание `audit` в `pr-checks.yml`; находка роняет цель, а задание входит в ворота
`main-gate`. Новое advisory на уже закреплённую версию на PR без правок не
проявится: она всплывёт на следующем прогоне или при ручном `make audit` — раз в
неделю и перед раскаткой его стоит запускать руками (расписания у проверки нет).

**SBOM.** `make sbom` пишет `sbom.cdx.json` (CycloneDX 1.6, дерево продукта из
`requirements.txt`); в git он не хранится (`.gitignore`), задание `audit` в CI
прикладывает его артефактом прогона (`sbom-cyclonedx`, 30 дней).

**Сверка источника перед сборкой.** `scripts/prod-update.sh` и `deploy/demo/update.sh`
зовут `scripts/verify-source.sh` после `git pull` и до `build`: HEAD обязан
совпадать с `main` на GitHub (адрес берётся у самого GitHub, `git ls-remote`), а
отслеживаемые файлы — быть неизменёнными (неотслеживаемые, вроде `compose.edge.yaml`
и `data/`, не считаются). Иначе отказ с причиной, образ не собирается. Осознанный
обход — `ALLOW_UNVERIFIED_SOURCE=1`, он печатается. Подписей коммитов у проекта нет,
поэтому подпись не сверяется: сверка подтверждает, что собирается ровно `main` с
GitHub, но не автора коммита. `scripts/deploy.sh` (MUSPELHEIM) сверки пока не
делает.

## 8.24. Глубина рассуждения и кэш запроса разбора (#1267, D646)

Одна переменная окружения, раскатки не требует — читается при старте процесса:

| Переменная | Значения | Умолчание |
|---|---|---|
| `RECOGNIZE_REASONING_EFFORT` | `none`, `low`, `medium`, `high`, `xhigh`, `max` (список `gpt-5.6-sol` по документации провайдера); `default` — параметр в запрос не передавать | `low` |

- Глубина уходит только в разбор кадра и комментария (`kind=recognize`) и только на модель из `RECOGNIZE_MODEL`; сведение комментария, перевод и правка идут на своих моделях и своих запросов не меняют. Неизвестное значение — отказ с названием переменной, а не молчаливый откат.
- Вернуть прежнее поведение (до #1267 параметр не передавался, работало `medium`): `RECOGNIZE_REASONING_EFFORT=default`.
- Кэш запроса включать не надо и ключа кэша заводить не надо: запрос к модели разбора сам ставит явную точку кэша после постоянной части (инструкции, схема, зоны, весь перечень пунктов), `prompt_cache_options.mode=explicit`. Первый запрос после простоя (запись живёт не меньше 30 минут) пишет эту часть в кэш и стоит чуть дороже; следующие читают её. Проверка живого кэша — поле `usage.input_tokens_details.cached_tokens` в ответе провайдера; стенд `tools/bench_run.py` печатает его в таблице (токены, четвёртое число), в `model_usage` оно не пишется.
- Если в `RECOGNIZE_MODEL` стоит модель старше GPT-5.6, провайдер может не принять `prompt_cache_options`: тогда каждый вызов разбора кончится отказом модели, и бот уйдёт на ручной выбор. Менять модель разбора — проверять вызовом.
