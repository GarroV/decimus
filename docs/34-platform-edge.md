## 4.6. MCP-сервер и доступ к нему снаружи (T255, T256, решение D100)

> **Сегодня действует D102: наружу выходит НЕ этот туннель, а общий вход
> площадки — Tailscale Funnel `:10000` через звено socat.** Домена в учётке
> Cloudflare нет ни одного, а имя постоянного туннеля берётся из зоны, так что
> сделать его не из чего. Поэтому шаги 1–2 и ожидание строки `tunnel` — `Up`
> в шаге 5 относятся к площадке со своим доменом; что работает сегодня и как
> не размножить звено — [§1](history/deploy-muspelheim-2026.md).

**Что было не так.** Бот выдавал человеку правильную строку настройки Claude
Desktop, но добраться по ней было некуда, и причин было три: сервер на площадке
не был запущен вовсе (его поднимали руками, `make mcp`, и жил он до конца
сессии запустившего), наружу он не публиковался, а адрес в строке был петлёй —
то есть указывал на машину того, кто строку выполняет.

**Что сделано.** Сервер стал обычным сервисом стенда (`docker-compose.yml`,
сервис `mcp`): поднимается вместе с ботом, перезапускается сам, имеет свою
проверку здоровья. Наружу выходит туннель Cloudflare (сервис `tunnel`), а порт
по-прежнему не публикуется никуда: туннель живёт в сетевом пространстве
контейнера сервера и ходит к его ПЕТЛЕ. Другого пути к серверу нет — открыть
его пришлось бы, слушай сервер внешний адрес, а он этого не делает и не станет
(`src/mcp/config.py`, `_parse_host`). Площадка общая, рядом чужие проекты, а
сервер отдаёт проверки партнёров.

**Порядок, шаг за шагом. Шаги 1–2 делаются один раз, 3–7 — при каждой раскатке.**

**1. Завести туннель в панели Cloudflare** (Zero Trust → Networks → Tunnels →
Create a tunnel → тип `Cloudflared`). Панель покажет команду установки с
токеном внутри — **выполнять её не нужно**: коннектор у нас поднимает compose.
Из этой команды нужно только значение токена.

**2. Там же добавить туннелю Public Hostname:**

| Поле | Значение |
|---|---|
| Subdomain + Domain | имя, по которому сервер будет виден снаружи (домен — в учётке Cloudflare владельца) |
| Type | `HTTP` |
| URL | `127.0.0.1:8265` — петля контейнера `mcp` |

**Cloudflare Access на этот адрес не ставить.** Он показывает страницу входа
вместо ответа сервера, и мост Claude получит HTML вместо JSON-RPC. Дверь здесь
и так заперта: сервер отдаёт что-либо только по личному токену.

**3. Заполнить `.env` на площадке** — четыре строки, имена и объяснения в
`.env.example`:

| Переменная | Что писать | Что будет, если забыть |
|---|---|---|
| `CLOUDFLARE_TUNNEL_TOKEN` | токен из шага 1 | туннель перезапускается вечно, в журнале «Provided Tunnel token is not valid» |
| `COMPOSE_PROFILES` | `funnel` — общий вход площадки, `tunnel` — свой домен | звено или туннель просто не поднимется, стенд при этом здоров, а снаружи доступа нет |
| `BOT_MCP_URL` | `https://<имя из шага 2>/` | бот печатает заглушку заглавными; петля здесь хуже пустоты — она выглядит настройкой |
| `MCP_TOKENS` | можно оставить пустой, если задана `DATABASE_URL` | обе пустые — **сервер не стартует**: без карты и без базы личных токенов он поднялся бы открытым |

Про `MCP_TOKENS` отдельно: с #214 она перестала быть обязательной. Дверей две,
и хватает любой — карта «арендатор=токен» из `.env` даёт доступ СТОРОНЕ, а
личные токены, которые выпускает бот (T253), живут в базе и выдаются человеку
поимённо. На площадке с базой карту заводить не нужно вовсе: держать сторонний
токен ради старта значило бы держать открытой ровно ту дверь, которую личные
токены заводились заменить. Отказ остаётся там, где закрыты обе.

Запись карты читается как `арендатор:роль=токен` (например `HQ:admin=<токен>`):
без роли токен получает `guest` — только чтение. Права изменяющих инструментов
служебному токену выдаёт явная роль.

Если сторонний токен всё же нужен, значение генерируется на площадке и никуда
не пересылается:

```powershell
docker compose run --rm --no-deps --entrypoint python mcp -c "import secrets; print(secrets.token_urlsafe(32))"
```

**4. Раскатать обычным порядком** (см. [§1](history/deploy-muspelheim-2026.md) — пара `build` + `up`, `up --build`
пересборку пропускает, а без `BUILD_SHA` образ отвечает «сборка: неизвестна»):

```powershell
$env:BUILD_SHA=(git rev-parse --short HEAD)
docker compose build
docker compose up -d
```

**5. Посмотреть, что поднялось:**

```powershell
docker compose ps
```

Ожидается три строки: `bot` — `healthy`, `mcp` — `healthy`, `tunnel` — `Up`.
`tunnel` в состоянии `Restarting` означает токен из шага 1; отсутствие строки
`tunnel` — забытый `COMPOSE_PROFILES`.

**6. Смоук раскатки с ноутбука** — он спрашивает у самого бота, какой адрес тот
раздаёт людям, и краснеет на петле:

```bash
DEPLOY_HOST=<HOST> scripts/smoke.sh
```

**7. Проверка, которая одна и отвечает на вопрос «работает ли»** — с ЧУЖОЙ
машины, не с площадки и не с ноутбука, с которого шла раскатка:

```bash
DECIMUS_MCP_URL=https://<имя из шага 2>/ DECIMUS_MCP_TOKEN=<личный токен из веба> \
  python3 tools/mcp_outside.py
```

Токен берётся в вебе: «Настройки» → «Нейросети» → Claude → «Получить команду установки»
— токен внутри готовой строки (бот его больше не выдаёт, D626). Смоук отказывается считать проверкой петлю и
засчитывает доступ, только когда без токена сервер отвечает 401, выдуманный
токен отвергается, а настоящий получает ответ с нашим `serverInfo`. Страница
ошибки туннеля и посредник, отдающий 200 на что угодно, доступом не считаются.

**Что помнить руками:**

- **Пересоздали `mcp` — пересоздайте `tunnel`:** он живёт в сетевом
  пространстве контейнера сервера, и после пересоздания это пространство уже
  другое. `docker compose up -d --force-recreate tunnel`.
- **То же про звено:** оно живёт в том же пространстве и теряет его так же.
  С #216 звено — сервис compose (`link`, профиль `funnel`), поэтому руками его
  больше не поднимают: `docker compose up -d --force-recreate link`. Осиротевшие
  копии, которые оставались от ручного подъёма и врали в списке ([§1](history/deploy-muspelheim-2026.md)), так больше
  не заводятся — имя у сервиса одно.
- **Поменяли `MCP_PORT`** — поменяйте и адрес Public Hostname в панели
  Cloudflare, иначе туннель будет отвечать «за ним никого нет» (502).
- **`MCP_CHECKLIST_STORE` (правка методики через агента) в контейнере не
  работает без своего монтирования.** Переменная задаёт каталог на ХОСТЕ, а
  контейнер его не видит: хранилище версий создастся внутри контейнера и
  исчезнет вместе с ним, причём молча. У MCP эта настройка выключена (обе
  переменные пусты) — включать её надо вместе с томом, отдельной задачей.
  **У админки она включена всегда** (#404): сервис `web` в `docker-compose.yml`
  сам задаёт `MCP_CHECKLIST_STORE=/app/methodology` и монтирует том
  `methodology`, а `scripts/prod-update.sh` после подъёма пробует записать в
  него из контейнера и краснеет, если не вышло. **Бот монтирует тот же том
  только на чтение** и получает `MCP_CHECKLIST_STORE=/app/methodology` (волна 3,
  #430): оттуда он берёт чек-листы, открытые в боте, и снимает издание
  выбранного. До этого публикация из «Методики» переставляла указатель в томе,
  а бот проверял по каталогу хоста `/app/data`. До #404 том жил в
  незакоммиченном override на MUSPELHEIM, переезд на VPS его потерял, и раздел
  «Методика» открылся с плашкой «не настроено» при зелёном смоуке.
- `docker compose down -v` на площадке не выполнять никогда — флаг уносит том
  с незавершёнными проверками.

### Пересоздали `mcp` — пересоздайте звено (T279, #243)

Проверено фактом 17.09.2026: снаружи сервер отдавал 502, контейнер `mcp` при
этом стоял `Up (healthy)`. Звено `link` жило в сетевом пространстве ПРЕЖНЕГО
контейнера `mcp` (`docker inspect` показывал `container:96548f54…` при живом
`fe75b812…`): контейнер сервера пересоздали, звено — нет. В новом пространстве
порт 8266 не слушал никто, и весь путь снаружи обрывался там.

```powershell
# лечится пересозданием звена вместе с сервером
docker compose up -d --force-recreate mcp link

# и проверяется с ЧУЖОЙ машины, а не отсюда
python tools/mcp_outside.py
```

Начиная с этой волны молчания здесь больше нет: проба здоровья контейнера
стучится не только на порт сервера, но и на порт звена — тот, куда приходит
трафик снаружи, — и требует от него отказа 401 от нашего сервера. Осиротевшее
звено красит контейнер. Само оно от этого не чинится (Docker не перезапускает
контейнер по `unhealthy`, и правильно: чинить надо `link`, а не сервер) — но
видно становится сразу.

## 8.9. Вход через Cloudflare — постоянный (D236, D304, #424)

В части стран служебный домен заблокирован по решению властей: провайдер отдаёт свою
заглушку и свой сертификат. Поэтому люди, бот и доки ходят на адреса
Cloudflare Worker'ов. Это постоянный вход, своего домена не будет, пока
владелец сам не решит (D304).

| Что | Адрес для людей | Имя сайта в Caddy |
|---|---|---|
| Админка | `https://decimus.vasiliy-garro.workers.dev` | `<ORIGIN_HOST>` |
| MCP | `https://decimus-mcp.vasiliy-garro.workers.dev` | `<MCP_ORIGIN_HOST>` |

**Путь до сервера — туннель (Workers VPC).** Worker не ищет сервер по имени
служебный домен в интернете: привязка `EDGE` (VPC-сервис `vps-edge-caddy`) ведёт
запрос туннелем `vps-edge` прямо в Caddy на VPS. Имя служебный домен остаётся только
SNI и Host, по которым Caddy выбирает сайт, — его DNS и доступность в пути не
участвуют. Туннель — контейнер `cloudflared` в `/srv/edge`
(`GarroV/vps-infra: edge/compose.yml`), токен — `/srv/edge/tunnel.env` (600,
вне git); наружу он ничего не публикует и видит только Caddy. **Другого пути
нет (D521, 16.10.2026):** туннель лёг — Worker отвечает 502 `upstream
unavailable, please retry` и пишет `tunnel failed` (журналы Worker'ов выключены,
строку видно только в `npx wrangler tail <имя>`); привязки `EDGE` нет — 503. Сайты
decimus в Caddy (`GarroV/vps-infra: edge/sites/decimus.caddy`) отдают продукт
только запросу из сети туннеля с верным ключом фронта, всё прочее получает 403 —
в том числе прямой заход на имя сайта из интернета. До 16.10 при упавшем туннеле
запрос без тела уходил на сервер через интернет.

| Что в Cloudflare | Имя | ID |
|---|---|---|
| Туннель | `vps-edge` | `<TUNNEL_ID>` |
| VPC-сервис | `vps-edge-caddy` (хост `caddy`, проверка сертификата выключена — участок туннель→Caddy внутри docker-сети) | `<VPC_SERVICE_ID>` |

**Кэш статики на краю (#698).** Запрос до сервера идёт привязкой `EDGE` (туннель), а такой
подзапрос мимо кэша Cloudflare: статика с `Cache-Control: public, max-age=31536000, immutable`
всё равно доходила до VPS (TTFB CSS 210–440 мс, `cf-cache-status` в ответе не было). Теперь
`GET /static/*` админки уходит в отдельную точку входа Worker'а `StaticCache` (`front/src/index.js`,
маршрут — `front/src/proxy.js`) с включённым кэшем Worker'а (Workers Caching; работает и на
`workers.dev`, решает по `Cache-Control` ответа; нужен Wrangler 4.107.0+). Запрос уходит туда
без Cookie и Authorization; страницы под логином идут прежним путём и в кэш не попадают
(у `default` кэш выключен). Включается переменной `STATIC_CACHE=1` в шаблоне админки; у `mcp` и
стенда её нет. Сервер отдаёт `immutable` только на адрес с верным отпечатком (`src/web/assets.py`),
поэтому чужой `?v=` не кэшируется. Проверка после выкладки Worker'а (`./deploy.sh admin`):
дважды `curl -sI 'https://decimus.vasiliy-garro.workers.dev/static/decimus-web.css?v=<отпечаток из страницы>'`;
на втором ответе ждём падение TTFB (`-w '%{time_starttransfer}'`) и ответ без захода на VPS
(в логе Caddy нет второго запроса). Заголовка `cf-cache-status` Workers Caching может не
показывать: смотреть по времени ответа и по логу Caddy.

Код — `front/src/index.js` и `front/src/proxy.js`; проверка маршрутизации — `node --test
front/test/proxy.test.mjs` (входит в `tests/test_front_worker.py`). Настройки — шаблоны `front/wrangler.admin.template.jsonc`
и `front/wrangler.mcp.template.jsonc`: адреса инфраструктуры в репозиторий не
кладутся (D431, `tests/test_no_infra_identifiers.py`), в шаблонах стоят заглушки
`<VPC_SERVICE_ID>`, `<ORIGIN_HOST>`, `<MCP_ORIGIN_HOST>`. Wrangler подстановку
переменных в конфиг не поддерживает, поэтому рабочий конфиг собирает
`front/deploy.sh` из шаблона и неотслеживаемого `front/.deploy.env`
(образец — `front/.deploy.env.example`; собранные `wrangler.*.jsonc` и
`.deploy.env` в `.gitignore`).

Выкладка, из `front/`:

1. один раз: `cp .deploy.env.example .deploy.env` и вписать значения (ID
   VPC-сервиса — в панели Cloudflare → Workers VPC; имена сайтов — как в
   `/srv/edge/sites` на VPS);
2. `./deploy.sh admin` и `./deploy.sh mcp` (лишние аргументы уходят в
   `wrangler deploy`, например `--dry-run`).

Секрет `FRONT_KEY` задаётся отдельно (`npx wrangler secret put FRONT_KEY -c
wrangler.admin.jsonc`, после первого запуска `deploy.sh`) и выкладкой не
затирается. Журналы Worker'ов выключены (`observability.enabled: false`): через
них идут пароли, ключи и тела форм; код их тоже не пишет, в консоль уходит
только строка про откат туннеля. Всё, что до D431 попало в историю git, считается
раскрытым.

**Адрес посетителя.** За Worker'ом все посетители пришли бы с адресов Cloudflare,
а счётчик неудачных входов считает по адресу. Поэтому Worker передаёт адрес в
`X-Decimus-Client-IP` вместе с ключом фронта (`X-Decimus-Front-Key`), и Caddy
ставит его в `X-Forwarded-For` только при верном ключе
(`GarroV/vps-infra: edge/sites/decimus.caddy`). Ключ лежит в двух местах и больше
нигде: секрет `FRONT_KEY` у обоих Worker'ов и `/srv/edge/sites/decimus-front.snippet`
на VPS (в git не попадает). **Смена ключа без простоя** (так сменён 16.10.2026,
D521): новый ключ генерируется в файл (`openssl rand -hex 32`), значение нигде не
печатается; в сниппете на время смены стоят оба ключа (две строки `header
X-Decimus-Front-Key …` в одном именованном сопоставителе — Caddy сравнивает их по
«или»), `caddy reload`; затем `npx wrangler secret put FRONT_KEY -c
wrangler.admin.jsonc < файл` и то же для `wrangler.mcp.jsonc` (значение — со
стандартного ввода, не аргументом); затем в сниппете остаётся только новый ключ и
снова `caddy reload` (`docker compose exec caddy caddy reload --config
/etc/caddy/Caddyfile` в `/srv/edge`). Проверка — админка и MCP через Worker
отвечают, прямой заход на сайт Caddy — 403.
Проверено 29.09: через фронт, напрямую и с подделанным ключом счётчик видит
настоящий адрес посетителя.

**Ключ на стороне origin: `WEB_FRONT_KEY`** (F-107 аудита). Caddy проверяет ключ,
но админка доверяла `X-Forwarded-*` любому соседу по подсети
`WEB_TRUSTED_PROXY_ADDR`: другой контейнер сети `edge-decimus`, дотянувшийся до
порта мимо Caddy, подделывал адрес клиента. Теперь, если задана `WEB_FRONT_KEY`
(то же значение, что секрет `FRONT_KEY`; в `.env` площадки, в git нет),
`guard_forwarded` (`src/web/proxy.py`) сверяет `X-Decimus-Front-Key` за постоянное
время и при несовпадении или отсутствии заголовка обращается с соседом как с
чужим: `X-Forwarded-*` вырезаются, первый такой случай пишется в журнал (значение
ключа не пишется никогда). **Не задана — поведение прежнее** (доверие по подсети),
при старте в журнале одно предупреждение «WEB_FRONT_KEY не задан». Включение:
убедиться, что Caddy пропускает `X-Decimus-Front-Key` к админке (по умолчанию
`reverse_proxy` передаёт заголовки запроса), вписать `WEB_FRONT_KEY` в окружение
площадки, пересоздать контейнер `web`; проверка — вход через фронт работает, а
запрос из соседнего контейнера с подделанным `X-Forwarded-For` счётчик видит с
адреса соседа. **При смене ключа** (см. выше) значение `WEB_FRONT_KEY` менять в
том же окне, что и сниппет Caddy: пока в сниппете два ключа, у origin — один;
ставить новый только после того, как Worker'ы перешли на него. Сервер MCP делает ту же сверку
для `X-Forwarded-For` (адрес клиента в журнале действий, `src/domain/client_ip.py`):
ключ он берёт из `MCP_FRONT_KEY`, а в `docker-compose.prod.yml` по умолчанию это
`WEB_FRONT_KEY`, отдельной записи в `.env` не нужно; `MCP_FRONT_KEY` не задан — доверие по
подсети и предупреждение при старте. Caddy передаёт заголовок ключа к обоим сайтам
(`GarroV/vps-infra: edge/sites/decimus.caddy`).

**Вход через Google через фронт.** Нужен второй адрес возврата: в `.env` VPS
`GOOGLE_FRONT_REDIRECT_URI=https://decimus.vasiliy-garro.workers.dev/auth/google/callback`,
и та же строка — в **Authorized redirect URIs** клиента `decimus-web` в Google
Console (за владельцем). Метку фронта (`X-Decimus-Front`) ставит только Caddy;
без переменной фронт входит паролем. Черновик письма в Gmail возвращается на
`GOOGLE_MAIL_REDIRECT_URI`, с 09.10.2026 он тоже на Worker'е.

## 8.9.1. Публичный адрес стенда через Cloudflare

Имя стенда в Tailscale Funnel с 14.10.2026 не резолвится снаружи (внутри tailnet
резолвится). Стенд `decimus-viktoria` поэтому получил адрес на Cloudflare, который от
Funnel не зависит: `https://decimus-stand.vasiliy-garro.workers.dev`. Прод (§8.9) не
затронут: свой Worker, свой сайт в Caddy.

Путь: браузер → Worker `decimus-stand` → туннель `vps-edge` (VPC-сервис тот же, что у
прода) → Caddy на VPS → адрес стенда внутри tailnet → веб стенда.

| Звено | Что и где |
|---|---|
| Площадка стенда | `tailscale serve --bg --tcp=9030 tcp://127.0.0.1:8294`: порт 9030 открыт **только внутри tailnet** (не Funnel), конфигурация хранится в `tailscaled`. Funnel-порты не тронуты |
| Caddy на VPS | отдельный файл `/srv/edge/sites/decimus-stand-viktoria.caddy`: свой сайт, `reverse_proxy` на адрес стенда в tailnet, заголовки фронта срезаются. Ключ фронта не используется: адрес посетителя для счётчика входов на стенде — адрес туннеля |
| Worker | `front/src/index.js` без изменений; шаблон `front/wrangler.stand.template.jsonc`, выкладка `./deploy.sh stand` (в `front/.deploy.env` добавляется `STAND_ORIGIN_HOST`, образец — `.deploy.env.example`). Секрет `FRONT_KEY` у него свой, случайный: Caddy стенда его не проверяет, прод-ключ в Worker стенда не попадает |
| Настройки стенда | не менялись: заслон происхождения (`src/web/origin.py`) сравнивает `Origin` с `Host`, а Worker подставляет в `Origin` адрес сайта Caddy, то есть `Host` |

Проверено 14.10.2026 из браузера (Playwright, публичный DNS): вход, десять страниц, смена
пароля (POST через заслон происхождения), выход, повторный вход; ошибок консоли и
заблокированных ресурсов нет.

**Перезапуск.** Ручной перезапуск сервиса `web` рвёт `web-link` (он живёт в сети `web`):
после него пересоздать звено — `up -d --force-recreate web-link`; автообновление стенда
делает это само.

**Откат.** `npx wrangler delete -c wrangler.stand.jsonc` в `front/`, удалить файл сайта
в Caddy и перезагрузить конфиг, на площадке `tailscale serve --tcp=9030 off`.

## 8.19. Подключение нейросетей входом через сайт (OAuth, D417, D695)

Отдельного сервиса нет: сервер авторизации приезжает с образом веба
(`src/web/oauth.py`), третья дверь — с образом MCP (`src/mcp/config.py`).
Как устроено — `docs/furca/blocks/mcp.md`, раздел «Вход через сайт (OAuth)»;
экран — `docs/12-web-admin.md`.

1. **Миграция `0054_oauth.sql`** — таблицы `oauth_clients`, `oauth_codes`,
   `oauth_grants` (подключения), `oauth_tokens` (только отпечатки SHA-256).
   Данных не трогает. Накат: `docker compose exec -T bot python -m src.db.migrate`.
2. **Переменные** — в `.env` площадки, читают и `web`, и `mcp` (общий `env_file`):

   | Переменная | Значение | Что делает |
   |---|---|---|
   | `WEBAUTHN_RP_ID`, `WEBAUTHN_ORIGIN` | домен и происхождение для ключей доступа второй ступени (D463); пусты — берутся из `ADMIN_PUBLIC_URL` | на проде `decimus.vasiliy-garro.workers.dev` и `https://decimus.vasiliy-garro.workers.dev`, НЕ `workers.dev` (общий суффикс, отказ на старте). Потерянный доступ главного админа: `dc exec web python tools/web_user.py reset-second-factor <логин> --tenant HQ` |
| `ADMIN_PUBLIC_URL` | внешний адрес админки, `https://<адрес входа>` (§8.9), с префиксом, если он есть | издатель OAuth: адреса `/oauth/authorize`, `/oauth/token`, `/oauth/register` в метаданных строятся от него |
   | `MCP_PUBLIC_URL` | тот же адрес, что `BOT_MCP_URL` | ресурс OAuth: его человек вставляет в нейросеть; он же в `resource_metadata` отказа 401 |

   Пусто хотя бы одно — OAuth выключен целиком, всё работает как раньше.
   Кривое значение (не `https`, строка запроса) — сервис не поднимается и
   называет переменную. После правки — перезапуск `web` и `mcp`.
3. **Пути снаружи.** Нейросеть ходит со своих серверов (Anthropic, OpenAI): `ADMIN_PUBLIC_URL`
   должен отдавать `/.well-known/oauth-authorization-server` и `/oauth/*` без
   входа (их пропускает заслон админки), `MCP_PUBLIC_URL` — POST и GET
   `/.well-known/oauth-protected-resource`. Админка отдаёт метаданные по адресу
   `<ADMIN_PUBLIC_URL>/.well-known/oauth-authorization-server`. Если у неё снаружи
   есть префикс пути, RFC 8414 велит искать их в корне хоста
   (`/.well-known/oauth-authorization-server/<префикс>`), а корень — не админки;
   такая раскладка не проверена, проще дать админке свой корень.
4. **Смоук** — тестовой учёткой каждой роли (УК-админ, аудитор, контроль),
   пароль только из окружения:

   ```bash
   OAUTH_SMOKE_PASSWORD=... python3 tools/oauth_smoke.py \
       --admin "$ADMIN_PUBLIC_URL" --mcp "$MCP_PUBLIC_URL" --login <тестовая учётка>
   ```

   Ждём `OK` в конце; в выводе — роль и список инструментов (контроль — только
   рейтинги, аудитор — без правки методики и загрузки). Прогон заводит и сам же
   отзывает подключение. Затем в базе:
   `select revoked_reason, count(*) from oauth_grants group by 1` — отзыв `user`.
5. **Последний шаг — руками:** claude.ai → Настройки → Коннекторы → Добавить
   свой коннектор → адрес из плитки «Нейросети»; `claude mcp add --transport http
   decimus <MCP_PUBLIC_URL>` в Claude Code. ChatGPT (D695, #1439): обычные чаты и
   браузер подключает администратор рабочего пространства — добавляет MCP-сервер
   по тому же адресу с входом OAuth, потом каждый входит своей учёткой decimus;
   настольное приложение на Mac — командой из плитки «Нейросети» → ChatGPT
   (личный токен, мост в `~/.decimus/chatgpt`, регистрация штатным `codex mcp
   add` из ChatGPT.app; сервер виден только во вкладке Work). Ручное «Plugins →
   Add MCP server» вход OAuth не запускает — не использовать. Адреса возврата и их
   проверка — `docs/furca/blocks/mcp.md`.
6. **Отключить всё сразу** — опустошить обе переменные и перезапустить `web` и
   `mcp`: маршрутов OAuth нет, токены через сайт не принимаются. Токены бота и
   `.env` работают как прежде.
