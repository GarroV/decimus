# Активация технических пунктов и возврат методики

Выпуск кода и публикация методики — последовательные операции. Сначала все
сервисы получают новый runtime и проходят смоук. Затем публикуется издание
с техническими пунктами. Новые проверки получают его; начатые и завершённые
сохраняют свои издания и подтверждения.

Фактически выполнено 27.11.2026: production runtime `aa8ec972`, опубликованная
версия `turkish-2026-11-27-4571a1ec7a65`, 74 пункта. Все четыре сервиса читают
её; остальные файлы методики и scoring побайтово совпали с прежним изданием.
Прежние218 проверок и 140 отчётов сохранены, искусственных подтверждений нет.

## Подготовка

`tools/technical_activate.py` добавляет только `technical_checks.json` в копию
**опубликованного** издания. Не переносит остальные файлы подготовленного набора,
не меняет scoring, зоны, формулировки и веса. Источник — частный файл вне Git.

Фактическая опубликованная версия перед выпуском:
`turkish-2026-11-10-912b99e5c7e7` в `/app/methodology/current`.
`/app/data` содержит другой legacy-набор; брать его за основу активации нельзя.
Перед запуском нужно повторно прочитать текущий указатель. Значения ниже относятся
к предвыпускной проверке; при изменившемся указателе утилита откажет.

1. Сохранить резерв базы, состояния и всего хранилища методик.
2. Развернуть новый код на всех четырёх сервисах и проверить здоровье.
3. Поместить согласованный частный manifest в `/tmp/technical_checks.json`
   контейнера `decimus-web-1`. Файл не добавляется в образ или репозиторий.
4. Проверить без записи:

```sh
docker exec decimus-web-1 python tools/technical_activate.py stage \
  /tmp/technical_checks.json --expected turkish-2026-11-10-912b99e5c7e7
```

Ожидается `status=validated`, 74 пункта, 221 пара «пункт — зона» до отбора по стране.
Для конкретной проверки число зависит от применимости к стране (например, 211).
Проверены существование кодов/зон, формат и отпечаток опубликованной основы.
Проверка без `--write` не создаёт издание и не меняет журнал.

## Создание и публикация

```sh
docker exec decimus-web-1 python tools/technical_activate.py stage \
  /tmp/technical_checks.json --expected turkish-2026-11-10-912b99e5c7e7 --write
```

Нужно получить `accepted=true` и сохранить выданное поле `version` в журнале
выпуска. Издание ещё не опубликовано. Движок проверяет и считает кандидата;
общая блокировка отвергает параллельную правку или изменение опубликованной
основы. Уже существующий другой manifest нельзя затереть этой утилитой —
для дальнейших изменений используется редактор методики.

```sh
docker exec decimus-web-1 python tools/technical_activate.py publish NEW_VERSION \
  --expected turkish-2026-11-10-912b99e5c7e7
```

`NEW_VERSION` заменяется точным значением предыдущего шага. Публикация проверяет
ожидаемый текущий указатель под той же блокировкой, что правки. После публикации
повторный `stage` с тем же manifest и новым `--expected` возвращает `unchanged`.
Проверка новой функциональности с фиктивными данными проводится на стенде.
На проде не создаются тестовые учётки или проверки для этого выпуска.

## Возврат

После публикации **нельзя возвращать runtime 22056208**: его набор `DATA_FILES`
не включает `technical_checks.json`, поэтому отпечаток нового издания не совпадёт.
Это воспроизведено на копии опубликованной методики, а не выведено только из кода.

Чтобы остановить выдачу технических пунктов новым проверкам, сохранить новый
runtime и выполнить:

```sh
docker exec decimus-web-1 python tools/technical_activate.py publish \
  turkish-2026-11-10-912b99e5c7e7 --expected NEW_VERSION
```

Новые проверки снова получают прежнюю методику. Начатые по новому изданию
продолжают требовать свои подтверждения; их снимки и завершённая история остаются.
Таблицы, издания и файлы доказательств не удаляются. Ошибку нового runtime после
начала новых проверок исправляют следующим выпуском с сохранением нового читателя
данных. Старые образы пригодны для возврата кода только **до** активации методики.

## Публичное демо

`demo/data/technical_checks.json` содержит два вымышленных пункта по DEM-кодам.
Частная методика в демо не переносится. Посев истории закрепляет копию прежнего
демо-набора без technical manifest: завершённым проверкам не приписываются
непроведённые подтверждения. Живые RU/EN обходы и новые проверки получают два
обязательных пункта. Штатный reset демо остаётся отдельным от production.
