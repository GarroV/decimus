# Оценки в агрегаторах доставки

> Ведётся руками. Сверять с кодом: `src/ratings/aggregators/`, `src/db/agg_store.py`,
> `src/db/migrations/0050_aggregators.sql`, `0051_units_registry.sql`, `0053_agg_requests.sql`,
> `src/ratings/coverage.py`. Решения — D389 (раз в сутки), #638, D420 (заявка на обновление),
> D424 (реестр пиццерий, охват, автопоиск Glovo).

## Что это

Гость выбирает пиццерию в Wolt, Glovo, Bolt Food, Яндекс Еде и других приложениях
доставки по оценке на витрине. Блок «Оценки на картах и в агрегаторах» на странице
рейтингов показывает эту оценку по тем же группам, что и средние РС и РКО (кластеры в
срезе IMF, иначе сам срез): после колонок карт — по колонке на агрегатор, где у группы
есть хоть одна пиццерия (D423). Выбран период раньше первого сбора — показаны последние
собранные оценки, и под таблицей сказано, на какую дату. Бот собирает оценки сам раз в сутки, без браузера и без участия человека.

## Поверхности

| Поверхность | Для кого | Что делает |
|---|---|---|
| `/ratings` — блок `maps`, колонки агрегаторов | все, кто видит рейтинги | средняя группы на каждом агрегаторе, число пиццерий, дата данных; строка «Не собралось: …», если последний сбор агрегатора не удался |
| то же, контроль и админ УК | `may_manage` | под строкой сбоя — по агрегатору: когда сбор, когда последний удачный, текст ошибки |
| то же, контроль и админ УК | `may_manage` | кнопка «Обновить сейчас» (`POST /ratings/aggregators/update`, D420): ставит заявку на сбор всех агрегаторов, пока заявка не выполнена — вместо кнопки строка «Обновление в очереди с …»; остальным кнопки нет, адрес отвечает 403 |
| MCP `aggregators_status`, `request_aggregators_update` | Claude: любой токен читает состояние, токен УК просит обновить (D420) | то же, что видит контроль на экране: по агрегатору последний сбор, исход, ошибка (текст — только токену УК), последний удачный, заявка в очереди; заявка на обновление выбранных агрегаторов |
| `/ratings/coverage` — «Пиццерии на площадках» | все, кто видит рейтинги | где какая пиццерия есть и свежи ли данные: колонки — карты и агрегаторы, ячейка — оценка, △ (данные старше 7 дней), «—» (нет на площадке) или пусто (площадки в стране нет); `docs/15-ratings.md` |
| `POST /ratings/coverage/link` | контроль, админ УК | привязать пиццерию по ссылке на страницу магазина: Glovo (первая пиццерия нового города) или Migros Yemek (новая пиццерия Турции, #717); поле `aggregator` — `glovo` или `migros_yemek`, иное — 400 |
| бот, задача `agg_loader` | — | раз в час смотрит журнал: прошло 20 ч с последнего сбора — собирает все агрегаторы; раз в минуту смотрит только таблицу заявок (`agg.requests`) и по заявке собирает названных сразу, затем закрывает её исходом (D420) |
| `python -m src.ratings.aggregators` | разработка, на площадке через `docker exec decimus-bot-1 …` | собрать сейчас (все или `run wolt glovo`), наполнить справочник (`seed <файл.json>`) |

Компоновка — как у остальных блоков: контролинг включает и двигает блок на «Загрузках»
(`ratings.layout`, D368).

## Сквозные сценарии

1. **Сбор дня.** Бот берёт пиццерии из publicapi.dodois.io по всем странам IMF
   (`ratings.countries.is_imf`) и кладёт их в реестр `agg.units` (ниже); работающие
   (координаты и страна) идут дальше: по каждому агрегатору своей страны ищет Додо у координат пиццерии, привязывает
   найденное к пиццерии и пишет снимок дня. Агрегаторы собираются параллельно, по потоку
   на каждый: у каждого своя пауза между запросами, поэтому нагрузка на витрину та же,
   что и подряд. Одна строка журнала на агрегатор.
2. **Чтение.** Страница берёт для каждой привязанной точки последнюю оценку не позже
   конца выбранного периода и сводит по группам.
3. **Сбой.** Агрегатор не ответил, ответил не тем или вернул пусто, хотя в прошлый удачный
   сбор точки были, — в журнале `failed`, старые оценки остаются, страница пишет
   «Не собралось: …».
4. **Новая пиццерия.** Появилась в публичном API — попала в реестр сама, на экране
   охвата стоит с чипом «новая». Поисковые агрегаторы находят её при следующем сборе по
   координатам. Glovo — тем же сбором: если рядом (до 40 км) есть известная точка Glovo,
   `glovo_link.discover` спрашивает Glovo с координатами пиццерии и записывает точку, если
   её `addressId` ещё не занят (ниже). Первая пиццерия города, где Glovo ещё нет, —
   ссылкой на страницу магазина в форме «привязать» на экране охвата.

5. **Обновить сейчас (D420).** Контроль нажимает кнопку на странице рейтингов или просит
   Claude (`request_aggregators_update`; можно назвать агрегаторы, по умолчанию — все). Просьбу
   принимает процесс, получивший её (веб, MCP), — он только пишет строку в `agg.requests` с
   автором (логин учётки или подпись вызова MCP). Бот в течение минуты видит заявку, собирает
   названных агрегаторов тем же `collect.run_all`, не дожидаясь 20 часов, и закрывает заявку:
   `ok`, либо `failed` с текстом ошибок по агрегаторам. Пока заявка не выполнена, вторая не
   заводится — ответ «уже в очереди»; это держит частичный уникальный индекс в базе, а не
   проверка в коде. Просить можно только агрегаторов, которых бот собирает сам (Яндекс Еда на
   паузе — не просится). Людям бот о сборе не пишет: итог виден на экране и в `aggregators_status`.

## Словарь

- **Точка** — страница пиццерии на витрине агрегатора; ключ `(aggregator, point_key)`.
- **Привязка** — какая пиццерия Додо стоит за точкой (`dodo_id` = `UUId` из publicapi).
- **Родная шкала** — Wolt из 10, Glovo — % довольных, остальные — из 5.
- **Справочник** — `agg.points`: точки с привязкой. Для поисковых агрегаторов
  обновляется каждым сбором, для Glovo дополняется автопоиском и привязкой по ссылке,
  для Chowdeck наполняется `seed`-ом.
- **Реестр пиццерий** — `agg.units`: все пиццерии Dodo из публичного API (D424).

## Как считается

- **Привязка** — ближайшая точка не дальше 400 м, одна точка — одной пиццерии
  (`collect.assign`). Точка без привязки хранится, но в сводку не идёт.
- **Средняя группы** на агрегаторе — по всем оценкам её пиццерий: оценка точки
  взвешивается числом оценок; агрегатор числа не отдаёт — вес 1 (`summary.summarize`).
  Шкалы разных агрегаторов не сводятся.
- **Страж пустого ответа** (`collect.verdict`): 0 точек при ненулевом прошлом удачном
  сборе или одни ошибки — сбой. Ошибки по отдельным точкам при найденных остальных —
  не сбой, они в тексте журнала.
- Точку можно исключить из сводки руками: `agg.points.excluded_reason` (сбор её не трогает).

## Данные

Схема `agg` (миграции `0050`, `0051`, `0053`): `points` — справочник, `ratings` — снимок дня
`(aggregator, point_key, on_date)`, `loads` — журнал сбора, `units` — реестр пиццерий,
`requests` — заявки на обновление вне расписания (кто просил, какие агрегаторы, исход).
Пишет роль приложения (бот собирает и закрывает заявки; веб и MCP заявки принимают),
читает страница.

## Реестр пиццерий

`agg.units` (`dodo_id` — 32 hex, страна, имя, координаты, `working`, `first_seen`,
`last_seen`) заполняет каждый сбор: `collect.run_all` читает публичный API по всем
странам IMF плюс странам сборщиков (`fetch_units` подменяется в тестах) и пишет
`agg_store.save_units`. Отказ записи реестра сбор не останавливает — строка в журнале.
Страны IMF база не отдала — берутся только страны сборщиков.

- Новая пиццерия получает `first_seen = сегодня`; известная обновляется, `first_seen`
  не трогается. **Первое заполнение** (таблица была пуста) пишет `first_seen = null` —
  «была с самого начала», иначе вся сеть была бы «новой».
- «Новая» на экране охвата — `first_seen` не старше 30 дней (`coverage.NEW_DAYS`).
- Записи не удаляются: пиццерия, пропавшая из API, остаётся со старым `last_seen`.
  Закрытая (`State != 1`) — `working = false`, на экране охвата не показывается.

## Экран «Пиццерии на площадках»

`GET /ratings/coverage` (`src/ratings/coverage.py`, `render_coverage` в `src/web/ratings.py`).
Площадка ожидается в стране пиццерии, если страна есть у сборщика (`COUNTRIES`) или —
для Glovo и Chowdeck — у них есть точки в этой стране; Яндекс Еда на паузе (D397)
показывается, только где точки остались. Карты (Google, Яндекс) ожидаются везде.
Устаревшей считается последняя оценка старше `coverage.STALE_DAYS` = 7 дней: значок △
с датой в подсказке, строка не подсвечивается (D424). Счётчик «без точки на площадках» —
пиццерии, у которых нет точки хотя бы на одном ожидаемом агрегаторе (карты не считаются).

## Точки Glovo: автопоиск и привязка по ссылке

Id в адресе магазина Glovo — бренд в городе, точку выбирает Glovo по координатам доставки
(`glovo.py`). Поэтому новой пиццерии не нужен браузер (`glovo_link.py`, D424, #648):

1. **Автопоиск** — в каждом сборе Glovo, после обновления известных точек. Для работающей
   пиццерии страны, где Glovo уже есть, и без точки Glovo берётся ближайшая известная
   точка той же страны не дальше 40 км (`DONOR_MAX_M`) — её `store_id` и `city_code`; запрос
   `v3/stores/{id}` идёт с координатами самой пиццерии. Новый `addressId` — точка
   пиццерии: записывается с её кодом (расстояния нет, `link_distance_m = null`) и первой
   оценкой. `addressId`, который уже в справочнике, — пиццерия не на Glovo или покрыта
   чужой точкой, пропуск. Ошибка по одной пиццерии — в журнал, остальные идут. Не найденная
   пиццерия пробуется заново каждый сбор: один запрос в сутки на неё.
2. **Привязка по ссылке** — первая пиццерия нового города, где известной точки нет. На
   экране охвата, ячейка Glovo «—», форма «привязать» (контроль и админ УК): ссылка
   `https://glovoapp.com/<язык>/<страна>/<город>/stores/<магазин>`. Сервер читает страницу
   (в ней `/v4/stores/<store_id>/addresses/…` и `"cityCode":"…"`), берёт `store_id` и
   `city_code` и спрашивает Glovo с координатами пиццерии, как в автопоиске. Адрес
   проверяется строго (`parse_store_url`): https, хост ровно `glovoapp.com`, без порта и
   логина, путь указанной формы; страница читается без редиректов — на другие хосты сервер
   не ходит (SSRF). Страна в ссылке должна совпасть со страной пиццерии. Итог — одной
   строкой над таблицей; никому ничего не отправляется.

## Точки Migros Yemek: привязка по ссылке (#717)

Сам сбор новую пиццерию Турции на Migros не найдёт: координат карточка не отдаёт, а у
поиска нет фильтра по бренду. Поэтому новая точка заводится с экрана охвата: ячейка
Migros Yemek «—», форма «привязать» (контроль и админ УК), ссылка
`https://www.migros.com.tr/yemek/<slug>`. Сервер (`migros_link.py`) берёт из неё только
`slug` — https, хост `www.migros.com.tr` или `migros.com.tr`, без порта и логина, путь
`/yemek/<slug>` того же вида, что пропускает ретранслятор, — и читает карточку тем же
путём, что сбор (через домашний сервер, ниже). Название должно быть Dodo Pizza; страна
пиццерии — Турция; точка не должна быть уже в справочнике. Записывается точка с кодом
пиццерии и первой оценкой. Домашний сервер спит — отказ словами «проверьте, не спит ли
он». Колонка Migros на экране есть, пока в справочнике есть хоть одна его точка Турции.

## Справочник Glovo, Chowdeck и Migros Yemek

Ручной путь — для Chowdeck и запасной для Glovo и Migros Yemek, когда страница магазина не открывается
с сервера. Файл — список объектов с полями `aggregator, point_key, country_code, name, url, lat,
lng, dodo_id, dodo_name, link_distance_m, extra`. Для Glovo в `extra` обязательны
`store_id`, `city_code`, `country`, `lat`, `lng` — без них оценку не запросить; `point_key`
— `addressId` точки. Повтор безопасен: точка обновляется по ключу.

```bash
scp seed.json contabo:/tmp/ && ssh contabo 'docker cp /tmp/seed.json decimus-bot-1:/tmp/ \
  && docker exec decimus-bot-1 python -m src.ratings.aggregators seed /tmp/seed.json'
```

Новую точку Glovo, если автопоиск и ссылка не помогли, ищут в браузере на glovoapp.com: адрес доставки — у пиццерии, в
выдаче магазин Dodo Pizza; `store_id` и `addressId` видны в запросе `v3/stores/…`
вкладки «Сеть». Первичный справочник (39 Glovo, 16 Chowdeck, 11.10.2026) собран так же,
файл разведки — вне git (`workbench/private/decimus/aggregators-2026-10-11/`).

**Migros Yemek.** Координат у точки нет, поэтому пара «точка — пиццерия» задана
справочником (28 точек на 12.10.2026, все работающие пиццерии Турции). Откуда пары:
открытый поиск заведений `POST …/rest/food-bff/api/search/stores` с `cityIds`
(номер города = автомобильный код провинции: Адана 1, Анталья 7, Мерсин 33, Измир
35, Маниса 45; страницы по 500) отдаёт все заведения города, Додо — по названию; квартал в
названии («Dodo Pizza, Buca (Vali Rahmi Bey Mah.)») сверен с кварталом у той же
пиццерии на Trendyol Go, а четыре точки без такой пары — по координатам пиццерии и
району. Фильтра по бренду у поиска нет (в Анталье ~4000 заведений), поэтому сбор дня
ходит только по известным точкам — новая пиццерия на Migros заводится строкой
справочника (#717).

## Migros Yemek через домашний сервер (D434)

Адресу сервера площадки Migros отвечает 403 на весь сайт, включая главную, а с
домашнего адреса карточка открыта. Поэтому сбор идёт с прода как обычно, а запрос
к Migros — через ретранслятор на MUSPELHEIM (`src/ratings/aggregators/migros_relay.py`,
`deploy/migros-relay/`):

- ретранслятор делает ровно `GET /stores/<slug>` → карточку магазина Migros (хост
  зашит, `slug` по шаблону, без редиректов) и `GET /health`; всё прочее — 404;
- контейнер слушает `127.0.0.1:9021` домашнего сервера, в сеть Tailscale его
  выводит `tailscale serve --bg --tcp 9021 tcp://127.0.0.1:9021`; вне Tailscale
  его нет;
- на проде адрес задаёт `MIGROS_RELAY_URL` (адрес домашнего сервера в Tailscale и
  порт); http допустим только на адреса Tailscale (`base._https`), канал шифрует
  сам Tailscale.

**Это ненадёжно по природе:** домашний сервер засыпает и сам не просыпается.
Сбой виден так: строка «СБОЙ» в журнале сбора на странице рейтингов, △ у
устаревших оценок на «Пиццериях на площадках», и одна тревога в канал FURCA после
суточного сбора с ошибками (`aggregators/alert.py`, D438, D439; любой агрегатор, у
Migros — подсказка разбудить сервер): `POST /notify`, проект `decimus`, вид `alert`,
адрес и ключ — `FURCA_NOTIFY_URL`, `FURCA_SECRET` (`http://` — только для внутреннего имени без точки, localhost или локального адреса, внешний адрес — только `https://`); канал доводит её до владельца в
Telegram. Бот достаёт до канала по сети контейнера канала (`compose.edge.yaml`
площадки): сетевой экран сервера не пускает контейнеры к адресам хоста. Причина сбоя пишется
словами и без адреса ретранслятора: «Migros ответил HTTP 403 (через домашний
сервер)» или «домашний сервер не отвечает». Цепочку держит `tests/test_migros_relay.py`.
Если первые три точки подряд не ответили (`collect.GIVE_UP_AFTER`), остальные не
опрашиваются: источник лежит, а каждая точка с повторами ждёт до двух с половиной минут.

Обновить ретранслятор: скопировать `deploy/migros-relay/` и `migros_relay.py` в
`C:\projects\decimus-migros-relay` с теми же путями и выполнить там `docker compose -f deploy/migros-relay/compose.yaml up -d --build`.
