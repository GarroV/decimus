# Блок: domain

## Назначение

Единственная точка доступа к предметной области: чек-лист, зоны, состояние проверки, вызов движка. Ни один другой блок не открывает `inspection.json` и не запускает `audit.py`.

## API-контракт

Всё перечисленное импортируется из `src.domain`. Обязательные параметры — как в техплане; всё, что добавлено сверх него, необязательно и имеет значение по умолчанию.

```python
check_environment() -> Settings                               # проверка окружения на старте продукта
settings_for(chat_id: int) -> Settings         # окружение с методикой ТОЙ проверки (T169)
# `chat_id` ниже необязателен и меняет ровно одно: читать издание методики, по
# которому идёт проверка этого чата, а не то, что лежит в каталоге сейчас.
# Без него — действующая методика, как и раньше: так читают там, где проверки
# ещё нет (справочники до её начала, инструменты методики, замеры)
list_items(zone: str | None = None, kind: str | None = None, *,
           chat_id: int | None = None) -> list[ChecklistItem]
list_zones(*, chat_id: int | None = None) -> list[Zone]
get_item(code: str, *, chat_id: int | None = None) -> ChecklistItem
allowed_levels(code: str, *, chat_id: int | None = None) -> list[str]
checklist_version() -> str                     # издание ДЕЙСТВУЮЩЕЙ методики
get_state(chat_id: int) -> Inspection | None
kind_title(code: str, lang: str) -> str        # вид проверки словами (T152)
INSPECTION_KINDS                               # код вида → слово на каждом языке
# `kind` ниже — КОД из этой таблицы (`planned`), а не формулировка: формулировки
# переводятся и правятся, коды нет. Слово на языке отчёта блок кладёт в шапку для
# движка сам, `Inspection.kind` отдаёт код. Неизвестный код и незаведённый язык —
# `ValidationError` до вызова движка, а не молчаливый возврат исходника
start_inspection(chat_id: int, unit: str, kind: str, report_lang: str, *,
                 ui_lang: str = "ru", speech_lang: str = "ru", date: str | None = None,
                 city: str = "", partner: str = "", contact: str = "", auditor: str = "",
                 tenant: str = "default") -> Inspection
add_finding(chat_id: int, code: str, level: str, zone: str, text: str, *,
            comment: str = "", source: str = "") -> Finding   # source: SOURCE_COMMENT | SOURCE_PHOTO
edit_finding(chat_id: int, n: int, **fields: str) -> Finding   # code, level, zone, text, comment
drop_finding(chat_id: int, n: int) -> None
attach_photo(chat_id: int, n: int, file_id: str) -> None
score(chat_id: int) -> Score
sync_checklist_version(chat_id: int) -> Inspection   # перевести проверку на действующую методику
drop_inspection(chat_id: int) -> bool                # убрать проверку ЧАТА (T201, D080)
```

`drop_inspection` убирает только копию проверки в чате — файл состояния. Отданный отчёт и
строка проверки в истории точки остаются: запечатанное не правится и не удаляется, а
доступа к истории у этого блока нет вовсе. Зовётся ботом на «Убрать из чата», когда сданная
проверка мешает начать следующую (решение владельца D080). `False` — убирать было нечего, и
это законный исход, а не отказ: аудитор нажимает кнопку и второй раз.

Типы (`src/domain/models.py`):

| Тип | Поля | Формулировки |
|---|---|---|
| `ChecklistItem` | `code`, `kind`, `levels`, `zones`, `days` | `process(lang)`, `question(lang)`, `applies_to(zone)` |
| `Zone` | `code`, `title_ru`, `title_en`, `share_pct` | `title(lang)` |
| `Finding` | `n`, `code`, `level`, `zone`, `text`, `comment`, `photos`, `zone_unusual`, `source` | — |
| `Inspection` | `chat_id`, `unit`, `kind`, `date`, `ui_lang`, `speech_lang`, `report_lang`, `checklist_version`, `tenant`, `city`, `partner`, `contact`, `auditor`, `findings` | `finding(n)` |
| `Score` | `pct`, `grade`, `counts`, `deductions`, `by_zone` | `label(lang)` |
| `ZoneScore` | `code`, `share`, `counts`, `loss`, `left`, `zeroed` | `name(lang)` |

**Язык — параметр, поэтому формулировки отдаются методом с языком, а не полем.** Неизвестный язык — отказ, а не молчаливый откат на русский: иначе партнёр получит отчёт, в котором часть текста внезапно не на его языке, и заметит это только он.

`Score` строится разбором вывода `audit.py score --json`. Собственного расчёта в блоке нет и быть не может — это проверяется контрактом `engine-not-imported` в `lint-imports`.

Данные читаются из каталога `AUDIT_DATA_DIR`. Переменная не задана или каталог неполный — падение на старте с внятным сообщением.

## Что нужно знать потребителям блока

- **Отказы.** `ConfigError` — окружение непригодно, продукт не должен подниматься. `ValidationError` — значение отвергнуто до вызова движка. `InspectionNotStarted` — в чате нет начатой проверки (бот предлагает начать). `EngineError` — отказ движка, `message` дословно от него. `ChecklistVersionMismatch` — проверку считают не по той методике, которой она помечена (`recorded`, `current`); бот спрашивает аудитора, а не решает сам.
- **Проверка идёт по тому изданию методики, при котором её начали (T169).** Издание снимается снимком на старте (`STATE_DIR/methodology/<издание>/`), и по нему идёт всё: запись, правка, подсчёт, сборка отчёта. Публикация версии (D049) переставляет каталог `AUDIT_DATA_DIR` под живой проверкой — для идущей проверки это перестало быть событием, а следующая начинается уже на новом издании. Отказа на записи нет и быть не может: аудитор стоит на точке, починить методику оттуда он не в силах, а выезд не переигрывается.
- **Смесь изданий стоит не отказа, а испорченного отчёта, и поэтому закрыта на записи, а не на подсчёте.** Запись по пункту, снятому переизданием, движок не отвергает: `compute` берёт `cl.get(qid, {})` — и партнёру уходит строка с пустой формулировкой и сроком «немедленно» вместо настоящего. Воспроизведено (см. «Проверено фактически»).
- **Чтобы читать методику ТОЙ проверки, назовите чат:** `list_items(chat_id=…)`, `get_item(code, chat_id=…)`, `allowed_levels(code, chat_id=…)`, `list_zones(chat_id=…)`. Без этого аудитору можно предложить пункт, которого в его издании нет, — и запись по нему движок не примет. Кто зовёт движок сам (сборка отчёта), берёт окружение через `settings_for(chat_id)`.
- **`score` считает только по той методике, которой проверка помечена (T148).** Снимка нет и издание другое — `ChecklistVersionMismatch`, а не тихий пересчёт: оценка по новой методике под старой отметкой уезжает в базу выглядящей сравнимой с соседними, не будучи ею. Без снимка остаются проверки, заведённые до T169, и те, чья полка снимков не пережила переезд. Пустая отметка расхождением не считается — так помечены проверки, заведённые до версионирования.
- **Выход из расхождения один и он явный — `sync_checklist_version`.** Переводит проверку на действующую методику (снимая заодно её снимок) и оставляет след в ней самой (`domain.version_history`: `from`, `to`, `at`) плюс строку в журнал процесса. Отдельным вызовом, а не поведением подсчёта: перевод меняет то, чем проверка измеряется, и это решение человека. Спросить обязан бот — задача блоку `bot`.
- **Текст отказов движка написан для командной строки.** Дубль пары советует «`audit.py photo 1 --add ...`». Аудитору такое показывать нельзя — переформулировать при показе обязан бот (задачи T055, T056).
- **`counts` содержит и `D0`** — информационные записи (замеры, настройки печи, фото продукта). Они не влияют на процент, но в отчёте нужны. Перечня классов в коде блока нет: список приходит от движка.
- **`source`** — откуда взялась запись (решение D044): `SOURCE_COMMENT` — со слов аудитора, `SOURCE_PHOTO` — распознано по кадру, пусто — источник не записан (проверки, заведённые до D044; выдавать их за слова аудитора нельзя). Ставится при фиксации и правкой не меняется: `edit_finding(source=…)` — отказ. В поля движка, которые печатаются партнёру, источник не попадает.
- **`zone_unusual`** — зона не из списка пункта. Движок такую запись пропускает и лишь помечает; бот показывает пометку аудитору.
- **Служебные пункты (`kind` = `aggregate`, `info`) блок не прячет.** Отсеивать их — работа разбора (`docs/03-recording-rules.md`, правило 8).
- **`start_inspection` не защищает от перезаписи начатой проверки** — движок затирает состояние целиком и молча. Спросить «продолжить или начать заново» обязан бот (задача T052).
- **Формулировка, начинающаяся с дефиса, доезжает целой:** движку всё передаётся видом `--ключ=значение`.
- **Идентификатор кадра с запятой отклоняется**: движок режет список фотографий по запятой, и один кадр молча превратился бы в два несуществующих.

## Где что лежит

- **Состояние** — `STATE_DIR/chat_<chat_id>/inspection.json`, папка на чат (решение D007). Рядом движок оставляет `inspection.json.lock`.
- **Поля, которых у движка нет**, — в том же файле под ключом `domain`: `schema`, `chat_id`, `tenant`, `checklist_version`, `ui_lang`, `speech_lang`, `sources` (номер записи → источник). Записываются под той же блокировкой, что берёт движок. Проверка должна быть одним объектом: при переезде на базу иначе теряется половина её сведений.
- **Язык отчёта — в шапке движка (`meta.lang`)**, потому что оттуда его берёт сборка отчёта. Второй копии у блока нет намеренно: две копии разошлись бы.
- **Снимки изданий методики** — `STATE_DIR/methodology/<издание>/`: копия файлов методики плюс `checklist_version.txt`. Каталог назван изданием, а издание выведено из содержимого (D050), поэтому две проверки на одном издании делят один снимок, а подложенный каталог не сходится отпечатком и в дело не идёт. Старые снимки не удаляются: по ним считаются идущие проверки, а после них — объяснимость отчёта (D050). Размер снимка — размер методики (боевая на 05.09.2026 — 192 КБ).
- **След перевода версии** — `domain.version_history` в том же файле: список записей `{from, to, at}`. В проверке, а не в логах стенда: отвечать «по какой методике это посчитали» придётся тогда, когда логов уже не будет, а проверка будет — она к тому времени уедет в базу целиком.
- **Версия методики** — составной идентификатор `имя-дата-отпечаток` (`imf-2026-09-01-3f5a91b2c7d0`, решение D050). Имя и дату управляющая компания кладёт в `checklist_version.txt` строкой «имя набора плюс дата»; отпечаток — 12 знаков sha256 по всем файлам методики, включая маршрут обхода. Файла нет — версия остаётся одним отпечатком (`local-…`). Файл есть, но не разбирается — отказ на старте: молчаливый откат на `local-…` потерял бы дату издания навсегда.
- **Порядок обхода** — `route.csv` в каталоге методики (`entity,code,order`), файл необязательный. Отдельным файлом, а не колонкой в `checklist.csv` и `zones.csv`, потому что `engine/manage.py` перезаписывает оба фиксированным списком колонок и стёр бы маршрут молча.
- **Движку передаются две переменные**: `INSPECTION_FILE` — путь к состоянию, `CHECKLIST_DIR` — каталог методики. Вторая обязательна: без неё движок берёт данные из своей копии рядом со скриптом или из форка `checklist_data/` в рабочей папке.

- [x] Состояние хранится в папке на чат, запись атомарна, одновременная запись двух кадров альбома не теряет запись и не портит файл (тест обязателен).

- [x] `score` возвращает то же, что печатает `audit.py score`, — сверено тестом на данных `examples/`.
- [x] Наличие форка `checklist_data/` в рабочем каталоге обнаруживается и приводит к отказу запуска.
- [x] Три языковых поля (интерфейс, речь аудитора, отчёт) хранятся раздельно; версия чек-листа записана в проверку.
- [x] `mypy --strict` чист, `lint-imports` зелёный.
- [x] Версия методики составная (имя, дата, отпечаток): правка данных под прежним именем даёт другой идентификатор, а проверки, заведённые до этого, читаются по-прежнему.

- [x] Проверка не может собраться из двух изданий методики: издание снимается на старте, запись и подсчёт идут по нему, переиздание посреди выезда не отказывает аудитору и не двигает цифру (T169).
- [x] У записи хранится источник — со слов аудитора или распознавание по кадру; источник живёт в самой проверке и доезжает до базы (проверено сливом в Postgres).

## Проверено фактически

Хроника прогонов снята — она в `git log` точнее и бесплатно. Здесь остаётся то, что держит контракт:

- **Набор идёт без боевых данных** (симлинки `data`/`examples` убраны): 1204 passed, 195 skipped — пропускается ровно то, что боевых данных требует по существу. **Изоляция от боевой методики доказана подменой:** на изменённой копии каталога 1175 passed, а поднятая ставка `D1` красит боевой якорь — связь там, где она нужна, не перерезана.
- **T169 воспроизведён до починки и не воспроизводится после** (боевая методика, её копия): переиздание посреди выезда оставляет письмо по идущей проверке байт в байт прежним; та же проверка по действующей методике дала бы на 1 п.п. меньше — этот пункт и есть то, что держит снимок. Цена снимка замерена: первый — 1,6 мс, подстановка каталога на вызов движка — 0,13 мс при `score` в 26 мс.
- **Нумерация записей проверена запуском движка** (T221, T305): записи 1-3 → снятие 3 и 2 → следующая получает 4, после снятия всех — 5. В состоянии БЕЗ ключа `seq` — то же самое: счётчик выводится при чтении (`raise_seq`, T295) и уносится в файл первой же меняющей командой. Довод «номер освобождается» опровергнут запуском, а не рассуждением.
- **Испорченная методика отвергается так же, как движком** (T302): нечисловой срок и дубль кода пункта. Тесты написаны до кода и падали на прежней реализации обоими случаями; боевая методика читается по-прежнему — 136 пунктов, 10 зон.
- **Каждый новый тест прогнан на испорченной копии**, откат — из копии, снятой до порчи, md5 сверен. Две подмены сначала не покраснели, и оба теста были слабыми, а не подмены безвредными, — оба переписаны.

## Решения, принятые в блоке

| Решение | Почему |
|---|---|
| Снимок адресуется содержимым: имя каталога — составной идентификатор издания (D050) | Даром получаются три свойства, каждое из которых иначе пришлось бы городить: два чата на одном издании делят снимок; повторный снимок — не работа, а проверка, что он на месте; подложенный или неполный каталог не сходится отпечатком и в дело не идёт. Полнота снимка отдельно не проверяется намеренно — пропавший файл в отпечаток не входит, и такой каталог отвергается тем же сравнением. **С T236 сама сверка живёт в `version.edition_of`**, а не здесь: тот же вопрос задаёт хранилище версий MCP (`mcp.letters.pinned`), и второй ответ на него расходился бы с этим молча — ровно так дефект и был найден. Оттуда же MCP читает и эту полку: издания, снятые на выезде, в его хранилище не попадают никогда |
| Отказ на подсчёте (T148) сохранён, а не снят | Он перестал быть общим случаем, но остался единственным честным ответом там, где издание проверки взять негде: проверки, заведённые до T169, и потерянная полка. Снять его значило бы вернуть ровно то, что T148 закрывал, — оценку по новой методике под старой отметкой |
| Мультиарендность — поле `tenant` в состоянии, но не в раскладке папок | Решение D005: форма данных сейчас, функции потом. Папки по арендаторам без функций мультиарендности были бы структурой ради структуры, а поле задним числом в готовые проверки не впишешь |
| Источник записи — в состоянии проверки, а не в заметках бота | D044 требует хранить источник у записи, а заметки бота (`bot.json`) обнуляются на старте следующей проверки того же чата: ответить «чья это была формулировка» через месяц было бы нечем. В базе колонка `findings.source` уже ждала этого поля, а `db.push` читает его через `getattr` — слив источника заработал без единой правки блока `db` (проверено сливом в Postgres) |
| Источник ставится при фиксации, а не отдельным вызовом | Оба пути бота (комментарий и «Разобрать») знают источник в момент фиксации. Отдельный вызов следом означал бы окно, в котором запись уже есть, а источника у неё нет, — и такая запись выглядит как слова аудитора |
| Отпечаток версии считается по всем файлам методики, включая маршрут, и имя файла входит в хеш | «Любая правка чек-листа — новая версия» (D050) значит любая: маршрут обхода — тоже методика. Имя файла в хеше нужно, чтобы перенос строки из одного файла методики в другой менял отпечаток |
| Тесты идут по синтетической методике, боевая — только там, где она и есть предмет | Правка данных управляющей компанией красила нашу сборку: применение новой карты слов роняло тесты, и это требовало правки тестов тем же движением. Исключений ровно три вида, и каждое обязано себя объяснить: боевой якорь 97.5 %/97 % на `examples/`, полнота каталога управляющей компании, живой замер быстрого пути. Их метка — `requires_data`, их фикстуры — `live_data_env`/`live_data_copy` |
| Методика передаётся движку в тестах ЯВНО, молчаливого варианта нет | Без `CHECKLIST_DIR` движок берёт данные из своей копии рядом со скриптом, то есть из боевого `data/`. Умолчание «если не задано — синтетика» проверено на худшем случае: боевой якорь, посчитанный по синтетическому набору, СОШЁЛСЯ бы — ставки и доли зон совпадают — и перестал бы что-либо стеречь, не покраснев ни разу. Поэтому `data_dir=DATA` в тесте пишется руками |
| В синтетическом наборе настоящие только идентификаторы | Коды пунктов и зон, классы, ставки вычетов и пороги букв были в репозитории и до него — ими продукт связывает сущности, они стоят в контрактах блоков и в докстроках продукта. Формулировки, названия зон, критерии, подсказки карты — выдуманы: именно их и считал утечкой счёт T146 (формулировки вопросов, названия зон, строки карты). Структуру боевого набора (полный список пунктов с их классами, зонами и сроками) в git не переносил намеренно: это была бы новая утечка вместо старой |
| Расхождение версий при подсчёте — отказ, а не пересчёт и не тихая перестановка отметки | Третьего честного варианта нет. Пересчитать по прежней методике блок не может: её данных в `AUDIT_DATA_DIR` больше нет, а снимок версии лежит в хранилище блока `mcp`, и лезть туда домену — обратный импорт слоёв. Посчитать по новой под старой отметкой запрещает D033: проверка не меняется задним числом. Молча переставить отметку — тот же D033, только выглядящий намеренным: проверка сама переехала бы на другую методику. Остаётся отказ, а решение — человеку. Побочная польза: `publish_checklist_version` уже отвечает «inspections already scored stay on their own version and are not recalculated» — до этой правки это было неправдой для проверки, посчитанной после публикации |
| Перевод проверки на действующую методику есть, но отдельным вызовом (`sync_checklist_version`) | Без него отказ был бы тупиком: аудитор в поле не может ни досчитать, ни отменить публикацию. Вызов оставляет след в самой проверке (`from`, `to`, `at`), поэтому перевод виден потом, а не растворяется. Отдельным вызовом — потому что перевод меняет то, чем проверка измеряется: такое решение принимает человек, и спросить его обязан бот |
| Сверка стоит на подсчёте, а не на каждой записи | Подсчёт — точка невозврата: его цифра уходит партнёру и в базу. Сверка на `add_finding` заперла бы аудитора посреди выезда на первой же записи после публикации, а починить он оттуда ничего не может. Остаточный риск назван прямо ниже, в «что осталось» |
| Кеша методики нет | Каталог подкладывают томом снаружи; кеш означал бы работу по старой методике до перезапуска. Разбор 136 строк занимает доли миллисекунды |
| Проверка мёртвого кода сканирует `tests/` вместе с `src/` | Контракт блока сегодня зовут только тесты — `bot`, `recognize` и `report` появятся позже. Иначе проверку пришлось бы глушить списком исключений на весь контракт, и она перестала бы что-либо ловить. В таком виде она сразу нашла настоящий мёртвый код (`Finding.is_violation`), и он удалён |
| `checklist.Store` и `letters.Papers` не сводятся в один тип (T213) | Общего у них только два пути из тех же двух переменных окружения; предмет разный, и сведение было бы регрессом сразу по трём счётам. **Первое: `Store` несёт право, `Papers` не несёт никакого.** `Store` собирается ровно в одном месте — `_checklist_for` в `src/mcp/server.py`, — и арендатору без права на методику выдаётся `None` вместо него: проверено запуском, «с правом» отдаёт `Store(...)`, «без права» отдаёт `None`. `Papers` собирается в `letters.sources()` из окружения, без кода арендатора вовсе, и на пустом окружении честно отдаёт три `None`. Один тип на оба места означал бы, что пара, которой публикуют версии, собирается из переменных кем угодно. **Второе: обязательность полей — это смысл, а не стиль.** У `Store` оба поля обязательны (`Store()` падает на `root` и `live`): публиковать некуда без хранилища, а `live` нужен, чтобы ответить, увидит ли движок публикацию (`os.path.realpath(store.live)` против указателя `current`). У `Papers` все три необязательны намеренно — процесс может стоять без любого из каталогов, и пересборка тогда отказывает, называя переменную. И `live` в них отвечает на разные вопросы: у `Store` — «читает ли движок это сейчас», у `Papers` — «это ли и есть нужное издание» (`edition_of(papers.live, DATA_FILES)`). **Третье: `shelf` в `Store` не нужен и вреден.** Полка (`STATE_DIR/methodology/`) принадлежит идущим проверкам, и писать туда MCP не имеет права ничем, а `Store.root` — каталог, в который он как раз пишет и в котором держит указатель. Один тип свёл бы «пишем сюда» и «сюда нельзя писать никогда» в один объект. **А то, что действительно могло разойтись, уже сведено:** устройство хранилища и сторож имени версии живут в `checklist.py` и оттуда импортируются в `letters.py` (`VERSIONS_DIR`, `_check_version`), формула самого идентификатора и список файлов методики — в `src/domain` (`compose`, `edition_of`, `DATA_FILES`, `SHELF_DIR`), это сделали T236 и T243. **И канонического места в `domain` для общего типа быть не может:** зонд `from ..mcp.checklist import Store` в `src/domain` роняет контракт границ — `src.domain is not allowed to import src.mcp`; зонд удалён |

## Что осталось соседним блокам

- **Довод про освобождающийся номер остался в контракте блока `bot`** (`docs/furca/blocks/bot.md`, строка Definition of Done: «номер освобождается, и оставленное досталось бы чужой записи»). Опровергнут запуском — правка чужого файла, не моя.
- **`validate` не ловит нарушение без срока — блоку `engine-fix`.** У пункта вида `violation` с классами `D1`/`D2` можно оставить `days` пустым, сверка пропустит, а партнёр прочтёт «устранить немедленно». На боевой методике не стреляет: без срока там три строки, и все три информационные (`D0`). Чинить отказом, а не подстановкой умолчания: подстановка молча решит за управляющей компанией, каким будет предписание партнёру.
- **Доля существующей зоны и её переименование не настраиваются ничем, кроме файла — блоку `mcp`.** Зону завести можно, настроить нельзя: остаётся уравнять доли всех зон. Подробности и довод — `docs/10-checklist-configuration.md`.
- **Порядок обхода (`route.csv`) не знает ни CLI, ни MCP — блоку `mcp`.** Разбор уже строгий, на цифру оценки файл не влияет вовсе; самое дешёвое из несделанного.
- **Имена переменных окружения и правило приведения пути в `src/mcp` написаны по второму разу — блоку `mcp`** (находка T213; сводить их отсюда нельзя — `src.domain` чужой блок не импортирует, это держит контракт границ).
- **Боевая методика всё ещё цитируется в доке и в докстроках продукта** — больше всего `docs/02-domain.md`, плюс `docs/06-mvp-bot.md` и `docs/furca/blocks/bot.md`. Репозиторий публичный.
- **Расхождение версий надо показать аудитору и спросить** — блоку `bot`: `score` отдаёт `ChecklistVersionMismatch` с полями `recorded` и `current`, человеческий текст и выбор за ботом.
- **Записи, добавленные после переиздания методики, сверкой не ловятся:** `add_finding` идёт через движок и проверяется уже новой методикой, отметка в проверке остаётся прежней до подсчёта.
- **Тексты отказов движка не годятся для показа аудитору** — блоку `bot`, T055 и T056. **`audit.py init` затирает начатую проверку молча** — защита на боте, T052.
- **`--lang en` даёт смешанный отчёт** (текст находки, пиццерия и аудитор остаются как введены). Ограничение движка, здесь не лечится.
