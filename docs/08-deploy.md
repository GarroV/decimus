[`docker-compose.prod.yml`](../docker-compose.prod.yml), почему она устроена
так — в её шапке.

## 8.1. Подключение к прокси — надстройка площадки

Приложение слушает сеть контейнера только по явному ключу
`WEB_LISTEN_NETWORK=1` / `MCP_LISTEN_NETWORK=1` (без него — отказ на старте,
правило петли D100 для MUSPELHEIM не отменено). Прод-надстройка ставит ключи
сама. Сеть `edge-decimus` подключает надстройка площадки: канон —
`vps-infra/projects/decimus/compose.edge.yaml`, на сервере —
`/srv/decimus/compose.edge.yaml`. По сути:

```yaml
services:
  web:
    networks: {default: {}, edge: {aliases: [decimus-web]}}
  mcp:
    networks: {default: {}, edge: {aliases: [decimus-mcp]}}
networks:
  edge: {name: edge-decimus, external: true}
```

Цели Caddy — псевдонимы в `edge-decimus`: `decimus-web:8267` и `decimus-mcp:8265`. Порты на хосте остаются
только на `127.0.0.1` (`WEB_HOST_PORT` 8268, `MCP_HOST_PORT` 8266) — для смоука
с сервера. `ports: !reset []` в надстройке площадки тоже допустим, но тогда
смоук скрипта ниже не найдёт порт.

**`WEB_TRUSTED_PROXIES=1` обязателен:** перед админкой одно своё звено —
Caddy. Без ключа все приходят с адреса Caddy, и ограничитель перебора пароля
становится общим на всех (T325). Прод-надстройка ставит `1` сама, если в `.env`
площадки значения нет.

**`MCP_TRUSTED_PROXIES` и `MCP_TRUSTED_PROXY_ADDR` — адрес клиента в журнале действий
(D462).** Сервер MCP стоит за тем же Caddy: прод-надстройка ставит `1` звено и берёт подсеть
из `WEB_TRUSTED_PROXY_ADDR`, если свою не задали. Верят `X-Forwarded-For` только от этого
звена и считают с конца цепочки (`src/domain/client_ip.py`); без обоих в журнал идёт адрес
соединения, то есть Caddy. Проверить на проде: вызов изменяющего инструмента админом — адрес в
«Журнал» → «Действия» должен быть адресом клиента, а не Caddy.

**`WEB_TRUSTED_PROXY_ADDR` — от кого верить заголовкам звена** (F-038 аудита
12.10). Только запросам с этого адреса или подсети админка верит
`X-Forwarded-For/-Proto/-Host`; заголовки остальных соседей (процесс на машине
через опубликованный на петле порт, соседний контейнер) вырезаются
(`src/web/proxy.py: guard_forwarded`). На проде — подсеть сети `edge-decimus`,
из которой приходит Caddy; посмотреть на сервере:

```bash
docker network inspect edge-decimus --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

и вписать в окружение площадки строкой `WEB_TRUSTED_PROXY_ADDR=<подсеть>`.
**Переменная обязательна:** без неё прод-надстройка не собирается
(`${WEB_TRUSTED_PROXY_ADDR:?…}` — любая команда `docker compose` с ней падает с
этой причиной); допускающего умолчания нет. Админка, запущенная в сети
контейнера без переменной в обход надстройки, не верит никому — счётчик
перебора общий, формы за HTTPS получают 403 заслона происхождения — и пишет
предупреждение при старте. `*` («любой сосед») принимается только явно и тоже
с предупреждением. Подсеть сети меняется,
только если сеть пересоздать; тогда значение правится тем же движением.

**`WEB_SECRET_KEY` обязателен:** админка, слушающая сеть контейнера, без ключа
подписи не поднимается (F-008) — временный ключ выбрасывал бы всех при каждой
выкатке.

**`SECRETS_KEY` — ключ шифрования секретов в базе (D491).** Им зашифрованы ключи сервисов
(модель, Pointer, iSpring; D576), которые главный админ вставляет на вкладке «Администрирование → Ключи и API» (пару приложения маркетплейса Dodo IS — на вкладке «Администрирование → Dodo IS», первым блоком); в базу он не попадает. 32 случайных
байта в base64; один и тот же у веба, бота и обхода (все читают ключ модели из базы). Без него
сохранить ключ на экране нельзя, а уже сохранённый не открывается — тогда работает
`OPENAI_API_KEY`. Потерянный `SECRETS_KEY` значит «ключи на экране вставить заново», больше ничего; значения из `.env` (`OPENAI_API_KEY`, `POINTER_API_KEY`, `ISPRING_CLIENT_ID`/`ISPRING_CLIENT_SECRET`, `DODOIS_CLIENT_ID`/`DODOIS_CLIENT_SECRET`) остаются запасными.
Сгенерировать: `python3 -c "import secrets,base64;print(base64.b64encode(secrets.token_bytes(32)).decode())"`
и положить в `.env` площадки значением `SECRETS_KEY=` (значение в репозиторий не попадает).

**Оповещения владельцу о сбоях подключений (D641)** идут через канал FURCA теми же переменными,
что тревога агрегаторов (D438): `FURCA_NOTIFY_URL` (адрес службы канала, доступный из контейнера
бота) и `FURCA_SECRET`; имена и пояснения — в `.env.example`. Значение секрета канала лежит на
машине владельца (`~/.claude/furca/channel.env`); в репозиторий не попадает. Не заданы — оповещения
выключены (одна строка в журнале бота на старте и строка «Оповещения выключены» во вкладке
«Администрирование → Ключи и API»). В демо не уходят никогда, даже при заданных переменных.
Входы Dodo IS нескольких стран, сменивших состояние за один заход, приходят одним сообщением
со списком стран (D678), а не по сообщению на страну.

**`WEB_HSTS=1` — только когда админка снаружи открывается исключительно по
HTTPS.** Ключ велит слать `Strict-Transport-Security: max-age=31536000` (#489,
[30-web-screen-rules](30-web-screen-rules.md#заголовки-безопасности-489)). Браузер помнит
заголовок год и всё это время не откроет имя админки по HTTP, поэтому на стенде
без сертификата (петля, Funnel по HTTP, проверка по IP) ключ не ставится. По
умолчанию выключен; любое значение, кроме пусто, `0` и `1`, — отказ на старте.
Включение на проде — решение владельца при раскатке, само не включается.

## 8.3. Подъём и обновление — одна команда

```bash
cd /srv/decimus
DECIMUS_OVERLAYS=/srv/decimus/compose.edge.yaml scripts/prod-update.sh
```

Без `DECIMUS_OVERLAYS` скрипт сам подключает `compose.edge.yaml` из каталога репозитория
и пишет об этом: забытая надстройка роняла прод в 502 (`web` выпадал из сети прокси,
21.10.2026). Пустое значение (`DECIMUS_OVERLAYS=`) — осознанный подъём без неё.

Выкатка идёт одна за раз (#729): скрипт берёт замок `.git/prod-update.lock`
(`flock`), вторая ждёт первую до `DEPLOY_LOCK_WAIT_S` секунд (по умолчанию 900)
и иначе отказывает. Накат миграций вдобавок держит `pg_advisory_lock` — два
наката разом не повторят одну миграцию, откуда бы их ни запустили.

[`scripts/prod-update.sh`](../scripts/prod-update.sh) делает по порядку:
`git pull --ff-only` → сверка источника (`scripts/verify-source.sh`: HEAD = `main` на GitHub, дерево чистое, [§8.23](35-platform-services.md)) → проверка утечки методики (`tools/methodology_leak.py data --tracked-only`, D517: цитата останавливает раскатку, обход `LEAK_CHECK=0`) → сборка с `BUILD_SHA` (вместе с профилем `backup`) →
база с ожиданием здоровья →
накат миграций → `up -d --wait` → смоук (`/login` 200, MCP без токена 401,
админка не пишет в `state`, сервис обхода пишет, `/tg/walk` 200 — [§8.14](35-platform-services.md)).
Один и тот же порядок для первого подъёма и для каждого обновления: накат
идемпотентен, корзина заводится с `--ignore-existing`. Первый подъём с переносом
базы — порядок в [§8.4](history/deploy-muspelheim-2026.md).

Руками — тем же набором файлов:

```bash
dc() { docker compose -f docker-compose.yml -f docker-compose.prod.yml -f "$DECIMUS_OVERLAYS" "$@"; }
dc ps; dc logs -f bot
```

**Никогда `down -v`** — это снос базы, хранилища и состояния.

### 8.3.1. Образ идёт не от root — разовый `chown` томов (F-003, аудит 12.10)

Бот, MCP, веб и обход работают от пользователя `app` (uid/gid `10001`,
`Dockerfile`), у сервисов отобраны все привилегии ядра и запрещено их
повышение (`cap_drop: [ALL]`, `no-new-privileges`, `docker-compose.yml`).
Новый пустой том наследует владельца каталога образа и поднимается сам. Тома,
созданные до этого изменения, принадлежат root (`state`, `frames`,
`methodology`) — **до первой выкатки образа с `USER`** их владельца меняют
один раз, иначе сервисы стартуют и падают на записи в `/app/state`:

```bash
# на VPS, ДО scripts/prod-update.sh; прежние контейнеры от root это не ломает
docker run --rm \
  -v decimus_state:/state -v decimus_frames:/frames -v decimus_methodology:/methodology \
  alpine chown -R 10001:10001 /state /frames /methodology
```

Имена томов — `<имя проекта>_<том>` (`docker volume ls | grep decimus`).
Каталог бэкапа состояния (`BACKUP_DIR`, сервис `state-backup`) — каталог хоста:
он должен быть записываем для uid 10001 (`chown 10001:10001 <каталог>`), иначе
бэкап не сможет писать архив. Методика `/app/data` читается всеми (`o+r`), её
менять не надо. Проверка после выкатки: `docker exec decimus-bot-1 id -u`
отвечает `10001`, а смоук `prod-update.sh` (запись обхода в `state`) зелёный.

### 8.3.2. Потолки ресурсов и сроки базы (F-128, F-119, аудит 12.10)

**Память и процессы.** Каждому сервису в `docker-compose.yml` задан
страховочный потолок — не рабочий лимит, а предел, на котором взбесившийся
процесс убивается docker-ом (`restart: unless-stopped` поднимает его заново), а
не уносит хост. Лимит по ЦП не ставится намеренно: он молча душит задержку.

| Сервис | `mem_limit` | `pids_limit` |
|---|---|---|
| `web`, `walk`, `demo` (якорь `x-stand`) | 768m | 512 |
| `bot` (ffmpeg, PDF, расшифровка) | 1g | 512 |
| `mcp`, `migrate`, `demo-seed`, `state-backup` | 512m | 512 |
| `db` | 1g | 1024 |
| `storage` (мок для смоука) | 512m | 512 |
| `tunnel`, `link`, `web-link` | 256m | 256 |

Площадка общая (11 ГиБ на несколько проектов), поэтому потолок — 3–5 рабочих
пиков (прод 12.10: web 221, walk 210, bot 187, mcp 35, db 46 МиБ), а не «сколько
не жалко». Сверять с `docker stats`; пик подошёл к половине — поднять. Тест: `tests/test_container_hardening.py`.
Одновременных сборок PDF в процессе не больше трёх (`MAX_CONCURRENT_BUILDS`,
`src/report/engine.py`); лишняя ждёт очереди до `QUEUE_WAIT_SEC`, потом отказ
«сборка занята».

**Сроки базы.** Соединения роли приложения (пул `src/db/pool.py` и прямые
подключения слива, рейтингов, агрегаторов, OAuth) получают при старте
`statement_timeout` 30 с, `lock_timeout` 10 с и `connect_timeout` 10 с
(`src/db/timeouts.py`); пакетные загрузки рейтингов (`ratings_sync`,
`agg_store`, `ratings/importer`) — `statement_timeout` 300 с
(`DB_BATCH_STATEMENT_TIMEOUT_S`), остальные сроки те же. Не затронуты: накат миграций, подключения владельца
схемы и администратора истории вне пула, `tools/`; предписания УК держат свои
5 с / 15 с. Настройка: `DB_STATEMENT_TIMEOUT_S`, `DB_LOCK_TIMEOUT_S`, `DB_BATCH_STATEMENT_TIMEOUT_S` (секунды;
`0` — не ставить). Если `DATABASE_URL` поведёт через пулер, не принимающий
стартовый параметр `options` (Supabase), — обе переменные в `0`.

**Потолки входа (аудит 12.10).** Голосовое: до 25 МБ и 10 минут
(`MAX_AUDIO_BYTES`, `MAX_AUDIO_SECONDS`, `src/recognize/transcribe.py`, F-123) —
больше отказ словами «попросите написать текстом» до ffmpeg и платной
расшифровки. Ответ агрегатора: тело до 20 МБ и 200 с на запрос со всеми
повторами (`BODY_MAX_BYTES`, `DEADLINE_SEC`, `src/ratings/aggregators/base.py`,
F-126). Кадров в одном поиске пункта — 20 (`docs/13-walk-mini-app.md`), строк в
CSV рейтингов — 500 000 (`docs/15-ratings.md`).

## Откат

Автоматического отката нет: `scripts/prod-update.sh` только едет вперёд, и `git checkout` старого коммита его не вернёт —
скрипт сверяет, что собирается ровно `main` с GitHub. Откат — это **возврат прежних образов приложений при неизменной базе**.
Так делалось в раскатках 30.10–01.11.2026 (журнал — [`history/deploy-rollouts-2026.md`](history/deploy-rollouts-2026.md)):

1. **До раскатки** снять резерв в `~/.local/state/decimus/rollbacks/<имя-раскатки>/` на сервере: дамп базы (проверенный
   `pg_restore --list`), защищённая копия `.env`, прежние образы `bot`, `web`, `walk`, `mcp` под неизменяемыми тегами
   `decimus-rollback-<имя>-<служба>:<дата>`, файл `rollback.yaml` (подмена образов этими тегами) и `manifest.json` (исходные ID образов).
   Скрипта, который делает это сам, пока нет — шаг ручной.
2. **Вернуть приложения**, оставив базу и состояние как есть:

   ```bash
   cd /srv/decimus
   docker compose -f docker-compose.yml -f docker-compose.prod.yml -f compose.edge.yaml \
     -f "$HOME/.local/state/decimus/rollbacks/<имя-раскатки>/rollback.yaml" \
     up -d --no-deps --no-build --pull never bot web walk mcp
   ```

3. **Проверить**: состояние всех служб, `BUILD_SHA` четырёх приложений (должен быть прежний), внешний смоук
   (раздел «Проверка после раскатки»).

**Дамп поверх рабочей базы не восстанавливают**: записи, сделанные людьми после раскатки, пропали бы. Миграции откатом не
отменяются; поэтому они пишутся совместимыми со старым кодом (новые поля допускают пустое значение). Если миграция несовместима —
это решение владельца, а не шаг скрипта. Откат с флагом, который старый код не знает, возвращает старое поведение (так было с
паузой экшн-планов 01.11.2026) — учитывать до отката. Восстановление базы из бэкапа — [`33-backup-restore.md`](33-backup-restore.md), шаги — этап 2.

## 4.5.1. Накат встал на отпечатке — как чинится (T299, #258)

Случай не выдуманный: он случился на площадке. 06.09 миграции `0001`–`0011`
применились; 09.09 сплошная правка комментариев по репозиторию задела
**применённый** файл `0007_model_suggestion.sql` (SQL не тронут, три строки
комментария), отпечаток разошёлся, и накат с тех пор отказывал на седьмой
миграции. Следствие: `0012` и `0013` на площадку не попали, хотя код, которому
они нужны, там стоял и работал — карта синонимов формулировок жила без своей
схемы.

**Чинится в репозитории, а не на площадке.** Применённый файл возвращён к тому
виду, в котором он применён (отпечаток `e0a40b638c9d…` — тот же, что стоит в
`schema_migrations` площадки), и на это заведена проверка
`tests/test_db_migrations_frozen.py`: любая правка закоммиченной миграции
красит прогон локально. Подгонять отпечаток в базе руками нельзя — это ровно
тот молчаливый обход, ради которого отпечатки и считаются.

**Порядок на площадке** (раскатка: только по явному «да» владельца и в ночное
окно). Все команды — из `C:\projects\decimus`:

```powershell
# 1. Что стоит сейчас — записать ДО, чтобы было с чем сравнить
docker compose exec -T db psql -U dodo_audit -d dodo_audit_service `
  -c "select filename, left(checksum,12) as cs, applied_at from schema_migrations order by filename"

# 2. Свежий дамп на всякий случай (ночной снимается в 03:30 сам, см. §4.8)
docker exec decimus-infra-db-1 pg_dumpall -U dodo_audit --clean --if-exists > C:\backups\decimus-pre-0012.sql

# 3. Забрать код и пересобрать образ: миграции запечены в образ, а не смонтированы,
#    и без пересборки внутри контейнера останется прежний, изменённый 0007
git pull
$env:BUILD_SHA=(git rev-parse --short HEAD)   # без него образ ответит «сборка: неизвестна»
docker compose build

# 4. Поднять с новым образом. Звено само НЕ пересоздаётся: оно в профиле funnel,
#    и обычный `up -d` оставит его в сетевом пространстве удалённого сервера (#304, §4.6)
docker compose up -d
docker compose --profile funnel up -d --force-recreate mcp link

# 5. Накатить
docker compose run --rm --no-deps migrate
```

Ожидаемый ответ шага 5 — ровно две строки в списке применённых:

```
Применены миграции: 0012_phrase_aliases.sql, 0013_phrase_alias_curation.sql
```

**Проверить фактом, а не по коду:**

```powershell
# 13 строк, и отпечатки 0001–0011 те же, что в записи из шага 1
docker compose exec -T db psql -U dodo_audit -d dodo_audit_service `
  -c "select count(*) from schema_migrations"

# повторный накат обязан быть пустым
docker compose run --rm --no-deps migrate    # «Схема уже актуальна, накатывать нечего»
```

Если шаг 5 снова отказал на отпечатке — значит на площадку уехал не тот код:
сверять надо не «мы же починили», а `git log -1` в каталоге проекта и дату
сборки образа.
