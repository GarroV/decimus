# Электронный план исправлений — спека

Решения: D612 (план в вебе, строки = нарушения), D613 (отсчёт срока), D614
(напоминания), D617 (срок 10 дней из методики), D618 (план шаблонный и
электронный, выполнение подтверждает девелопер), D619 и D621 (штамп и
геометка на фото, текст штампа). Макет, принятый владельцем 22.10.2026:
https://garva-pages.pages.dev/decimus-plan/

## Что это

Партнёр отвечает на проверку УК не файлом «как получится», а планом по каждой
строке: что сделает, кто отвечает, к какому сроку. Потом он отмечает сделанное
с фото, а девелопер страны подтверждает или возвращает. Всё время план живёт в
системе в электронном виде; файл — только удобный способ заполнить его вне
сайта.

Вопрос экрана: **«что по этой проверке исправлено, а что нет, и кто сейчас
должен действовать»**.

## Кто что делает

| Кто | Что |
|---|---|
| Партнёр (пространство страны) | заполняет строки, отправляет на согласование, отмечает выполнение с фото, просит перенос срока |
| Девелопер страны и админы УК | принимают или возвращают план, подтверждают или возвращают строку, решают перенос |
| Система | заводит план, ставит сроки, шлёт напоминания, считает просрочку |

«Девелопер страны» сейчас — имя строкой в карточке страны (D508), не учётка.
Чтобы уведомление пришло человеку, в карточке страны появляется выбор
девелопера из учёток УК с ролью `developer`. Пока он не выбран, уведомления
по стране получают админы УК. Подтверждать строки может любой с правом УК на
экшн-планы — так же, как сейчас принимать файл.

## Путь

1. **Запрос.** Как сейчас: сам при подтверждении проверки УК с D2/D3 (D272)
   или кнопкой УК. При создании записывается дата создания и спрашивается, от
   какой даты считать срок (D613); по умолчанию — дата создания.
   Черновик письма партнёру (кнопка «Письмо») предлагает начать отсчёт с
   сегодняшнего дня одной галочкой: отправка письма — это и есть начало срока.
2. **Заполнение.** Строки заводятся сразу — все нарушения проверки с классом
   D1–D3, тяжёлые сверху. Рекомендации в план не входят. Партнёр заполняет
   «что сделаем», «кто отвечает», по желанию «почему так вышло» и может
   поставить срок строки раньше положенного. Заполнять можно на экране или
   файлом (ниже). «Отправить на согласование» доступно, когда у каждой строки
   есть мера и ответственный.
3. **Согласование.** Девелопер принимает план или возвращает его с
   комментарием — партнёр правит и отправляет снова.
4. **Выполнение.** Партнёр по строке: «Взяли в работу» → фото со штампом и
   комментарий → «Сделано». Девелопер: «Подтвердить» или «Вернуть» с причиной.
   Перенос срока: партнёр просит новую дату с причиной, срок сдвигается только
   после согласия девелопера (D621).
5. **Закрыт** — когда подтверждены все строки.

## Сроки

- **Срок ответа планом** — дата начала отсчёта + `plan_due_days` методики
  (10 дней, D617, `src/domain/plan_due.py`). Тот же, что в письме.
- **Срок строки** — дата начала отсчёта + дни пункта методики (`days` в
  `checklist.csv`, не больше `deadlines.max_days` по классу из
  `scoring.json`; D3 — немедленно). Считает движок, веб числа не держит.
- Смена даты начала отсчёта пересчитывает все сроки, кроме перенесённых
  согласием.
- «Просрочено» не хранится, а считается на чтении (как сейчас `is_overdue`).

## Файл туда и обратно

- **Выгрузка** — xlsx из текущих строк. Колонки системы (№, класс, зона,
  нарушение) закрыты от правки; партнёр заполняет «что сделаем», «кто
  отвечает», «почему», «срок». В скрытой колонке — id строки, в скрытой ячейке —
  ревизия плана на момент выгрузки.
- **Загрузка** — файл разбирается по id строки в те же строки. Итог на экране:
  сколько строк прочитано, где не хватает меры или ответственного, какой срок
  не принят (позже допустимого или не дата), какие строки без пары пропущены.
  Сам файл сохраняется версией, как сейчас (`action_plan_files`), — для истории.
- **Конфликт.** Если с момента выгрузки план на экране поменяли (ревизия не
  совпала), система показывает разницу по строкам и спрашивает, какую версию
  оставить.
- Файл, который не разбирается (не наш шаблон), принимается вложением, как
  сейчас, с пометкой «не разобран — заполните на экране».

## Фото выполнения и штамп

- Штамп в правом нижнем углу: `ДД.ММ.ГГГГ ЧЧ:ММ · пиццерия · кто снял` (D621).
  Время местное для страны пиццерии. Ставится на сервере при сохранении кадра
  и вшит в файл; оригинал без штампа не хранится (как D250).
- Тот же штамп — на кадрах проверки из всех путей ввода: бот, мини-апп, веб,
  MCP. Общая точка — сохранение кадра в `src/db/photos.py` (сжатие перед
  `store.put`). Кадры исторического импорта (`origin = 'legacy'`) штамп
  сегодняшней датой не получают.
- Геометка: мини-апп и веб спрашивают браузер; отказ — фото принимается без
  неё. Бот: кнопка «Поделиться местом» один раз на проверку, место кладётся ко
  всем её кадрам. MCP: геометки нет (фото с компьютера), штамп есть.
- Координаты хранятся рядом с кадром, на кадр не печатаются. Дальше
  `FAR_METERS` (300 м) от адреса пиццерии — пометка «снято не на месте» у кадра.

## Уведомления

Колокольчик в шапке и красная точка на пункте меню и на строке, где есть новое
(D604, D614). Таблица `notifications` общая с ОСБ (#1129): кому, что, ссылка,
когда, прочитано. События плана:

| Событие | Кому |
|---|---|
| Запрос плана | партнёр страны |
| План отправлен на согласование | девелопер страны |
| План принят / возвращён | партнёр |
| Строка отмечена сделанной | девелопер |
| Строка подтверждена / возвращена | партнёр |
| Просьба о переносе / решение по ней | девелопер / партнёр |
| Срок строки через 2 дня, срок прошёл | партнёр; при просрочке — и девелопер |

Напоминания по срокам собирает раз в день фоновая задача. Telegram девелоперу и
почта закладываются каналами за флагом, выключены; тексты, адресаты и условие —
на отдельное «да» владельца (D614, правило «никакой коммуникации без
владельца»).

## Данные

| Таблица | Что |
|---|---|
| `action_plan_requests` | + `count_from date` (начало отсчёта), + `revision int`; статусы: `requested` (заполнение), `on_review`, `in_work`, `closed`; `accepted` старых файловых планов остаётся как есть |
| `action_plan_rows` | новая: запрос, запись проверки, снимок класса/зоны/формулировки, мера, ответственный, причина, срок, статус строки, причина возврата |
| `action_plan_row_photos` | новая: строка, путь в хранилище, текст штампа, широта, долгота, расстояние до пиццерии, кто, когда |
| `action_plan_extensions` | новая: строка, новая дата, причина, решение, кто и когда |
| `action_plan_events` | + `row_id` (пусто — событие плана целиком) |
| `notifications` | общая с ОСБ (#1129) |
| `countries` | + выбранный девелопер-учётка |

Права держит база, как сейчас (0036): партнёр пишет только свои строки и только
в своих статусах; вердикты — роль УК.

## Старые планы

Запросы, по которым уже лежит файл, остаются файловыми: панель показывает их
по-старому. Электронные строки заводятся у новых запросов и у открытых
запросов без файла.

## MCP (D620)

Чтение плана и строк, подтверждение и возврат строки, решение по переносу —
инструментами MCP тем же заходом. Заполнение плана партнёром — только веб и
файл.

## Порядок стройки

1. Колокольчик и `notifications` (#1129) — общий фундамент.
2. Строки плана, путь «заполнение → согласование → выполнение → закрыт»,
   отсчёт срока (D613), сроки строк из движка.
3. Файл туда и обратно с разбором и конфликтом.
4. Фото выполнения со штампом и геометкой; штамп на кадрах проверки во всех
   путях ввода (#1157).
5. Напоминания по срокам; каналы Telegram и почта за выключенным флагом.
6. MCP-инструменты плана.

Каждый шаг — отдельный PR с тестами на права и сроки (ядро: деньги здесь не
считаются, но срок и «кто подтвердил» партнёр читает как факт).
