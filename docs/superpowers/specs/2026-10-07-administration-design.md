# Администрирование: роли, права, пространства — в вебе и в MCP

> Спека. Ведётся руками. Опирается на решения владельца D017, D233, D282–D289,
> D304–D308 (`docs/furca/decisions.md`). Задачи: #340 (пространства, волна 2),
> #399 (мастер-админка), #452 (статический токен MCP), часть #334 (токен MCP
> привязан к человеку). Отделено в #526 (загрузка сторонних отчётов).
> Статус: **согласована владельцем** (07.10.2026, D309).

## Что строим

Decimus используют две стороны:

- **УК** ведёт эталонный чек-лист и работает со **всеми** проверками: своими,
  партнёрскими по странам и загруженными сторонними (D304, D305).
- **Партнёр** по стране работает только в своём пространстве. Эталон УК,
  проверки УК и сторонние проверки он не меняет. Править может только то,
  что завёл сам (D304).

Сейчас это держится на разрозненных проверках в коде и на переменных
окружения. Права MCP не знают ролей, а круг людей, которым бот выдаёт MCP,
никак не связан с учётками веба. Строим одну модель прав, которую
**настраивают в вебе** и которая одинаково действует в вебе, в боте и в MCP:

1. **Роли с матрицей «роль × действие»** (D306). Человеку назначается роль,
   галочки в матрице определяют, что роль может.
2. **Раздел «Администрирование»** (D308) на месте «Пользователей»:
   пространства, люди, роли и права.
3. **MCP и бот по тем же правам.** Токен наследует роль человека, переменные
   окружения права больше не задают.

## Поверхности

| Поверхность | Кто | Что делает |
|---|---|---|
| Веб → «Администрирование» → пространства | админ УК | заводит пространство страны и его админа (вместо `make space`) |
| Веб → «Администрирование» → люди | админ УК — везде; админ страны — у себя (D307) | добавляет сотрудника, назначает роль, отключает, правит почту |
| Веб → «Администрирование» → роли и права | админ УК | матрица галочек «роль × действие» |
| Бот → `/mcp` | роль с правом «подключение MCP» | выпуск личного токена и установка одной строкой (как сейчас) |
| MCP | владелец токена | видит и вызывает только разрешённые его роли инструменты |

## Сценарии

**УК заводит страну.** Админ УК в «Администрировании» нажимает
«+ Пространство», выбирает страну (одна страна принадлежит одному партнёру,
D284) и указывает почту админа страны. Админ страны входит через Google и
добавляет своих сотрудников. Роль он может назначить только из ролей страны.

**УК поправила данные партнёра.** Админ УК снимает проверку партнёра или
правит его предписание. Действие проходит, потому что УК действует во всех
пространствах, и пишется в журнал «кто, что, когда, в чьём пространстве»:
данные принадлежат владельцу пространства (D017).

**Партнёр подключает агента.** Сотрудник страны с правом «подключение MCP»
пишет боту `/mcp` и ставит MCP одной строкой. Агент видит проверки его
страны (включая проверки УК по ней, D289), правит методику его пространства,
если у роли есть это право, и не видит инструментов, которые роли закрыты.
Админ УК снимает галочку, и следующий вызов агента уже получает отказ.

## Глоссарий

- **Пространство** — тенант: УК (`HQ`) или партнёр, которому принадлежат
  страны (`space_countries`).
- **Роль** — набор прав внутри пространства. Роль относится либо к УК, либо
  к стране.
- **Действие** — код одной пишущей операции (`checklist.publish` и т. п.).
  Подписи переводятся, коды нет.
- **Граница** — правило «чьё пространство вправе действовать над чьим
  объектом». Зашита в коде и не настраивается.

## Модель прав

Решение `can(человек, действие, пространство_объекта)` принимается двумя
слоями. Отказ первого слоя не переопределяется вторым.

**Слой 1 — граница (код, не настраивается):**

- человек из УК действует в любом пространстве;
- человек страны действует только в своём пространстве;
- объект, принадлежащий УК, в том числе эталон, проверки УК и сторонние
  проверки (#526), человек страны не меняет никогда;
- действия «только УК» не выдаются роли страны ни одной галочкой: заводить
  пиццерии (D233), заводить пространства и назначать админов стран (D307),
  править матрицу ролей (D306).

Видимость остаётся как сейчас (`src/db/reach.py`, `reach_of`): УК видит всё,
партнёр — проверки пиццерий своих стран, кто бы их ни проводил (D289).

**Слой 2 — матрица (настраивается админом УК):** есть ли у роли человека
право на это действие.

### Каталог действий

Коды живут в коде (`src/domain/permissions.py`), по одному на каждую
пишущую операцию, которая уже есть. Новая операция получает свой код в
момент появления: это часть её готовности.

| Код | Операция (где сейчас) |
|---|---|
| `inspection.conduct` | провести проверку в боте |
| `inspection.retract` | снять проверку (веб, MCP `retract_inspection`) |
| `inspection.move` | перенести проверку (`inspection_moves`) |
| `inspection.letter` | черновик письма по проверке |
| `prescription.manage` | создать, править, отправить, закрыть предписание |
| `prescription.reply` | ответить на предписание |
| `plan.manage` | запросить план действий, рассмотреть, назначить срок |
| `plan.submit` | загрузить план действий |
| `checklist.edit` | правка пунктов, зон, развесовки, маршрута, кадров |
| `checklist.publish` | публикация версии |
| `checklist.manage` | создать, переименовать чек-лист, сменить состояние, открыть боту, применить |
| `phrases.manage` | убрать и переправить выученные синонимы |
| `people.manage` | добавлять сотрудников, назначать роли, отключать |
| `mcp.connect` | выпуск личного токена MCP в боте |
| `unit.create` | завести пиццерию — **только УК** |
| `space.manage` | завести пространство, назначить админа страны — **только УК** |
| `roles.manage` | править матрицу — **только УК** |

Каталог сверяется с маршрутами при реализации. Пишущая операция без кода в
каталоге — дефект, его ловит тест (см. «Проверка»).

### Роли по умолчанию

Миграция заводит четыре роли и переносит текущие учётки
(`web_users.role ∈ {admin, auditor}` × пространство):

| Роль | Пространство | Права по умолчанию |
|---|---|---|
| `hq_admin` | УК | все |
| `hq_staff` | УК | всё, кроме `people.manage`, `space.manage`, `roles.manage`, `unit.create` |
| `country_admin` | страна | все, кроме «только УК» |
| `country_staff` | страна | `inspection.conduct`, `inspection.letter`, `prescription.reply`, `plan.submit`, `mcp.connect` |

Набор прав по умолчанию повторяет то, что люди могут сейчас, с тремя
отличиями: УК пишет в пространства партнёров (D304); админ страны заводит
своих людей (D307); сотрудник страны больше не правит методику. Сейчас
маршруты правки ролью не ограничены (Q065), но по умолчанию это право
получает только админ страны, а админ УК может раздать его галочкой. Админ УК может завести новую роль
(название ru/en, пространство) и расставить ей галочки. Удалить роль, на
которой есть люди, нельзя.

## Данные

- `roles(code PK, scope ∈ {hq, country}, name_ru, name_en, created_at)`.
- `role_permissions(role_code FK, action_code, PK(role_code, action_code))`.
  Код действия проверяется по каталогу приложения при записи.
- `web_users.role` → FK на `roles.code`. Ограничение: роль `scope=hq`
  только у людей пространства `HQ`, роль `scope=country` только у людей
  страны.
- `mcp_tokens.web_user_id` → FK на `web_users`. Токен принадлежит учётке, а
  `telegram_id` остаётся как канал выдачи. Живые токены переносятся
  миграцией через привязку бота (`bot_bindings`). Токен, который не удалось
  сопоставить с учёткой, отзывается, а список таких токенов печатается при
  раскатке.
- `cross_space_actions(id, at, actor_web_user_id, actor_tenant,
  object_tenant, action_code, object_ref)` — журнал действий человека УК в
  пространстве партнёра. Пишется тем же вызовом, что и действие, в одной
  транзакции.
- Уходят: таблица `mcp_admins`; env `MCP_TOKENS`, `MCP_CHECKLIST_TENANTS`,
  `MCP_RETRACTION_TOKENS`, `BOT_MCP_OWNER_ID`. `DATABASE_RETRACTION_URL`
  (роль БД «администратор истории») остаётся: это граница прав базы, а не
  людей.

## Веб: «Администрирование»

Раздел `users` переименовывается в «Администрирование» (EN
«Administration»). Новой вкладки нет: навигация уже широкая, а раздел
`tenants` («Проект», `built=False`) снимается, его работа уходит сюда.

Вопрос экрана — «**кто в системе и что может**». Раскладка общая, как в
«Методике» и «Стране» (D296):

- **слева** колонка пространств: УК, затем страны. Админ УК видит все, админ
  страны только своё, сотрудник раздел не видит. Внизу колонки кнопка
  «+ Пространство» (только админ УК);
- **справа** люди выбранного пространства: имя, почта, роль (выбор из ролей
  этого пространства), привязан ли бот, кнопки «Добавить сотрудника» и
  «Отключить»;
- **«Роли и права»** — последний пункт колонки, только у админа УК. Справа
  матрица: строки — действия по группам каталога, столбцы — роли. Действия
  «только УК» в столбцах ролей страны не отображаются как галочка, а
  подписаны «только УК».

Свой пароль и привязку бота человек меняет, как и сейчас, у себя, без
доступа к остальному разделу. Все тексты заводятся на ru и en.

## MCP и бот

- `resolve_access` (`src/mcp/config.py`) принимает только личные токены из
  БД. На каждом вызове по токену берутся учётка, её пространство и её текущая
  роль, поэтому снятая галочка или отключённая учётка действуют со
  следующего вызова.
- Каждый инструмент каталога (`src/mcp/catalogue.py`) объявляет свой код
  действия, у читающих его нет. `tools/list` отдаёт только разрешённые
  роли, а вызов запрещённого возвращает отказ с кодом `forbidden`, без
  подробностей. Пространство объекта для слоя 1 берётся из самого объекта,
  а не из аргумента.
- Бот: `Binding` знает учётку и роль. `/mcp` видят те, у чьей роли есть
  `mcp.connect`. `/mcp_add`, `/mcp_revoke`, `/mcp_who` уходят: людей и роли
  ведут в «Администрировании». Свой токен человек по-прежнему отзывает
  сам.
- Сервисного доступа к MCP без человека не остаётся. Если он понадобится,
  это будет отдельная учётка с ролью, а не env.

## За рамками

- Загрузка сторонних отчётов — #526.
- Правка завершённого отчёта как новая операция: её сейчас нет. Когда
  появится, получит код в каталоге.
- RLS по тенанту в базе. Граница остаётся в коде, но в одном месте
  (`can`), а не размазанной.
- Единая сущность «человек» (#334) за пределами связи токен ↔ учётка.
- Личные исключения поверх роли (D306).

## Проверка

**Ядро — тестами вперёд** (права доступа, `testing.md`):

- таблица «роль × действие × пространство человека × пространство объекта
  → да/нет» для четырёх ролей по умолчанию, включая все запреты слоя 1;
- прогон той же таблицы на заведомо сломанной матрице, например с галочкой
  `checklist.edit` у страны над эталоном УК: тест обязан упасть и назвать
  нарушенное правило;
- тест полноты: каждый пишущий маршрут веба, каждая команда бота и каждый
  пишущий инструмент MCP проходят через `can` с кодом из каталога. Это
  закрывает и #271 со стороны прав;
- миграция: каждая текущая учётка получает роль с теми же возможностями,
  каждый живой токен сопоставлен с учёткой или отозван и показан в списке.

**Остальное — запуском** на тестовом стенде (MUSPELHEIM):

- MCP под токеном сотрудника страны: `tools/list` без закрытых инструментов,
  вызов правки эталона УК даёт `forbidden`; под токеном админа УК —
  снятие проверки партнёра проходит и появляется в журнале;
- снять галочку в матрице → следующий вызов MCP получает отказ;
- вход в веб каждой из четырёх ролей: что видно в «Администрировании»;
- снимки «Администрирования» на телефоне и десктопе, путь новичка «где
  добавить сотрудника?» за три клика;
- регрессия движка: `belgrade-1` 97.5% A, `belgrade-2` 97.0% A.

## Порядок стройки

Три блока, каждый раскатывается отдельно:

1. **Ядро прав:** таблицы, миграция ролей, `can`, журнал, тесты таблицы
   прав. Веб, бот и MCP переводятся на `can` без изменения поведения для
   людей.
2. **Веб «Администрирование»:** пространства, люди, матрица.
3. **MCP и бот:** токен ↔ учётка, фильтр `tools/list`, уход env-прав и
   `mcp_admins`.

Раскатка блока 3 меняет доступ живым пользователям MCP. Она идёт с
отдельного «да» владельца в ночное окно, со списком токенов, которые будут
отозваны.
