# Множественность чек-листов

> Спека. Ведётся руками. Опирается на решения владельца D177, D178, D180
> (`docs/furca/decisions.md`) и на разбор `docs/10-checklist-configuration.md`.
> Факты о коде проверены чтением и запуском 22.09.2026, а не по памяти.

## Что строим

Платформа перестаёт нести один эталонный чек-лист и начинает нести **много**:
девелоперский аудит, аудит РНД, любой другой, заведённый в систему. Чек-лист
настраивается целиком — состав, зоны, веса, маршрут, карта кадров, — и из
админки решается, какой из них идёт для проверки.

Критерий приёмки владельца: **новый чек-лист заводится руками с нуля**, а не
копией существующего.

Выбор чек-листа на старте конкретной проверки (бот или мини-приложение) в объём
**не входит** — D178 назвал это будущим. Но всё, что строится сейчас, обязано
этот выбор потом принять без переделки.

## Словарь

| Слово | Значение |
|---|---|
| **Чек-лист** (набор) | Методика целиком: семь файлов плюс своя история изданий. Опознаётся кодом |
| **Издание** (версия) | Снимок чек-листа на момент правки: `<имя набора>-<дата>-<12 знаков отпечатка>` |
| **В работе** | Состояние чек-листа: годен к употреблению. Таких может быть несколько |
| **Применён к проду** | Указатель: по этому чек-листу идут проверки, пока выбор на старте не спрашивают. Ровно один |
| **Дверь** | Способ править методику: файлы, CLI, MCP, экран админки |

## На чём стоим: что уже держит множественность

Проверено чтением кода. Это главная причина, по которой работа дешевле, чем
выглядит.

| Факт | Где | Что это значит |
|---|---|---|
| Движок получает каталог методики **на каждый вызов** | `src/domain/engine.py:161`, `env["CHECKLIST_DIR"]` | Движок к одной папке не привязан вовсе и переписывания не требует |
| Домен подменяет каталог **на проверку** | `src/domain/edition.py:224`, `pin()` | Проверка уже идёт по своей методике, а не по действующей |
| Карта кадров читается оттуда же | `src/recognize/cues.py:201` | Шов используется последовательно, а не только движком |
| Имя набора уже в идентификаторе издания | `src/domain/version.py` | Зацепка под код чек-листа есть |
| `tenant` — поле журнала, а не раздел хранилища | `src/mcp/checklist.py` | Положить чек-лист на арендатора нельзя: это разные вещи |

Допущение «методика одна» живёт ровно в трёх местах: `AUDIT_DATA_DIR` как
единственный живой каталог, `Store` как единственное хранилище версий, и бот,
который никогда не спрашивает, по какому чек-листу идёт проверка.

## Почему файлы, а не база

Решено D180. Методика остаётся файлами, потому что **движок читает именно их**.
Перенос чек-листов в таблицы завёл бы вторую копию правды: база — то, что правит
человек, папка — то, по чему считают партнёру, и между ними шаг генерации.

Довод не гипотетический. Разбор T302 нашёл в этом же продукте расхождение
справочной части с движком, читавших один файл: продукт поднимался, справочник
выглядел исправным, а отказ вылезал на точке у аудитора.

Дорога к базе при этом не закрыта: поверх файлов можно положить читающий индекс,
оставив файлы источником правды. Это добавление, а не переезд.

## Сущность «чек-лист»

| Поле | Правила |
|---|---|
| `code` | `^[a-z0-9][a-z0-9_-]{0,31}$` — тот же шаблон, что у имени набора сегодня. **Не меняется никогда**: им чек-лист связан с проверками в базе и со снимками на полке |
| `name_ru`, `name_en` | Название для человека. Меняется свободно — это формулировка |
| `state` | `draft` (черновик) / `active` (в работе) / `retired` (снят) |

Связь — кодом, показ — названием. Это требование проекта, а не украшение:
формулировки переводятся и правятся, коды нет.

**Состояния не совпадают с применением к проду.** «В работе» говорит, что
чек-лист годен к употреблению, и таких может быть несколько — это и есть задел
под выбор на старте. «Применён к проду» — указатель, и он ровно один, пока
выбора не спрашивают. Когда выбор появится, бот предложит все `active`, а
применённый к проду станет умолчанием. Переделки не потребуется.

**Удаления чек-листа нет.** Только `retired`: со строкой ушла бы история
проверок, посчитанных по нему. То же правило, что у точек (T338).

## Хранилище

Было:

```
<MCP_CHECKLIST_STORE>/
  current -> versions/<издание>
  versions/<издание>/
  journal.jsonl
```

Стало:

```
<MCP_CHECKLIST_STORE>/
  current -> <код>/current              # применён к проду
  <код>/
    meta.json                           # код, названия, состояние
    current -> versions/<издание>       # опубликованное издание ЭТОГО чек-листа
    versions/<издание>/                 # семь файлов методики
    journal.jsonl                       # журнал правок ЭТОГО чек-листа
```

Три следствия, каждое намеренно:

1. **`AUDIT_DATA_DIR` не меняется.** Он как и сегодня смотрит на
   `<store>/current`; поменялось лишь то, куда этот указатель ведёт. Площадку
   перенастраивать не нужно, а значит миграция не может разойтись с окружением.
   Сверка «движок читает методику из хранилища версий»
   (`src/mcp/checklist.py:1035`) остаётся на месте и продолжает работать.
2. **`meta.json` лежит РЯДОМ с изданиями, а не внутри.** Состояние чек-листа не
   входит в отпечаток методики: пометка «в работе» не должна порождать новое
   издание — она не меняет ни одного вопроса.
3. **Журнал на чек-лист, а не общий.** «Кто и что правил» читается по тому
   чек-листу, который смотрят, и не тонет в соседних.

**Миграция.** Существующее хранилище переносится в подкаталог с кодом по
умолчанию, `<store>/current` перенаправляется на его `current`. Миграция
обратима перемещением назад: ничего не переписывается, только перекладывается.

## Заведение с нуля

Сегодня хранилище заводится снимком боевой методики — для первого чек-листа
это верно, для второго негде взять базу. Поэтому новый чек-лист рождается из
**бланка**, лежащего в репозитории данными:

| Файл | Чем рождается |
|---|---|
| `checklist.csv` | только заголовок, ни одной строки |
| `zones.csv` | одна зона с долей 100% |
| `scoring.json` | бланк ставок и порогов из репозитория |
| `criteria.md` | пусто |
| `route.csv`, `photo-cues.md` | отсутствуют (законное состояние) |
| `checklist_version.txt` | имя набора и дата заведения |

Бланк — **данные, а не код**: его правка меняет то, с чего начинаются новые
чек-листы, и не трогает ни одного существующего.

Такой чек-лист рождается в состоянии `draft` и к проду не применяется — см.
заслон 1.

### Проверено запуском 22.09.2026

Пустая методика (заголовок без строк, одна зона 100%, боевой `scoring.json`)
проходит **всю** цепочку двери:

```
manage.py validate  → «вопросов: 0, зон: 1 / Всё в порядке.»          код 0
audit.py init       → состояние заведено                               код 0
audit.py score      → «Итог: 100%  оценка A — Соответствует стандарту» код 0
```

Заведение с нуля, таким образом, **возможно** — движок такую методику принимает.
И ровно поэтому обязателен заслон: она же даёт партнёру высшую оценку, не задав
ни одного вопроса (#339).

## Применение к проду

Одно движение: переставить `<store>/current` на `<код>/current`. Повторной
сверки движком при этом нет — она уже прошла, когда издание создавалось.

Откат — применение прежнего чек-листа. Никаких особых средств не нужно: это то
же движение в обратную сторону.

## Связь с проверкой

- В `inspections` добавляется `checklist_code` рядом с `checklist_version`.
  **Дописывается в конец списка выборки** — договорённость с соседней сессией по
  #338: разбор в `src/db/queries.py` позиционный, и вставка в середину молча
  сдвинет колонки, подставив в письмо партнёру одно вместо другого. Если к
  моменту работы #338 закроется переводом разбора на имена — ограничение
  снимается.
- Существующим строкам код проставляется миграцией: код того чек-листа, по
  которому они на деле шли. Это не переписывание задним числом (D033), а запись
  того, что и так было правдой.
- Полка снимков становится двухуровневой: `STATE_DIR/methodology/<код>/<издание>/`.
  Разные чек-листы могут дать одинаковое имя издания, и сегодня они легли бы друг
  на друга.

## Крючки MCP

Требование владельца: продумать в том же заходе, а не после.

**Правило, а не список: ни одна возможность не появляется только на экране.**
Каждая операция хранилища получает и маршрут веба, и инструмент MCP — в одном
изменении. Иначе двери расходятся молча, а это ровно то, чего вся конструкция
избегает.

**Существующие 24 инструмента** получают необязательный параметр `checklist`
(код):

- не передан → тот чек-лист, что применён к проду. Старые вызовы агента
  продолжают работать слово в слово;
- передан → именно он. Новые вызовы явные.

**Новые инструменты:**

| Инструмент | Что делает |
|---|---|
| `checklists` | Список: код, названия, состояние, применён ли к проду, текущее издание |
| `checklist_meta` | Один чек-лист целиком |
| `create_checklist` | Завести с нуля из бланка |
| `rename_checklist` | Поменять названия (не код) |
| `set_checklist_state` | Черновик / в работе / снят |
| `apply_checklist` | Применить к проду |

**Право.** Сегодня `may_manage_checklist` выдаётся арендатору целиком и градаций
не имеет. Заведение чек-листа и применение к проду ложатся под то же право —
заводить систему прав заодно с первой таблицей неправильно. Но применение к
проду тяжелее правки черновика, и это **открытый вопрос владельцу**, а не
решение спеки.

## Заслоны: что обязано отказывать

Каждый — со словами, а не молча, и каждый проверяется порчей.

1. **Чек-лист без пунктов вида `violation` к проду не применяется** (#339).
   Пустая методика даёт 100% и высшую оценку — сбой выходит наружу не ошибкой, а
   хорошей новостью. Заслон стоит на применении, а не в `validate`: «вопросов 0»
   для черновика законно.
2. **Код чек-листа не меняется ничем.** Им держится связь с проверками и
   снимками.
3. **Снятый (`retired`) к проду не применяется.**
4. **Применённый к проду не снимается.** Сначала применяется другой.
5. **Удаления чек-листа нет вовсе.**

## Границы

- **Выбор чек-листа на старте проверки** — не входит (D178), но конструкция его
  принимает: несколько `active` и указатель-умолчание.
- **Роли у учёток** — не входит. Всякий вошедший в админку правит методику
  наравне; круг узкий и заводится руками.
- **Правка весов партнёром** — нет и не будет (D132). Партнёр видит эталон
  чтением.
- **Вторая копия арифметики оценки** — никогда, ни под каким видом. Проценты,
  буква, разбивка и сроки приходят только из `audit.py score`; контракт
  `engine-not-imported` держит это на сборке.

## Чем проверяем

| Что | Как |
|---|---|
| Ничего не разошлось | `examples/belgrade-1` → 97.5%, A, 5×D1; `belgrade-2` → 97.0%, A, 6×D1 |
| Миграция не потеряла историю | Издания и журнал на месте после переноса; `<store>/current` ведёт туда же, куда вёл |
| Заведение с нуля работает | Завести чек-лист, добавить один пункт, применить к проду, провести проверку, получить оценку |
| Заслоны краснеют | Снять каждый заслон по очереди — прогон обязан упасть с внятной причиной |
| Старые вызовы MCP целы | Инструменты без параметра `checklist` дают тот же ответ, что до работы |

Ядро здесь — заслоны и миграция: ошибка в них выходит наружу правдоподобной
цифрой. Остальное проверяется запуском, а не модульным тестом.

## Волны

| # | Что | Виден ли результат человеку |
|---|---|---|
| 1 | Хранилище, сущность, миграция, заведение с нуля, крючки MCP | Только агенту по MCP |
| 2 | Экраны: список чек-листов, заведение, состояние, применение к проду | **Да** — это «решать из админки» |
| 3 | Полная настройка внутри: зоны с долями, веса, маршрут, карта кадров | **Да** — пять файлов из семи, которых у экрана нет |
| 4 | Признак сравнимости (#337) | **Да** — сводка перестаёт молча смешивать эталоны |

Волна 1 не видна человеку намеренно: она кладёт шов, на который встают
остальные. Строить экраны раньше значило бы делать их дважды — сегодня `/admin`
это «тот самый чек-лист», а станет «какой-то из».

## Открытые вопросы владельцу

1. **Право на применение к проду** — то же, что на правку, или отдельное?
   Сегодня ролей нет вовсе, и это единственное место, где их отсутствие заметно
   опасно.
2. **Код чек-листа по умолчанию** при миграции — как назвать существующую
   методику? Имя попадёт в базу к каждой уже проведённой проверке.
